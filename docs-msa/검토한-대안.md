# 검토한 대안

결정마다 "무엇을 놓고 골랐고, 왜 나머지를 버렸는가"를 적는다.
`결정기록.md` 가 고른 것의 근거와 검증을 적는다면, 이 문서는 고르지 않은 것을 적는다.
발표 질의응답에서 "다른 방법은 생각해 봤나"에 답하는 용도다.

점수는 판단을 숫자로 옮긴 것이고 측정값이 아니다. 측정한 값은 따로 "측정"이라고 적었다.

## 과제 조건

- 과제: 컨테이너, k8s 인프라 구축 / MSA 애플리케이션 구축 운영 (개인, 5일, 11월 19일~25일)
- 평가 역량: 클라우드 플랫폼 관리, 컨테이너화 기술, 컨테이너 오케스트레이션
- 직접 정한 주제: 클러스터를 지워도 명령 한 번으로 복원된다. dev 는 main 을 따라가고 prod 는 태그에 고정한다.
- 이어지는 과정: 마지막에 기업 연계 실무 프로젝트가 있다. 이번에 실무에 가까운 구성을 한 번 해 본다.

## 1. 서비스를 몇 개로 나눌까

| 선택지 | 판단 |
|---|---|
| **3개 (고름)** | 원래 패키지 경계와 같다. 서로 부르는 코드(`staff` → `reservation`)를 한 서비스에 두어 서비스 간 호출이 0건이다. |
| 하나로 유지 | 경로 분기, 개별 배포, 장애 격리를 보여 줄 수 없다. 과제의 부제가 MSA 다. |
| 더 잘게 (공지 분리, 직원 화면 분리) | 직원 화면을 떼면 예약 서비스를 네트워크로 불러야 한다. 한쪽이 죽으면 같이 실패한다. 공지만 떼는 것은 서비스 수만 늘린다. |

- **다시 볼 조건**: 서비스마다 팀이 다르거나, 부하가 한 기능에만 몰려 그 기능만 따로 늘려야 할 때.

## 2. DB 안의 경계 (결정 대기, 임시 환경에서 검증함)

쓰기가 겹치는 테이블은 `slots` 하나다. clinic 이 줄을 추가하고 reservation 이 그 줄을 고친다. 나머지 테이블은 주인이 하나씩이다.

| 선택지 | 점수 | 강점 | 문제점 |
|---|---|---|---|
| **스키마 + 뷰 (제안)** | 86.5 | 앱 코드를 안 고친다. 남의 데이터는 주인이 내준 뷰로만 읽는다. 예약 서비스가 비밀번호 해시를 볼 수 없다. 중복 예약 방지 트랜잭션이 그대로다. | MySQL 은 여전히 하나다. 뷰와 권한을 관리할 초기화 스크립트가 길어진다. |
| 계정만 분리 | 85.5 | 앱 코드를 안 고친다. 테이블별 권한으로 주인을 강제한다. | 스키마가 하나라 경계가 눈에 덜 보인다. 열 단위로는 못 가린다. |
| 스키마 분리 (SQL 에 이름을 붙임) | 77.5 | 남의 데이터를 읽는 곳이 코드에 드러난다. | SQL 을 파일 7개쯤 고쳐야 한다. 원본 코드를 그대로 옮겼다는 장점을 잃는다. |
| 현행 (공용 계정 하나) | 76.5 | 할 일이 없다. | 경계가 어디에도 없다. auth 계정으로 예약 테이블을 지울 수 있다. |
| 완전 분리 (서비스별 MySQL) | 57.0 | 교과서적인 MSA 다. | 예약과 슬롯이 다른 DB 로 가면 한 트랜잭션으로 묶을 수 없다. 예약 서비스가 clinic 에 물어봐야 해서 장애 격리가 나빠진다. 서비스 경계부터 다시 그려야 한다. |

- 기준과 가중치: 발표 방어력 25, 구현 위험·기간 25, 장애 격리 15, 기존 동작 보존 15, 복원 단순성 10, 최소 권한 10.
- 발표 방어력을 40 으로 올려도 순위는 바뀌지 않았다.
- **다시 볼 조건**: 서비스마다 DB 종류나 크기를 다르게 가져가야 할 때. 그때는 슬롯을 예약 서비스로 옮기는 것부터 한다.

**스키마 + 뷰 검증 (11월 12일, 별도의 임시 compose 환경, 서비스 이미지는 그대로)**

| 스키마 | 테이블 | 뷰 (남의 데이터) |
|---|---|---|
| `auth` | users | – |
| `clinic` | pets, notices, vets, slots | – |
| `reservation` | reservations | pets, vets, users(비밀번호 해시 제외), slots(예약 번호와 열림 여부만 수정 가능) |

| 확인한 것 | 결과 |
|---|---|
| 코드와 이미지를 바꾸지 않고 smoke (격리 제외 22개) | 22개 통과 |
| auth 계정으로 예약·반려동물 읽기 | 거부 (`ERROR 1142`) |
| clinic 계정으로 사용자 읽기, 예약 지우기 | 거부 |
| reservation 계정으로 비밀번호 해시 읽기 | 뷰에 그 열이 없음, 원본 테이블은 거부 |
| reservation 계정으로 반려동물 이름 바꾸기, 슬롯 시각 바꾸기, 슬롯 지우기 | 거부 |
| 보호자 9명이 같은 시간을 신청 | 1명만 201, 8명은 409 `SLOT_TAKEN`. 실패한 쪽의 예약 수는 그대로(롤백됨) |
| 같은 반려동물로 같은 날 두 번째 신청 | 409 `PET_SAME_DAY` |

## 3. DB 를 어디서 돌릴까 (결정 대기)

| 선택지 | 과제 역량과의 관계 | 강점 | 문제점 |
|---|---|---|---|
| MySQL Pod, 디스크 없음 | 컨테이너화, 오케스트레이션 | 10초 만에 뜬다(측정). 어느 가용 영역으로든 옮겨 간다. 클러스터를 다시 만들면 같은 초기 상태가 된다. | Pod 가 다시 뜨면 데이터가 초기화된다. 노드가 죽으면 1~6분 멈춘다(예상). |
| MySQL Pod + 디스크(PVC) | 오케스트레이션의 저장소 | 재시작해도 데이터가 남는다. | 디스크가 있는 가용 영역에 묶인다. EBS 드라이버와 IAM 설정이 필요하다. |
| RDS Multi-AZ | 클라우드 플랫폼 관리 | 노드나 가용 영역이 죽어도 데이터가 남는다. 백업과 장애 조치를 AWS 가 한다. 실무에서 가장 흔한 구성이다. | 만드는 데 15~20분 걸린다. 비용이 든다. 접속 정보를 클러스터에 넣는 경로가 필요하다. |

- **제안**: dev 는 Pod(지웠다 만들기 쉽고 비용이 없다), prod 는 RDS Multi-AZ(데이터를 지킨다). 환경마다 위험과 비용에 맞춰 다르게 가져가는 것 자체가 실무 방식이다.
- 앱은 접속 주소와 계정만 바꾸면 RDS 에 붙는다. 코드는 같다.
- **직접 정한 주제와의 관계**: RDS 를 클러스터 바깥에 두면 클러스터를 지웠다 만들어도 데이터가 남는다. "클러스터에는 상태가 없다"는 말이 오히려 분명해진다.

## 4. 노드(EC2) 구성

이미지가 6종류라고 EC2 가 6대 필요한 것이 아니다. 노드 위에 Pod 30개 안팎이 함께 올라간다.

**측정 (11월 12일, 로컬 Docker, 초당 80건 처리 중)**

| 컨테이너 | 메모리 | CPU |
|---|---|---|
| auth, clinic, reservation | 170~227MiB | 0.07~0.17코어 |
| web (Apache) | 15~19MiB | 0.12코어 |
| mysql | 190MiB (디스크 기준) | 0.06코어 |
| redis | 32MiB | 0.02코어 |

- 서비스가 뜰 때 하나당 CPU 10~11초를 쓴다. 평소보다 이때가 훨씬 무겁다.
- 전체 필요량: 메모리 약 4.1GiB, CPU 약 2코어, Pod 25개 + 노드당 2개. Argo CD 몫(1GiB)은 재지 못한 추정이다.

**조사**: Pod 한도는 t3.small 11개, t3.medium 17개, t3.large 35개. 노드가 실제로 내주는 메모리는 t3.medium 약 3.3GiB, t3.large 약 7.0GiB. 서울 리전 시간당 단가는 0.026, 0.052, 0.104달러.

| 구성 | 메모리 사용률 | Pod 사용 | 1대가 죽으면 | 5일 비용 | 판단 |
|---|---|---|---|---|---|
| **t3.medium 3대 (제안)** | 42% | 31 / 51 | 받아낸다 | 약 19달러 | 82.5점 |
| t3.large 2대 | 30% | 29 / 70 | 받아낸다 | 약 25달러 | 72.0점. 1대가 전체의 절반이다. |
| t3.medium 2대 | 63% | 29 / 34 | 못 받는다 | 약 12달러 | 61.5점. 롤링 업데이트 때 Pod 한도에 닿는다. |
| t3.small 4대 | 72% | 33 / 44 | 사실상 못 받는다 | 약 12달러 | 59.0점. 노드당 메모리가 작아 배치가 자주 실패한다. |

- **확인하지 못한 것**: EC2 에서의 실제 사용량, Argo CD 사용량, t3 의 CPU 크레딧 소진 여부.

## 5. 웹 서버

| 선택지 | 판단 |
|---|---|
| **Apache 와 nginx 두 벌 (고름)** | 과제 요구는 Apache 다. 나중에 nginx 로 바꿀 계획이라 겉으로 보이는 동작을 같게 맞췄다. 전환은 이미지 태그 한 줄이다. 같은 smoke 44개가 양쪽에서 통과한다(측정). |
| Apache 만 | 전환할 때 설정을 새로 쓰고 검증도 새로 해야 한다. |
| nginx 만 | 과제 요구와 다르다. |
| Ingress 컨트롤러 | 실무에서는 흔하지만 이번에는 쓰지 않기로 했다. 경로 분기를 웹 서버 설정으로 직접 보여 준다. |

## 6. 초기 데이터

| 선택지 | 판단 |
|---|---|
| **DB 가 뜰 때 그날 기준으로 생성 (고름)** | 언제 다시 만들어도 "오늘부터 14일"이 들어 있다. 준비까지 10초(측정). |
| 고정 `seed.sql` 을 그대로 넣기 | 10월 23일 기준이라 예약과 이벤트 기간이 전부 과거로 들어간다. |
| 고정 시드 + 슬롯 생성기에 재시도 추가 | 앱 코드를 고쳐야 한다. owner001 의 예약 3건은 여전히 과거다. |

## 7. 죽은 서비스의 응답

| 선택지 | 판단 |
|---|---|
| **웹 서버가 503 JSON 으로 통일 (고름)** | 화면이 `code` 와 `message` 를 읽는다. Apache 는 상황에 따라 500, 502, 503 을 내므로 하나로 맞췄다. |
| 웹 서버 기본 오류 페이지 | HTML 이 와서 화면이 "서버에 문제"라는 일반 문구로 떨어진다. |
| 서비스의 오류까지 웹 서버가 바꾸기 | 401, 409, DB 없음(503) 같은 서비스의 뜻 있는 응답이 가려진다. |

## 8. 헬스 체크와 상태 응답

| 선택지 | 판단 |
|---|---|
| **DB 를 보지 않는다 (고름)** | DB 가 잠깐 끊겨도 멀쩡한 Pod 가 전부 재시작되지 않는다. 서비스가 DB 보다 먼저 떠도 된다. |
| DB 까지 확인 | DB 장애가 모든 Pod 의 재시작으로 번진다. 복구가 더 늦어진다. |
| 상태를 한 곳에서 모아 주기 | 그 한 곳이 죽으면 상태 화면 전체가 "응답 없음"이 된다. 서비스마다 경로를 둬야 그 줄만 바뀐다. |

- **알고 있는 한계**: 상태 쪽지의 "정상"은 프로세스가 답한다는 뜻이다. DB 가 죽어도 "정상"으로 보인다.

## 9. 저장소와 이미지 공개 여부

| 선택지 | 판단 |
|---|---|
| **둘 다 공개 (고름)** | 데이터와 계정이 전부 가짜다. 복원할 때 넣어야 하는 인증 정보가 없다. |
| 비공개 (ghcr.io) | Argo CD 용 토큰과 이미지 풀 시크릿이 필요하다. 토큰이 만료되면 조용히 고장 난다. |
| ECR | 노드가 IAM 역할로 받아 시크릿이 필요 없다. 실무에서 흔하다. 이미지 주소에 계정 ID 가 들어간다. |

- **다시 볼 조건**: 실제 코드나 데이터를 다루게 될 때. 그때는 ECR 이 먼저다.

## 10. 배포 파일 도구

| 선택지 | 판단 |
|---|---|
| **Kustomize (고름)** | dev 와 prod 의 차이(복제본 수, 분산, 이미지 태그)가 작다. 바탕 하나에 차이만 덧씌우면 된다. kubectl 에 들어 있다. |
| Helm | 값 주입과 배포판 관리가 강하지만, 직접 쓰는 앱 하나에는 템플릿 문법이 짐이다. |

## 실무와 다른 점 (알고 두는 것)

이번 구성에서 일부러 단순하게 둔 부분이다. "실무라면 어떻게 하나"에 대한 답이다.

| 지금 | 실무라면 |
|---|---|
| HTTP 만 쓴다 | 인증서를 붙여 HTTPS 로 받는다. |
| web 의 Service(LoadBalancer) 하나로 노출 | 로드밸런서 컨트롤러와 Ingress 로 받고 도메인을 붙인다. |
| Secret 을 명령으로 직접 만든다 | 비밀 저장소(예: AWS Secrets Manager)에서 클러스터로 동기화한다. |
| Redis 가 Pod 하나다 | 관리형 캐시를 쓰거나 복제를 둔다. 지금은 Redis 가 다시 뜨면 모두 로그아웃된다. |
| 상태 쪽지와 `kubectl` 로 본다 | 지표와 로그를 모아 대시보드와 경보를 건다. |
| 테스트 계정이 공개돼 있다 | 접속 대역을 제한하거나 계정을 따로 발급한다. |
