# ② 컨테이너 이미지 — Docker 런타임 테스트

①에서 확인한 앱을 이미지로 만들고, 웹 서버·DB·Redis 와 함께 Docker 에서 띄워 확인한 기록이다.
이 단계에서 보는 것은 "이미지가 맞게 만들어졌는가", 그리고 "컨테이너 여럿이 함께 떠서 하나의 서비스로 동작하는가"다.

- 테스트한 날: 11월 12일 ~ 13일
- 환경: Windows 11, Docker Desktop (엔진 29.8.2), Docker Compose v5.6.0
- 안에 든 버전: Temurin JRE 21.0.13, httpd 2.4.71, nginx 1.30.6, MySQL 8.4.13, Redis 7

## 무엇을 만들었나

### 이미지 6개

| 이미지 | Dockerfile | 안에 든 것 | 실행 사용자 | 크기 |
|---|---|---|---|---|
| `vet-auth:1.0.0` | `msa/auth-service/Dockerfile` | JRE 21 + 풀어 놓은 jar | 10001 | 357MB |
| `vet-clinic:1.0.0` | `msa/clinic-service/Dockerfile` | 〃 | 10001 | 357MB |
| `vet-reservation:1.0.0` | `msa/reservation-service/Dockerfile` | 〃 | 10001 | 357MB |
| `vet-web:1.0.0-apache` | `msa/web/Dockerfile.apache` | Apache httpd + 빌드된 화면 | 82 | 115MB |
| `vet-web:1.0.0-nginx` | `msa/web/Dockerfile.nginx` | nginx + 빌드된 화면 | 101 | 109MB |
| `vet-db:1.0.0` | `msa/db/Dockerfile` | MySQL 8.4 + 스키마·시드 생성기·초기화 도구 | 공식 이미지 방식 | 1.27GB |

- 서비스와 web 이미지는 두 단계로 만든다. 앞 단계에서 빌드하고(JDK·Gradle, Node), 뒤 단계에는 실행에 필요한 것만 옮긴다.
- 서비스 이미지는 jar 를 통째로 넣지 않고 라이브러리(36MB)와 우리 코드(12KB)로 풀어서 넣는다. 코드만 고치면 작은 층만 새로 올라간다.
- 모든 이미지에 빌드할 때 넣은 버전이 들어 있다. 이미지 태그와 같은 값이다.
- web 은 두 벌이다. 포트(8080), `/health`, 응답 헤더, 환경 변수, 오류 응답이 같아서 태그만 바꾸면 전환된다.

### 함께 띄우는 구성 (`compose.yaml`)

```
브라우저 ──▶ web (Apache 또는 nginx, 밖으로 열린 유일한 포트)
               ├─ /api/auth/…, /api/status/auth                    ──▶ auth
               ├─ /api/pets, /api/notices, /api/slots,
               │  /api/admin/notices, /api/status/clinic            ──▶ clinic
               ├─ /api/reservations, /api/admin/…, /api/director/…,
               │  /api/status/reservation                           ──▶ reservation
               └─ 그 밖: 소개 페이지, 예약 화면(/app), 상태 쪽지(/status)

auth, clinic, reservation ──▶ mysql (서비스마다 자기 스키마와 계정)
                          ──▶ redis (로그인 세션, 셋이 함께 읽음)
```

- 비밀번호 5개는 `.env` 에서 읽는다. `.env` 는 커밋하지 않고 `.env.example` 만 둔다.
- 일부러 뜨는 순서를 정하지 않았다(`depends_on` 없음). 쿠버네티스에서는 순서를 보장할 수 없기 때문이다.
- DB 에는 볼륨이 없다. 컨테이너가 다시 뜨면 스키마와 그날 기준 시드로 돌아간다.

## 어떻게 테스트했나

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\new-env.ps1    # .env 만들기 (처음 한 번)
docker compose up -d --build                                               # 이미지 6개 중 5개를 만들고 6개 컨테이너를 띄운다
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\smoke.ps1      # 54개 항목
```

웹 서버를 바꿔 같은 테스트를 한 번 더 한다. `.env` 의 `WEB_SERVER` 를 `nginx` 로 바꾸고:

```powershell
docker compose up -d --build web
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\smoke.ps1
```

`smoke.ps1` 은 브라우저와 같은 길(web 을 거쳐서)로 요청한다. 만든 예약은 스스로 취소하므로 여러 번 돌려도 된다.

### 이 단계에서만 볼 수 있는 것

| 확인한 것 | 방법 | 결과 |
|---|---|---|
| 이미지가 root 가 아닌 사용자로 뜬다 | `docker exec … id`, 이미지 설정 | 서비스 `uid=10001`, Apache `82`, nginx `101` |
| JVM 이 컨테이너 메모리 한도를 따른다 | 한도 512MiB 에서 JVM 설정 출력 | 힙 최대 256MB(한도의 50%), GC 는 Serial |
| 종료 신호에 정리하고 끝난다 | `docker stop` 뒤 로그 | `Commencing graceful shutdown` → `Graceful shutdown complete`, 0.6초 |
| 시간대가 컨테이너와 무관하다 | 컨테이너 시계와 서비스 로그 | 컨테이너는 `UTC`, 서비스 로그는 `+09:00` |
| 층이 재사용된다 | 소스를 안 바꾸고 다시 빌드 | 모든 단계 `CACHED` |
| 한 서비스가 멈춰도 나머지는 동작한다 | smoke 5번 | 22개 통과 |
| 멈춘 서비스의 경로는 HTML 이 아니라 JSON 503 이다 | clinic 을 멈추고 `/api/notices` | `503`, `application/json`, `{"code":"SERVICE_UNAVAILABLE",…}` |
| 서비스의 IP 가 바뀌어도 웹 서버를 다시 띄우지 않는다 | clinic 을 다른 IP 로 다시 만듦 | nginx 2초, Apache 3초 만에 새 컨테이너가 응답. 웹 서버 재시작 없음 |
| 뜨는 순서가 뒤바뀌어도 정상이 된다 | web → 서비스 → DB·Redis 순으로 띄움 | 중간에 죽지 않고 503 JSON. DB 가 뜬 뒤 재시작 없이 smoke 통과 |
| DB 를 다시 띄우면 초기 상태가 된다 | 값을 바꾸고 `docker restart` | 원래 값으로 복원. 준비까지 10초 |
| 웹 서버를 바꿔도 같다 | Apache ↔ nginx | 같은 smoke 54개가 양쪽에서 통과 |
| 한 서비스만 새 버전으로 바꾼다 | clinic 만 `1.0.1` 로 다시 올림 | clinic 만 `1.0.1`, 나머지는 `1.0.0` 그대로 |
| 상태 쪽지가 그 줄만 바뀐다 | clinic 을 멈췄다 켬 | clinic 줄만 "응답 없음", 켜면 새로고침 없이 "정상" |
| 같은 이미지로 바깥 DB 를 초기화한다 | 빈 MySQL 을 RDS 대신 세움 | 처음 실행 성공, 다시 실행하면 건너뜀, 강제 재생성 성공 |

### 자원 사용량 (③ 쿠버네티스의 requests 근거)

`docker stats` 와 cgroup 값으로 쟀다. 초당 80건을 처리하는 동안의 값이다.

| 컨테이너 | 메모리 | CPU |
|---|---|---|
| auth, clinic, reservation | 170~227MiB (최고 221MiB) | 0.07~0.17코어 |
| web (Apache) | 15~19MiB | 0.12코어 |
| web (nginx) | 11MiB (유휴) | 재지 않음 |
| mysql | 190MiB (디스크 기준), 440MiB (tmpfs 포함) | 0.06코어 |
| redis | 32MiB | 0.02코어 |

서비스가 뜰 때는 하나당 CPU 10~11초를 쓴다. 평소보다 이때가 훨씬 무겁다.

## 발견한 문제와 조치

| 문제 | 원인 | 조치 |
|---|---|---|
| smoke 첫 실행에서 3개 실패. 멈춘 서비스의 경로가 500 HTML 을 돌려줬다. | Apache 2.4.71 은 이름을 못 찾으면 500 을 낸다. 502 일 것이라 짐작하고 500 을 빼놓았다. | 로그(`AH00898`)를 보고 500 도 503 JSON 으로 바꾸게 했다. |
| Apache 의 `ErrorDocument` 는 본문만 바꾸고 상태 코드는 그대로 둔다. | Apache 의 동작이다. | 상태 줄까지 적어 둔 `.asis` 파일을 오류 문서로 쓴다. |
| 고정 시드를 넣으니 예약과 이벤트 기간이 전부 과거였다. | `db/seed.sql` 이 10월 23일 기준으로 만든 파일이다. | DB 가 뜰 때 그날 기준으로 시드를 만든다. `db/` 의 파일은 고치지 않았다. |
| 호스트 8080 포트를 쓸 수 없었다. | PC 에 Apache 가 서비스로 깔려 있다. | 기본 포트를 8088 로 했다. |
| 바깥 DB 의 강제 재생성(`VET_FORCE=1`)이 실패했다. | 스키마끼리 외래 키로 서로 참조해 삭제가 막혔다. | 지우는 동안만 외래 키 검사를 끈다. |
| 중복 예약 시험이 한 번 무효가 됐다. | 일요일(휴진)을 골라 빈 시간이 없었다. | 진료일로 바꿔 다시 했다. 9명 중 1명만 예약됐다. |

## 한계

- **DB 를 다시 띄우면 예약 데이터가 사라진다.** 의도한 동작이다. prod 는 RDS 를 쓴다.
- **MySQL 서버는 하나다.** 스키마와 계정은 서비스별로 나눴지만 서버가 죽으면 세 서비스가 모두 영향을 받는다.
- **auth 가 멈춘 동안 화면을 새로고침하면 로그인 화면이 나온다.** API 는 계속 되지만 화면 코드가 그렇게 동작한다. 화면을 바꾸지 않기로 해서 고치지 않았다.
- **compose 에서 Apache 는 멈춘 서비스 경로에 몇 초 늦게 응답한다.** 이름 조회가 실패할 때까지 기다린다.
- **`vet-db` 이미지가 1.27GB 다.** MySQL 공식 이미지가 1.12GB 다.
- **자원 사용량은 이 PC 에서 가벼운 부하로 잰 값이다.** 이미지의 압축 크기는 재지 않았다.
- **상태 쪽지의 "정상"은 DB 까지 본 결과가 아니다.**
- **실제 RDS 에서는 초기화를 돌려 보지 않았다.**
