# ③ 쿠버네티스 — 매니페스트와 오케스트레이션 테스트

②에서 확인한 이미지를 쿠버네티스 배포 파일로 올려 확인한 기록이다.
이 단계에서 보는 것은 "배포 파일이 맞는가", 그리고 "쿠버네티스가 대신 해 주는 일(무중단 배포, 자동 복구)이 실제로 되는가"다.

- 테스트한 날: 11월 13일
- 환경: Docker Desktop 의 쿠버네티스 (kind, 노드 1개, v1.36.1), kubectl v1.36.1 (Kustomize v5.8.1)
- 이 단계는 로컬 클러스터까지다. EKS 에서만 볼 수 있는 것은 ④에서 다룬다.

## 무엇을 만들었나

`gitops/apps/vet/` 아래에 Kustomize 로 만들었다.

```
gitops/apps/vet/
├── base/                      환경과 무관한 바탕
│   ├── web.yaml               Deployment + Service(LoadBalancer). 밖에서 들어오는 유일한 길
│   ├── auth.yaml              Deployment + Service
│   ├── clinic.yaml
│   ├── reservation.yaml
│   └── redis.yaml
├── components/                DB 를 어디서 쓸지 고르는 조각 (둘 중 하나)
│   ├── db-in-cluster/         MySQL Pod (디스크 없음)
│   └── db-external/           바깥 DB(RDS) + 초기화 Job
├── overlays/
│   ├── dev/                   네임스페이스 dev, 복제본 1개, MySQL Pod
│   └── prod/                  네임스페이스 prod, 복제본 2개, 분산, PDB, HPA, 바깥 DB
└── secrets.example.yaml       Secret 의 이름과 키만 (값 없음, 배포되지 않음)
```

### dev 와 prod 의 차이

| | dev | prod |
|---|---|---|
| 복제본 (web, auth, clinic, reservation) | 1개씩 | 2개씩 |
| 배치 | 제한 없음 | 서로 다른 노드에 강제, 가용 영역은 되도록 나눔 |
| 배포·정비 중 보장 | – | 최소 1개 유지 (PodDisruptionBudget 4개) |
| 자동 확장 | – | reservation 2~4개 (CPU 70%) |
| DB | 클러스터 안의 MySQL Pod | 바깥 DB + 초기화 Job |
| 이미지 태그 | `overlays/dev/kustomization.yaml` 의 `images` | `overlays/prod/kustomization.yaml` 의 `images` (고정) |

- 이미지 태그는 환경마다 한 곳에서만 정한다. dev 의 값이 바뀌어도 prod 는 그대로다.
- prod 의 DB 는 `components:` 한 줄로 고른다. RDS 가 준비되지 않았으면 그 줄을 `db-in-cluster` 로 바꿔 dev 와 같은 방식으로 띄울 수 있다.
- Secret 은 Git 에 없다. 배포 파일은 이름과 키만 참조하고, 값은 `scripts\new-k8s-secrets.ps1` 이 클러스터에 직접 넣는다.

### 컨테이너마다 넣은 것

| 항목 | 설정 | 근거 |
|---|---|---|
| 프로브 | 서비스: startup·readiness·liveness 모두 `/health`. web: readiness·liveness. mysql: 서비스 계정으로 시드를 읽어 본다 | `/health` 는 DB 를 보지 않는다. DB 가 늦게 떠도 Pod 는 준비되고, 그동안 API 는 503 JSON 을 돌려준다 |
| requests / limits | 서비스 100m·256Mi / 1코어·512Mi, web 50m·32Mi / 500m·128Mi, mysql 100m·256Mi / 1코어·768Mi, redis 25m·32Mi / 250m·128Mi | ②에서 잰 값: 서비스 170~227MiB, web 15~19MiB, mysql 190MiB, redis 32MiB. 서비스는 뜰 때 CPU 10초를 쓰므로 CPU 한도를 넉넉히 뒀다 |
| 배포 방식 | `maxSurge 1`, `maxUnavailable 0` | 새 Pod 가 준비된 뒤에 옛 Pod 를 내린다 |
| 종료 처리 | `preStop` 에서 5초 대기 → 종료 신호 → 처리 중인 요청을 마침 | 대기하는 5초 동안 Service 에서 빠진다. 그 뒤에 종료가 시작돼야 요청이 끊기지 않는다 |
| 보안 | root 아님, 권한 상승 금지, 모든 capability 제거. 서비스와 redis 는 루트 파일 시스템 읽기 전용 | |
| 노드 장애 대비 | mysql 과 redis 는 노드가 죽으면 30초 뒤 다른 노드로. 둘은 되도록 다른 노드에 둔다 | 기본값은 5분이다. 한 대가 죽었을 때 데이터와 로그인을 한꺼번에 잃지 않게 한다 |

## 어떻게 테스트했나

```powershell
# 1) 배포 파일이 오류 없이 만들어지는지
kubectl kustomize gitops\apps\vet\overlays\dev
kubectl kustomize gitops\apps\vet\overlays\prod

# 2) dev 를 로컬 클러스터에 올린다
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\new-k8s-secrets.ps1 -Namespace dev
kubectl apply -k gitops\apps\vet\overlays\dev

# 3) ②와 같은 기능 테스트 (서비스를 멈출 때 kubectl scale 을 쓴다)
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\smoke.ps1 -BaseUrl http://localhost -Isolation k8s -Namespace dev

# 4) 쿠버네티스에서만 볼 수 있는 운영 동작
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\test-k8s-ops.ps1 -Namespace dev -BaseUrl http://localhost
```

로컬 클러스터는 로컬에서 만든 이미지를 보지 못한다. 배포 전에 이미지 6개를 노드에 넣었다(명령은 `로컬실행.md`).

prod 구성은 RDS 대신 아무것도 없는 MySQL 을 다른 네임스페이스에 세워 놓고(`scripts\k8s\fake-external-db.yaml`) 같은 테스트를 했다.

## 발견한 문제와 조치

자세한 과정은 [문제와-해결.md](문제와-해결.md) 의 17 ~ 19번에 있다.

| 문제 | 조치 |
|---|---|
| 로컬 클러스터가 로컬에서 만든 이미지를 보지 못한다 | 배포 전에 이미지를 노드에 넣는다 |
| prod 의 LoadBalancer 가 주소를 받지 못했다 | 로컬에서는 80 포트를 하나만 쓸 수 있다. dev 의 Service 를 잠시 내부용으로 바꿨다 |
| 자동 복구 시간을 재는 방법이 처음에는 틀렸다 | 옛 Pod 가 사라진 때가 아니라, 새 Pod 가 응답한 때를 응답 헤더로 구분해 잰다 |

이 단계는 처음 시도에 배포가 됐다. ①과 ②에서 뜨는 순서, 죽은 서비스의 응답, DB 초기화를 미리 풀어 둔 덕이다.

## 한계 — 로컬에서 확인하지 못한 것

| 항목 | 이유 | 어디서 확인하나 |
|---|---|---|
| 복제본이 서로 다른 노드에 놓이는지 | 노드가 1개다 | ④ EKS |
| 가용 영역 분산 | 영역이 없다 | ④ EKS |
| 노드가 죽었을 때 30초 뒤 옮겨 가는지 | 노드를 죽이면 클러스터가 사라진다 | ④ EKS |
| 자동 확장(HPA)이 실제로 늘리는지 | 지표 서버가 없어 CPU 값이 `<unknown>` 이다. 최소 2개는 유지됐다 | ④ EKS (metrics-server 애드온) |
| AWS 로드밸런서가 만들어지는지 | 로컬은 Docker Desktop 이 localhost 로 열어 준다 | ④ EKS |
| 레지스트리(ghcr.io)에서 이미지를 받는지 | 이미지를 노드에 직접 넣었다. 레지스트리에는 아직 올리지 않았다 | ④ EKS |
| 실제 RDS 에서의 초기화 | 빈 MySQL 로 대신했다 | ④ EKS |
| web 과 mysql 의 루트 파일 시스템 읽기 전용 | 두 이미지는 시작할 때 설정 파일과 데이터를 쓴다. 적용하지 않았다 | – |

그 밖의 한계:

- **dev 는 복제본이 1개라 Pod 가 죽으면 그 서비스가 수 초 멈춘다.** 배포는 끊기지 않지만 장애는 끊긴다. prod 는 2개다.
- **prod 의 reservation 은 복제본 수를 배포 파일(2개)과 HPA 가 함께 정한다.** Argo CD 를 쓸 때는 이 값의 차이를 무시하도록 설정해야 둘이 다투지 않는다.
- **무중단 배포 시험의 부하는 Pod 하나가 차례로 보내는 요청이다.** 동시 접속이 많은 상황은 아니다.
