# 테스트 시나리오 (모든 단계 공통)

과제는 ①에서 정한 테스트 시나리오를 ② ③ ④에서도 그대로 쓰라고 한다. 그래서 시나리오를 스크립트 하나(`scripts/smoke.sh`)로 만들고, 단계마다 **대상 주소만 바꿔** 실행한다.

- 필요한 것: bash, curl. (서비스 격리와 DB 경계 확인에는 docker 또는 kubectl 도 쓴다.)
- 계정: README 의 테스트 계정(보호자 `owner001`, 간호사 `admin1`, 원장 `vet1`). 전부 모의 데이터다.
- 만든 예약은 스크립트가 취소하므로 여러 번 돌려도 된다.
- 끝나면 `결과: 통과 N, 실패 M` 을 출력하고 실패 수를 종료 코드로 돌려준다.

## 확인 항목과 기대 결과

| # | 종류 | 무엇을 하나 | 요청 | 기대 결과 |
|---|---|---|---|---|
| 0 | 준비 | 전부 응답할 때까지 기다린다 | `GET /health`, `GET /api/notices`, 로그인, `GET /api/reservations/me` | 모두 200 |
| 1 | 조회 | 보호자 로그인, 내 정보 | `POST /api/auth/login`, `GET /api/auth/me` | 200, 역할 `OWNER`, 아이디가 같다 |
| 2-1 | 조회 | 반려동물 목록 | `GET /api/pets` | 200, 1마리 이상 |
| 2-2 | **등록** | 빈 시간을 찾아 예약 신청 | `GET /api/slots?date=…&type=GENERAL`, `POST /api/reservations` | 201, 예약 번호를 받는다 |
| 2-3 | 조회 | 내 예약 | `GET /api/reservations/me` | 방금 신청한 예약이 `REQUESTED` |
| 2-4 | **수정** | 예약 취소 | `DELETE /api/reservations/{번호}` | 204, 다시 조회하면 `CANCELLED` |
| 3-1 | 조회 | 간호사 로그인, 예약 현황 | `GET /api/admin/reservations?date=…` | 200, 보호자가 신청한 예약이 `REQUESTED` |
| 3-2 | **수정** | 승인 | `POST /api/admin/reservations/{번호}/approve` | 200, `CONFIRMED` |
| 4 | 조회 | 원장 로그인, 내 일정 | `GET /api/director/schedule?date=…` | 200, 진료 시간 1칸 이상 |
| 버전 | 조회 | 서비스별 버전과 응답한 서버 | `GET /api/status/{auth,clinic,reservation}`, `GET /status` | 200, 본문의 버전과 `X-App-Version` 헤더가 같다 |
| DB | 권한 | 서비스 계정이 남의 데이터를 못 건드린다 | DB 안에서 `vet-sql <계정> "<SQL>"` 10가지 | 자기 것은 허용, 남의 것은 `denied` |
| 5 | 격리 | 서비스 하나를 멈춘다 (auth, clinic, reservation 차례로) | 멈춘 서비스의 경로와 나머지 경로 | 멈춘 경로만 JSON 503, 나머지는 200, 다시 켜면 복구 |

2번과 3번이 과제가 말하는 "등록 · 조회 · 수정"이다. 예약을 **등록**하고, 다른 화면(내 예약, 간호사 현황)에서 **조회**되는지 보고, 승인과 취소로 **수정**한 뒤 바뀐 상태를 다시 조회한다. 로그인은 auth, 반려동물과 빈 시간은 clinic, 예약은 reservation 이 맡으므로 이 흐름 하나가 서비스 3개와 DB, 세션 저장소를 모두 지난다.

## 단계별 실행 방법

| 단계 | 대상 | 명령 | 항목 수 |
|---|---|---|---|
| ① 앱 | 서비스 3개에 직접 (웹 서버 없음) | `scripts/run-app.sh test` (안에서 `scripts/smoke.sh --auth-url … --clinic-url … --reservation-url … --db-exec …` 를 부른다) | 32 |
| ② 컨테이너 | compose 의 web | `scripts/smoke.sh` | 54 |
| ③ 쿠버네티스 | kubeadm 클러스터의 노출 주소 | `scripts/smoke.sh --base-url http://<주소> --isolation k8s --namespace <이름>` | 54 |
| ④ EKS | ALB 주소 | 위와 같다. 주소만 바뀐다 | 54 (DB 가 RDS 면 `--no-db-check` 로 44) |

단계마다 항목 수가 다른 이유는 그 단계에 없는 것을 건너뛰기 때문이다.

- ①에는 웹 서버가 없다. 화면(`/`, `/status`)과 "멈춘 서비스는 JSON 503" 확인은 웹 서버가 하는 일이라 뺀다. 대신 `/health` 를 서비스마다 확인한다.
- DB 경계 확인은 DB 컨테이너 안에서 명령을 실행한다. DB 가 RDS 면 들어갈 컨테이너가 없어 건너뛴다.

1 ~ 4번과 버전 확인(등록 · 조회 · 수정이 들어 있는 부분)은 어느 단계에서나 똑같이 실행된다.

옵션 전체는 `scripts/smoke.sh --help` 로 본다.

## 데이터가 남는지 확인하기 (DB Pod 교체)

③과 ④는 DB Pod 를 교체해도 데이터가 남는지를 본다. 시나리오는 만든 예약을 취소하므로, 이 확인에는 지우지 않는 예약을 따로 만든다.

```bash
# 1) 표식 예약을 만든다. 번호를 출력한다
scripts/smoke.sh --base-url http://<주소> --mark

# 2) DB Pod 를 지운다 (새 Pod 가 뜬다)
kubectl -n <이름> delete pod -l app=mysql

# 3) 그 예약이 남아 있는지 확인한다. --cleanup 을 붙이면 확인한 뒤 취소한다
scripts/smoke.sh --base-url http://<주소> --verify <번호> --cleanup
```

기대 결과는 `[통과] 표식 예약이 남아 있다 — 번호 …, 상태 REQUESTED` 다. 표식 예약은 시나리오와 겹치지 않게 다른 보호자(`owner002`)로 만든다.

### 미리 확인한 것 (스크립트가 맞게 도는지)

2026년 11월 16일에 스크립트를 만들면서 돌려 본 결과다. 스크립트가 맞게 동작하는지를 본 것이고, ③ ④의 증거는 아니다.

| 어디서 | 대상 | 명령 | 결과 |
|---|---|---|---|
| WSL 2 Ubuntu 26.04, Docker Engine 29.9 | 같은 WSL 에서 `docker compose up -d` 로 띄운 6개 컨테이너 (Apache) | `scripts/smoke.sh` | 통과 54, 실패 0 |
| Windows 의 Git Bash | Docker Desktop 의 로컬 클러스터(노드 1개), dev | `scripts/smoke.sh --base-url http://localhost --isolation k8s --namespace dev` | 통과 54, 실패 0 |
| Windows 의 Git Bash | 같은 클러스터의 서비스 3개를 `kubectl port-forward` 로 직접 | `scripts/smoke.sh --auth-url … --clinic-url … --reservation-url … --db-exec "kubectl -n dev exec deploy/mysql --"` | 통과 32, 실패 0 |
| Windows 의 Git Bash | 같은 클러스터 | `--mark`, `--verify <번호>`, 없는 번호로 `--verify` | 만들기와 확인 통과, 없는 번호는 실패로 나오고 종료 코드 1 |

WSL 에서의 이미지 빌드(`docker compose build`, 6개)는 처음 실행에 8분 57초가 걸렸다.

같은 날 배포 파일을 과제에 맞게 고친 뒤(네임스페이스 `vet`, 복제본 2개, MySQL 볼륨) 다시 돌렸다.

| 어디서 | 대상 | 명령 | 결과 |
|---|---|---|---|
| Windows 의 Git Bash | 로컬 클러스터, `overlays/local` | `scripts/smoke.sh --base-url http://localhost --isolation k8s -n vet` | 통과 54, 실패 0 |
| Windows 의 Git Bash | 같은 클러스터 | `scripts/test-k8s-ops.sh --base-url http://localhost -n vet --compare` | 통과 15, 실패 0. 5번 중 1번은 배포 중 요청 38,634건 가운데 1건이 실패해 14개 통과였다 |
| Windows 의 Git Bash | 같은 클러스터 | `--mark` → MySQL Pod 삭제 → `--verify` | 새 Pod 에서 표식 예약이 남아 있다. 끊긴 시간 8.7초, 10.7초 |

운영 확인(`test-k8s-ops.sh`)의 항목과 숫자는 `결정기록.md` 5-8 에 있다.

그 뒤 WSL 의 홈 폴더에 저장소를 새로 받아 ①과 ②를 처음부터 돌렸다. 순서와 출력은 [실행-안내-WSL.md](실행-안내-WSL.md) 에 있다.

| 어디서 | 대상 | 명령 | 결과 |

| WSL 2 Ubuntu 26.04, JDK 21 | 소스에서 빌드한 jar 3개 (MySQL, Redis 는 컨테이너) | `scripts/run-app.sh build`, `up`, `test` | 빌드 1분 50초, 통과 32, 실패 0 |

## Windows 에서

`scripts\smoke.ps1` 은 같은 항목을 PowerShell 로 확인한다. Windows 에서 개발할 때 쓰던 것이고, 과제의 증거는 `smoke.sh` 로 남긴다.
