# 결정 기록

보듬 동물병원 예약 시스템을 쿠버네티스용 서비스 3개로 나누면서 내린 결정을 단계별로 적는다.
항목마다 **확인한 사실 → 근거 → 그래서 이렇게 설정했다** 순서다. 실행해 보지 않은 것은 "실행하지 않음"이라고 적는다.

## 0단계: 전제

### 0-1. 웹 서버는 Apache 와 nginx 두 벌로 만들고, 기본은 Apache 다

- **확인한 사실**: 원본 3-Tier 는 nginx(`deploy/nginx.conf`)가 정적 파일을 주고 `/api` 를 WAS 로 넘겼다. 프로젝트 요구는 Apache httpd 다.
- **근거**: 먼저 Apache 로 올리고 나중에 nginx 로 바꿀 계획이다(11월 12일 결정). 바꿀 때 Deployment 나 검증 스크립트를 고쳐야 하면 전환 자체가 위험해진다.
- **그래서**: web 이미지를 두 벌 만들되 겉으로 보이는 규격을 같게 한다. 포트, `/health`, `X-Web-Node`, 서비스 주소를 받는 환경 변수, 죽은 서비스에 대한 503 JSON 이 같아야 한다. 그러면 같은 `smoke.ps1` 로 둘 다 검증하고, 전환은 이미지 한 줄만 바꾸면 된다. `deploy/nginx.conf` 는 읽기 전용 참고 자료로 둔다.
- **주의**: 경로 순서는 Apache 에서 중요하다. nginx 는 가장 긴 접두사가 이기지만 Apache 의 `ProxyPass` 는 먼저 적힌 줄이 이긴다. `/api/admin/notices` 를 `/api/admin` 보다 먼저 적어야 한다. 세부 설정은 2단계에서 채운다.

### 0-2. 원본 폴더는 고치지 않는다

- **확인한 사실**: `was/` 는 AWS 3-Tier 에 배포했던 그대로이고 부하 테스트 결과가 이 코드 기준이다.
- **그래서**: 새 코드는 전부 `msa/` 에 둔다. `was/` 와 `msa/` 를 나란히 비교하면 무엇이 바뀌었는지 보인다.

## 1단계: 백엔드 분리

### 1-1. 서비스 경계는 원래 패키지 경계를 따른다

- **확인한 사실**: 패키지 사이의 import 를 조사하니 `staff → reservation` 하나뿐이다. `clinic`, `auth` 는 `support` 와 `Auth`, `SessionUser` 만 쓴다.
- **근거**: 서로 부르는 코드를 다른 서비스로 나누면 서비스 간 HTTP 호출이 새로 생긴다. 그러면 한 서비스가 죽을 때 다른 서비스도 같이 실패한다.
- **그래서**: `reservation` 과 `staff` 를 한 서비스에 넣었다. 결과적으로 세 서비스는 서로 호출하지 않는다.

| 모듈 | 맡는 경로 | 들어간 클래스 |
|---|---|---|
| common | 없음 (라이브러리) | `support` 5개, `Auth`, `SessionUser` |
| auth-service | `/api/auth` | `AuthController` |
| clinic-service | `/api/pets`, `/api/notices`, `/api/slots`, `/api/admin/notices` | `clinic` 4개 |
| reservation-service | `/api/reservations`, 공지를 뺀 `/api/admin`, `/api/director` | `reservation` 4개, `staff` 2개 |

### 1-2. 원본 소스는 한 글자도 바꾸지 않고 옮겼다

- **확인한 사실**: `was/` 의 Java 파일 19개 중 시작 클래스(`VetApiApplication`)를 뺀 18개를 그대로 복사했고, `diff` 로 18개 모두 원본과 같음을 확인했다.
- **근거**: 평가 대상은 인프라다. 앱 동작이 바뀌면 기존 화면과 Locust 시나리오를 다시 검증해야 한다.
- **그래서**: 새로 쓴 것은 시작 클래스 3개, `ServiceBootstrap`, 설정 파일, 빌드 파일, 테스트뿐이다. 패키지 이름도 `kr.bodeum.vet.*` 그대로다.

### 1-3. 세 서비스가 같은 로그인 세션을 읽는다

- **확인한 사실**: 세션은 Spring Session 이 Redis 에 저장하고, 그 안의 `SessionUser` 는 자바 직렬화로 들어간다. 읽는 쪽에 같은 이름의 클래스(`kr.bodeum.vet.auth.SessionUser`)가 없으면 복원에 실패한다. 쿠키 이름은 `SESSION` 이다.
- **근거**: 로그인은 auth 만 처리하지만 반려동물·예약 API 도 로그인한 사용자를 알아야 한다. 서비스끼리 물어보게 하면 auth 가 죽을 때 전부 멈춘다.
- **그래서**: `SessionUser` 를 common 에 원래 패키지 이름 그대로 두었다. 쿠키 이름과 만료 시간은 `vet-common.yml` 한 파일에만 적어 서비스마다 달라질 수 없게 했다.
- **검증**: auth 에서 로그인한 쿠키로 clinic `/api/pets` 와 reservation `/api/reservations/me` 가 200 이었다. auth 에서 로그아웃하니 같은 쿠키로 clinic 이 401 을 돌려줬다.

### 1-4. 공통 설정은 한 파일을 불러와 쓴다

- **확인한 사실**: 스프링 부트는 클래스패스에 `application.yml` 이 여러 개 있어도 합치지 않고 하나만 읽는다.
- **그래서**: 공통 설정을 common 의 `vet-common.yml` 에 두고, 각 서비스의 `application.yml` 이 `spring.config.import` 로 불러온다. 서비스의 `application.yml` 에는 서비스 이름만 남는다.

### 1-5. 슬롯 자동 생성은 clinic-service 에만 둔다

- **확인한 사실**: `SlotGenerator` 는 시작할 때와 매일 00:05 에 오늘부터 14일의 슬롯을 채운다. `INSERT IGNORE` 와 유일 키 덕분에 여러 인스턴스가 동시에 돌려도 중복되지 않는다.
- **그래서**: `@EnableScheduling` 과 `SlotGenerator` 를 clinic-service 에만 넣었다.
- **검증**: 세 서비스를 띄운 뒤 로그를 보니 clinic 에만 "슬롯 576개 추가"가 있고 auth, reservation 에는 없다.
- **한계**: 시작할 때 DB 에 연결하지 못하면 경고만 남기고 다음 날 00:05 까지 다시 시도하지 않는다. 원본 동작 그대로다. 쿠버네티스에서는 서비스가 MySQL 보다 먼저 뜰 수 있으므로 4단계 전에 처리 방법을 정해야 한다.

### 1-6. 시간대는 코드에서 Asia/Seoul 로 고정한다

- **확인한 사실**: 컨테이너의 기본 시간대는 UTC 다. 코드는 `LocalDate.now()` 와 `LocalDateTime.now()` 로 "오늘"과 "지금"을 정한다. DB 의 DATETIME 은 병원 현지 시각이다.
- **근거**: 서비스마다 시간대가 다르면 예약 가능 시간과 "오늘"이 서비스에 따라 달라진다.
- **그래서**: 원본 `main` 에 있던 시간대 설정을 common 의 `ServiceBootstrap` 으로 옮겨 세 서비스가 같은 코드로 시작한다.
- **검증**: 시스템 날짜가 11월 11일(UTC)인 환경에서 새로 만든 슬롯의 첫 날짜가 11월 12일(한국 날짜)이었다.

### 1-7. DB 연결 수는 환경 변수로 정한다

- **확인한 사실**: MySQL 8.4 컨테이너의 `max_connections` 기본값은 151 이다(직접 조회). 원본은 인스턴스 하나가 연결 10개를 열어 둔다.
- **근거**: 전체 연결 수는 `서비스 3개 x 복제본 수 x 풀 크기` 다. prod(복제본 2)는 평소 60, 롤링 업데이트로 서비스마다 Pod 가 하나씩 더 뜨는 동안 90 이다. 복제본을 늘리면 151 을 넘는다.
- **그래서**: `DB_POOL_MAX`(기본 10)로 풀 크기를 받는다. 최소 유휴 연결 수도 같은 값을 쓴다.
- **검증**: `DB_POOL_MAX=3` 으로 세 서비스를 띄우고 요청을 보낸 뒤 MySQL 에서 앱 계정의 연결을 세니 9개였다.

### 1-8. Redis TLS 는 환경 변수로 끈다

- **확인한 사실**: 원본은 ElastiCache 용으로 TLS 를 켜 두었다. 클러스터 안에 띄울 Redis 는 TLS 없이 쓴다.
- **그래서**: `REDIS_TLS`(기본 true)로 받는다. 기본값을 true 로 둔 이유는 값을 빠뜨렸을 때 암호화 없이 조용히 붙는 것보다 연결 실패로 드러나는 편이 안전해서다.
- **검증**: `REDIS_TLS=false` 에서는 로그인이 200 이었다. 값을 주지 않으면 TLS 없는 Redis 에 2초 뒤 연결 실패가 났다.

### 1-9. /health 는 DB 와 Redis 를 확인하지 않는다

- **확인한 사실**: 원본 `/health` 는 일부러 "ok" 만 돌려준다.
- **근거**: DB 가 죽었을 때 `/health` 까지 실패하면 멀쩡한 Pod 가 전부 비정상으로 표시되어 재시작되고, DB 가 돌아와도 복구가 늦어진다. 또 서비스가 MySQL 보다 먼저 떠도 준비 상태가 될 수 있다.
- **그래서**: 원본 그대로 세 서비스에 두었다.
- **검증**: DB 와 Redis 없이 띄운 테스트에서 `/health` 는 200 이고, DB 가 필요한 `/api/notices` 만 503 `{ code: DB_UNAVAILABLE }` 이었다.

### 1-10. 종료 처리와 X-Served-By 는 원본 그대로다

- **검증**: 세 서비스에 SIGTERM 을 보내니 로그에 "Commencing graceful shutdown"과 "Graceful shutdown complete"가 남았다. 응답에는 세 서비스 모두 `X-Served-By`(호스트 이름)가 붙는다.
- **남은 일**: 종료를 기다리는 시간과 롤링 업데이트 설정은 4단계에서 정한다.

### 1-11. 서비스가 맡은 경로를 테스트로 고정했다

- **근거**: 웹 서버의 경로 분기표와 서비스가 실제로 가진 경로가 어긋나면 404 가 난다. 사람이 눈으로 맞추면 놓친다.
- **그래서**: 서비스마다 등록된 `/api` 경로 목록을 테스트가 확인한다. 컨트롤러를 다른 서비스로 옮기면 빌드가 실패한다.

### 1-12. Windows 에서 다시 검증했다 (11월 12일)

- **확인한 사실**: 위 검증은 Linux 에서 한 것이다. 발표와 시연은 Windows PC 에서 한다.
- **그래서**: 같은 커밋을 Windows 11(Corretto 21.0.12, Docker 29.8.2)에서 다시 돌렸다. `gradlew.bat clean build` 가 41초에 성공했고 테스트 13개(auth 4, clinic 5, reservation 4)가 모두 통과했다. 실행 가능한 jar 는 `vet-auth-1.0.0.jar`, `vet-clinic-1.0.0.jar`, `vet-reservation-1.0.0.jar` 세 개다.
- **검증**: 임시 MySQL 8.4 와 Redis 7 컨테이너에 jar 세 개를 붙여 아래를 확인했다. 전부 통과했다.

| 확인한 것 | 결과 |
|---|---|
| 시드 적재 | 사용자 305명 |
| 세 서비스 `/health` | 200, `X-Served-By` 있음 |
| 쿠키 없이 clinic `/api/pets` | 401 `UNAUTHORIZED` |
| auth 로그인(owner001) | 200, 쿠키 이름 `SESSION` |
| 같은 쿠키로 clinic `/api/pets` | 200, 2마리 |
| 같은 쿠키로 reservation `/api/reservations/me` | 200, 3건 |
| 보호자 쿠키로 `/api/admin/reservations` | 403 |
| auth 에 `/api/pets` 요청 | 404 `NOT_FOUND` |
| `DB_POOL_MAX=3` 일 때 MySQL 연결 수 | 9 (서비스 3 x 3) |
| `SlotGenerator` 로그 | clinic 에만 1줄 ("슬롯 576개 추가") |
| auth 로그아웃 뒤 같은 쿠키로 clinic | 401 |

- **확인하지 않은 것**: Redis 가 죽었을 때의 응답과 `REDIS_TLS` 를 빠뜨렸을 때의 동작은 Windows 에서 다시 돌리지 않았다. Linux 결과(아래 한계)만 있다.

## 2단계: 컨테이너와 로컬 실행

검증은 11월 12일 Windows 11, Docker 29.8.2 에서 했다. 사용한 버전: Temurin JRE 21.0.13, httpd 2.4.71, nginx 1.30.6, MySQL 8.4.13, Redis 7.

### 2-1. 서비스 이미지는 두 단계로 만들고, 덜 바뀌는 것부터 쌓는다

- **확인한 사실**: 실행 jar 37MB 의 대부분은 라이브러리 71개다. 우리 코드는 그중 아주 작은 부분이다.
- **근거**: jar 하나를 통째로 복사하면 코드 한 줄만 고쳐도 37MB 층이 새로 올라간다. 레지스트리에 밀어 넣는 시간과 노드가 받는 시간이 그만큼 늘어난다.
- **그래서**: 빌드 단계는 Gradle 래퍼와 빌드 스크립트만 먼저 복사해 의존성을 받고, 그다음 소스를 복사한다. 실행 단계는 스프링 부트의 층 분리(`extract --layers`)로 라이브러리, 로더, 애플리케이션을 따로 복사한다. 실행 이미지에는 JDK 가 아니라 JRE 만 넣는다.
- **검증**: 소스를 바꾸지 않고 다시 빌드하니 모든 단계가 `CACHED` 였다.

### 2-2. 모든 컨테이너는 root 가 아닌 사용자로 뜬다

- **근거**: 컨테이너가 뚫려도 호스트 권한으로 이어지지 않게 한다. 쿠버네티스의 `runAsNonRoot` 검사는 사용자를 숫자로 적어야 통과한다.
- **그래서**: 서비스는 10001, Apache 는 82(www-data), nginx 는 101 로 실행한다. 1024 아래 포트를 열 수 없으므로 웹 서버도 8080 에서 듣는다.
- **검증**: `docker exec vet-t-auth id` → `uid=10001(app) gid=10001(app)`. 이미지 설정의 사용자는 Apache `82:82`, nginx `101:101`.
- **예외**: MySQL 과 Redis 는 공식 이미지의 방식 그대로다. 시작할 때만 root 이고 서버 프로세스는 전용 사용자로 내려간다.

### 2-3. JVM 힙은 컨테이너 메모리 한도의 절반이다

- **확인한 사실**: 한도 512MiB 에서 `-XX:MaxRAMPercentage=50` 을 주니 `MaxHeapSize = 268435456`(256MB)이고 GC 는 Serial 이 자동으로 골라졌다. 세 서비스의 실제 사용량은 유휴 178~185MiB, 요청 600건 뒤 183~188MiB 였다.
- **근거**: JVM 은 힙 말고도 메타스페이스, 코드 캐시, 스레드 스택을 쓴다. 힙을 한도 가까이 잡으면 힙이 차기 전에 컨테이너가 OOMKilled 로 죽는다. 그때는 자바 로그에 아무것도 남지 않는다.
- **그래서**: 힙 50% 로 두고 `-XX:+ExitOnOutOfMemoryError` 를 넣었다. 메모리가 모자라면 JVM 이 이유를 남기고 스스로 끝나고, 재시작은 쿠버네티스가 한다. 값은 `JAVA_TOOL_OPTIONS` 환경 변수라서 이미지를 다시 만들지 않고 바꿀 수 있다.
- **종료 처리**: `ENTRYPOINT` 를 exec 형식으로 써서 java 가 1번 프로세스다. `docker stop` 에 `Commencing graceful shutdown` → `Graceful shutdown complete` 가 남고 0.6초에 끝났다.

### 2-4. DB 이미지는 뜨는 날을 기준으로 시드를 새로 만든다

- **확인한 사실**: `db/seed.sql` 은 만든 날(10월 23일)부터 14일의 슬롯과 예약이 들어 있는 고정 파일이다. 11월에 그대로 넣으면 시드 예약과 이벤트 기간이 전부 과거가 된다. 또 clinic 의 `SlotGenerator` 는 시작할 때 DB 가 없으면 다음 날 00:05 까지 다시 시도하지 않는다(1-5).
- **근거**: 프로젝트의 주제가 "클러스터를 지워도 똑같이 복원"이다. 언제 다시 만들어도 같은 모습(오늘부터 14일, owner001 의 예약 3건, 다음 주 월요일부터 이벤트)이 나와야 한다.
- **그래서**: MySQL 8.4 이미지에 `db/schema.sql`, `db/gen-seed.mjs`, `web/clinic.config.json` 과 Node 실행 파일을 넣고, 초기화 스크립트(`msa/db/10-vet-init.sh`)가 그 자리에서 시드를 만들어 넣는다. `db/` 의 파일은 고치지 않았고 이미지가 그대로 복사해 쓴다. 이미지가 하나(`vet-db`) 늘었다.
- **검증**: 컨테이너 로그에 `vet: slots=576 reservations=167 users=305 notices=5 first_slot=2026-11-12 now=2026-11-12 11:17:21`. 빈 상태에서 준비까지 10초. owner001 의 예약은 11월 13일(확정), 19일(취소), 21일(신청)이었다.
- **슬롯 재시도 문제**: 시드가 14일 치 슬롯을 이미 넣으므로 clinic 이 DB 보다 먼저 떠도 예약할 시간이 있다. 2-12 에서 확인했다.

### 2-5. 앱 계정의 권한은 원본과 같게 좁혔다

- **확인한 사실**: 원본 `db/init.sh` 는 앱 계정에 SELECT·INSERT·UPDATE 와 `notices` 의 DELETE 만 준다. 공식 MySQL 이미지는 `MYSQL_USER` 에 그 DB 의 모든 권한을 준다.
- **그래서**: 초기화 스크립트가 권한을 걷어 낸 뒤 원본과 같은 권한만 다시 준다.
- **검증**: `SHOW GRANTS` 가 위 두 줄만 보여 준다. 앱 계정으로 `DELETE FROM pets` 와 `DROP TABLE notices` 는 `ERROR 1142 ... command denied` 였다.

### 2-6. DB 는 볼륨 없이 띄운다 (재시작하면 초기 상태)

- **근거**: 쿠버네티스에서 EBS CSI 드라이버를 쓰지 않기로 했고, 데이터는 전부 가짜다. 재시작하면 깨끗한 시연 상태로 돌아가는 편이 오히려 낫다.
- **그래서**: compose 에서는 `/var/lib/mysql` 을 tmpfs 로 둔다. 컨테이너가 멈추면 데이터가 사라져 쿠버네티스의 emptyDir 와 같은 동작이 된다.
- **검증**: `pets` 의 이름을 바꾸고 `docker restart` 하니 원래 이름으로 돌아왔다.
- **한계**: 예약 데이터가 재시작마다 사라진다. Redis 의 세션은 남아 있으므로 로그인은 유지되지만 그 사이 만든 예약은 없어진다. 운영이라면 PVC 나 RDS 가 필요하다.

### 2-7. MySQL 설정: 연결 한도를 적어 두고 메모리를 줄였다

- **확인한 사실**: 기본 설정의 `max_connections` 는 151 이다. `performance_schema = OFF`, 버퍼 풀 128MB 로 띄우면 메모리는 189MiB 였다(데이터를 디스크에 둘 때). tmpfs 에 두면 데이터가 메모리로 잡혀 407MiB 다.
- **그래서**: `msa/db/vet.cnf` 에 `max_connections = 151` 을 적어 숫자를 드러냈다. compose 는 서비스 3개 x `DB_POOL_MAX` 5 = 15 개를 쓴다. Pod IP 는 역방향 이름이 없으므로 `skip-name-resolve` 도 넣었다.

### 2-8. Redis 는 비밀번호를 걸고 디스크에 남기지 않는다

- **근거**: 세션 저장소라서 같은 네트워크의 누구나 읽을 수 있으면 남의 로그인을 가져갈 수 있다. TLS 는 쓰지 않지만(`REDIS_TLS=false`) 비밀번호는 건다.
- **그래서**: `--requirepass` 를 환경 변수로 받고 `--save '' --appendonly no` 로 띄운다. Redis 가 다시 뜨면 모두 로그아웃된다.

### 2-9. /api 경로 분기

| 순서 | 경로 | 보내는 곳 |
|---|---|---|
| 1 | `/api/auth/` | auth |
| 2 | `/api/admin/notices` | clinic |
| 3 | `/api/pets`, `/api/notices`, `/api/slots` | clinic |
| 4 | `/api/reservations` | reservation |
| 5 | `/api/admin/` | reservation |
| 6 | `/api/director/` | reservation |
| 7 | 그 밖의 `/api/` | 웹 서버가 404 JSON |

- **확인한 사실**: Apache 의 `ProxyPass` 는 먼저 적힌 줄이 이기고, nginx 는 가장 긴 접두사가 이긴다.
- **그래서**: 두 설정 파일 모두 위 순서로 적었다. Apache 에서 2번이 5번보다 뒤로 가면 공지 등록이 reservation 으로 간다.
- **검증**: `POST /api/admin/notices` 의 `X-Served-By` 가 `/api/notices` 와 같은 컨테이너(clinic)였고, `GET /api/admin/reservations` 는 다른 컨테이너(reservation)였다. 1단계의 경로 테스트(1-11)가 서비스 쪽 목록을 고정하고 있다.

### 2-10. 죽은 서비스의 경로는 503 JSON 을 돌려준다

- **확인한 사실**: 화면(`api.ts`)은 오류 응답의 `code` 와 `message` 를 읽는다. HTML 오류 페이지가 오면 "서버에 일시적인 문제"라는 일반 문구로 떨어진다. Apache 2.4.71 은 서비스가 없을 때 상황에 따라 다른 코드를 낸다. 이름을 못 찾으면 500, 연결이 거절되면 503 이었다(로그 `AH00898`, `AH00957`).
- **근거**: 화면과 스크립트가 "이 기능만 잠시 안 됨"을 한 가지 응답으로 알아볼 수 있어야 한다.
- **그래서**: 웹 서버가 직접 만드는 500·502·503·504 만 `{"code":"SERVICE_UNAVAILABLE", ...}` 503 으로 바꾼다. nginx 는 `error_page 502 503 504 = @unavailable` 로 한다. Apache 의 `ErrorDocument` 는 본문만 바꾸고 상태 코드는 그대로 두므로, 상태 줄까지 적어 둔 `.asis` 파일(mod_asis)을 오류 문서로 쓴다.
- **서비스가 스스로 낸 오류는 건드리지 않는다**: 401, 409, 그리고 DB 가 없을 때의 503 `DB_UNAVAILABLE` 은 그대로 통과한다(Apache `ProxyErrorOverride`, nginx `proxy_intercept_errors` 모두 기본값 꺼짐).
- **검증**: clinic 을 멈추고 `/api/notices` 를 부르니 `503`, `Content-Type: application/json`, `{"code":"SERVICE_UNAVAILABLE",...}` 였고 같은 때 `/api/auth/me` 는 정상(401)이었다. 두 웹 서버 모두 smoke 5번에서 확인했다.
- **처음에는 실패했다**: Apache 가 500 HTML 을 냈다. 이름 조회 실패가 502 일 것이라 짐작하고 500 을 빼놓았기 때문이다. 로그를 보고 고쳤다.

### 2-11. 서비스의 IP 가 바뀌어도 웹 서버를 다시 띄우지 않는다

- **확인한 사실**: Apache 는 백엔드 연결을 재사용하는 동안 처음 찾은 IP 를 계속 쓴다. nginx 는 `proxy_pass` 에 주소를 직접 적으면 시작할 때 한 번만 이름을 찾고, 못 찾으면 아예 뜨지 않는다.
- **그래서**: Apache 는 `disablereuse=On`(요청마다 이름을 다시 찾음)과 `retry=0`(실패 뒤 60초 쉬는 기본 동작을 끔)을 준다. nginx 는 `proxy_pass` 에 변수를 쓰고 `resolver ... valid=5s` 를 둔다. DNS 서버 주소는 도커와 쿠버네티스가 다르므로 nginx 이미지의 진입 스크립트가 `/etc/resolv.conf` 에서 읽어 넣게 했다.
- **검증**: clinic 컨테이너를 지우고, 그 IP 를 다른 컨테이너가 차지하게 한 뒤 clinic 을 다시 만들었다. 웹 서버는 다시 띄우지 않았다.

| 웹 서버 | clinic IP | 새 컨테이너가 응답하기까지 | 웹 서버 재시작 |
|---|---|---|---|
| nginx | 172.22.0.4 → 172.22.0.8 | 2초 | 없음 |
| Apache | 172.22.0.8 → 172.22.0.5 | 3초 | 없음 |

- **쿠버네티스에서는**: Service 의 ClusterIP 는 Pod 가 바뀌어도 그대로다. 그래서 이 설정은 Service 자체가 다시 만들어지는 경우(클러스터 재구축)를 위한 안전장치다.
- **한계**: Apache 는 요청마다 백엔드 연결을 새로 맺는다. 같은 클러스터 안이라 비용이 작다고 보았고, 측정하지는 않았다. 또 compose 에서 멈춘 서비스의 경로는 이름 조회가 실패할 때까지 몇 초 걸려 응답한다(Apache). 쿠버네티스에서는 연결이 바로 거절되므로 해당하지 않을 것으로 보지만 **실행하지 않음**.

### 2-12. 뜨는 순서를 정하지 않는다

- **근거**: 클러스터를 다시 만들 때 Pod 가 뜨는 순서는 보장되지 않는다. 순서에 기대는 구성은 재구축 때 한 번씩 실패한다.
- **그래서**: compose 에 `depends_on` 을 쓰지 않았다. `/health` 는 원본대로 DB 를 보지 않는다(1-9).
- **검증**: 전부 지운 뒤 일부러 거꾸로 띄웠다.

| 단계 | 결과 |
|---|---|
| web 만 띄움 (서비스 없음) | `/health` 200, 홈 200, `/api/notices` 는 503 `SERVICE_UNAVAILABLE` (Apache, nginx 모두) |
| 서비스 3개를 띄움 (DB·Redis 없음) | 셋 다 healthy. `/api/notices` 와 로그인은 서비스가 낸 503 `DB_UNAVAILABLE`, 쿠키 없는 `/api/pets` 는 401 |
| MySQL 과 Redis 를 띄움 | 서비스를 다시 띄우지 않고(재시작 0회) smoke 1~4번 18개 통과 |

- clinic 로그에는 `슬롯 채우기 실패 (DB 초기화 전일 수 있음)` 가 남았지만, 시드가 14일 치를 넣으므로 예약 가능 시간은 정상으로 나왔다.

### 2-13. 웹 서버 두 벌은 겉으로 보이는 동작이 같다

- **그래서**: 같은 포트(8080), `/health`, `X-Web-Node`, `X-Web-Version`, 환경 변수 `AUTH_UPSTREAM`·`CLINIC_UPSTREAM`·`RESERVATION_UPSTREAM`, 같은 503·404 JSON, 같은 정적 경로 규칙(`/about` → `about.html`, `/app/*` → `index.html`, `/app` → `/app/`)을 쓴다. compose 는 `.env` 의 `WEB_SERVER` 로 고르고, 이미지 태그는 `1.0.0-apache`, `1.0.0-nginx` 다.
- **검증**: 같은 `scripts/smoke.ps1` 이 Apache 에서 37개, nginx 에서 37개 모두 통과했다.
- **다른 점**: 404 페이지의 모양과 `Server` 헤더는 각 서버의 기본값이다.

## 3단계: 시연용 기능 (버전 표시, 상태 쪽지)

검증은 11월 12일 compose 환경에서 했다. 화면 캡처는 `docs-msa/img/` 에 있다.

### 3-1. 버전 값은 이미지를 빌드할 때 넣고, 이미지 태그와 같다

- **확인한 사실**: 배포가 끝났는지를 화면에서 알 방법이 없었다. `X-Web-Node` 와 `X-Served-By` 는 어느 Pod 가 답했는지만 알려 준다.
- **근거**: dev 는 main 을 따라가고 prod 는 태그에 고정한다는 것이 프로젝트의 주제다. 지금 떠 있는 것이 어느 버전인지 눈에 보여야 시연이 된다.
- **그래서**: Dockerfile 의 `ARG VERSION` 을 환경 변수로 굽는다. 서비스는 `APP_VERSION`, web 은 `WEB_VERSION` 이다. compose 는 `.env` 의 `VERSION` 하나로 이미지 태그와 이 값을 함께 정하므로 둘이 어긋나지 않는다. web 은 `1.0.0-apache` 처럼 웹 서버 이름까지 들어간다.
- **검증**: clinic 만 `VERSION=1.0.1` 로 다시 올렸다.

| 시점 | auth | clinic | reservation |
|---|---|---|---|
| 올리기 전 | 1.0.0 | 1.0.0 | 1.0.0 |
| clinic 만 1.0.1 로 올린 뒤 | 1.0.0 | 1.0.1 (컨테이너도 바뀜) | 1.0.0 |
| 되돌린 뒤 | 1.0.0 | 1.0.0 | 1.0.0 |

- **한계**: 태그와 값이 같다는 것은 빌드할 때 같은 값을 줬을 때만 참이다. GitHub Actions 에서 이미지를 만들 때도 태그와 `--build-arg VERSION` 에 같은 값을 줘야 한다. 이미지 밖에서 jar 를 직접 실행하면 `dev` 로 보인다.

### 3-2. 기존 API 는 그대로 두고 헤더와 새 경로만 더했다

- **그래서**: 서비스의 모든 응답에 `X-App-Version` 헤더가 붙고, 웹 서버의 모든 응답에 `X-Web-Version` 헤더가 붙는다. 서비스마다 `GET /api/status/<이름>` 이 하나씩 생겼다. 기존 경로의 요청과 응답 본문은 바뀌지 않았다.
- **옮긴 원본 18개는 여전히 그대로다**: 새로 쓴 것은 common 의 `AppVersion`, `AppVersionFilter`, `StatusController` 세 클래스와 서비스별 설정 한 줄(`vet.service`)이다.
- **검증**: 경로 목록을 고정한 테스트(1-11)에 새 경로를 하나씩 더했고, 상태 응답을 확인하는 테스트를 서비스마다 하나씩 더했다. `gradlew.bat build` 가 통과했다. smoke 의 기존 항목 37개도 그대로 통과한다.

### 3-3. 상태 응답은 서비스마다 경로가 다르다

- **근거**: 상태 화면이 한 곳에 물어서 넷을 모두 알아내면, 그 한 곳이 죽을 때 화면 전체가 "응답 없음"이 된다. 서비스 하나를 멈췄을 때 그 줄만 바뀌어야 한다.
- **그래서**: `/api/status/auth`, `/api/status/clinic`, `/api/status/reservation` 을 웹 서버가 각 서비스로만 보낸다. 응답은 `{ service, status, version, servedBy }` 다. web 자신은 `/health` 응답의 헤더(`X-Web-Version`, `X-Web-Node`)로 읽는다.
- **DB 를 확인하지 않는다**: `/health` 와 같은 이유다(1-9). 그래서 "정상"은 "프로세스가 떠서 요청에 답한다"는 뜻이다.
- **검증**: 서비스를 하나씩 멈추고 세 경로를 불렀다. Apache 와 nginx 모두 같았다.

| 멈춘 서비스 | auth | clinic | reservation |
|---|---|---|---|
| auth | 503 | 200 | 200 |
| clinic | 200 | 503 | 200 |
| reservation | 200 | 200 | 503 |

- **한계**: DB 나 Redis 가 죽어도 이 화면은 "정상"으로 보인다. 로그인 없이 볼 수 있고, 버전과 Pod 이름이 드러난다.

### 3-4. 상태 쪽지 화면은 기존 디자인 체계 안에서 만들었다

- **확인한 사실**: `DESIGN.md` 는 종이 세 가지, 검은 잉크, 빨간 도장, 직각 모서리, `steps(2, end)` 전환만 쓴다. 한 단계 물러나는 정보는 회색이 아니라 빗금과 옅은 잉크로 낮춘다.
- **그래서**: 새 정적 페이지 `/status` 를 만들었다(`web/site/pages/status.html`, `assets/css/board-status.css`, `assets/js/status.js`). 홈의 영수증 띠를 넓게 펴서 표로 쓰고, 읽는 법은 마닐라 꼬리표에 적었다. 응답 없는 줄은 빗금 바탕과 옅은 잉크, 상태 글자는 기존의 경고 딱지(빨간 테두리와 빨간 글자)다. 상태가 바뀐 줄만 0.18초에 두 번 끊어 움직인다. 새 색과 새 글꼴은 없다. 바닥글에 링크 한 줄을 더했다.
- **동작**: 네 곳에 따로 묻고 답이 오는 대로 그 줄만 고친다. 3초 안에 답이 없으면 "응답 없음"이다. 5초마다 다시 묻고, 보이지 않는 탭에서는 멈춘다.
- **검증**: clinic 을 멈추니 clinic 줄만 "응답 없음"이 되고 아래 줄이 "4곳 중 3곳 정상 · clinic 응답 없음"으로 바뀌었다. 다시 켜니 화면을 새로고침하지 않아도 "4곳 모두 정상"으로 돌아왔다. 375px 폭에서 가로로 넘치지 않는다.

- **검토**: 디자인 점검 도구(impeccable detect)는 권고 1건을 냈다. 줄표(—)가 8개라는 것인데, 문장이 아니라 표의 빈 칸 표시라서 그대로 두었다. 별도 검토자의 마감 리뷰는 거치지 않았다. `DESIGN.md` 는 고치지 않기로 해서 이 페이지는 거기에 기록되지 않았다.

### 3-5. 예약 화면 하단에 버전을 함께 보여 준다

- **그래서**: 기존의 "마지막 응답 · WEB … · WAS …" 옆에 버전을 붙이고 상태 쪽지 링크를 더했다. 간호사·원장 화면의 하단 상태 막대에도 같은 값이 나온다.
- **검증**: 보호자 화면 하단은 `마지막 응답 · WEB 2bf33abdd998 1.0.0-apache · WAS e00cd0db8218 1.0.0 · 상태 쪽지`, 간호사 화면은 `WEB 5d18c1b20a0e 1.0.0-apache · WAS e00cd0db8218 1.0.0` 이었다(`img/app-footer-version.jpg`).
- 서비스가 멈춰 웹 서버가 직접 답한 응답에는 서비스 쪽 헤더가 없다. 그때는 마지막으로 본 값을 그대로 둔다.

### 3-6. 모의 서버도 같은 응답을 낸다

- **그래서**: `web/server/mock-server.mjs` 가 `X-Web-Version`, `X-App-Version` 과 `/api/status/*` 를 돌려준다. `MOCK_DOWN=clinic` 을 주면 그 서비스가 멈춘 것처럼 503 을 낸다. 컨테이너 없이 `npm start` 만으로 "응답 없음" 화면을 볼 수 있다.
- **검증**: `MOCK_DOWN=clinic` 으로 띄우니 `/api/status/clinic`, `/api/notices`, `/api/pets` 가 503 `SERVICE_UNAVAILABLE` 이고 auth 와 reservation 의 상태는 200 이었다.

## 한계

- **DB 를 공유한다.** 세 서비스가 한 스키마를 직접 읽고 쓴다. reservation 은 `pets`, `slots`, `users` 를 조인한다. 그 덕에 서비스 간 호출이 없어 한 서비스가 죽어도 나머지가 동작하지만, 테이블 구조를 바꾸면 세 서비스를 함께 배포해야 한다.
- **Redis 가 죽으면 로그인한 사용자의 요청이 실패한다.** 쿠키가 없는 요청과 `/health` 는 정상이다. 로그인은 503 을 돌려주는데 오류 코드 이름이 `DB_UNAVAILABLE` 로 나온다. 쿠키를 가진 요청은 500 이었다. 원본 코드의 동작이며 고치지 않았다.
- **`SPRING_DATA_REDIS_HOST` 를 빠뜨려도 서비스는 뜬다.** 첫 Redis 사용에서야 실패한다. 배포 파일에서 빠뜨리지 않도록 한다.
- **슬롯 생성 재시도가 없다.** 1-5 에 적었다. 2단계에서 DB 가 뜰 때마다 14일 치 시드를 넣도록 해서 예약할 시간이 비는 일은 없앴다(2-4, 2-12). 코드는 고치지 않았다.
- **auth 가 멈춘 동안 화면을 새로고침하면 로그인 화면이 나온다.** `web/app/src/auth.tsx` 는 `/api/auth/me` 가 401 이 아닌 오류여도 로그아웃 상태로 본다. 세션은 살아 있어서 API 는 계속 되고(smoke 5-1), auth 가 돌아온 뒤 새로고침하면 다시 로그인된 상태다. 화면 동작을 바꾸지 않기로 해서 고치지 않았다.
- **DB 를 다시 띄우면 예약이 사라진다.** 2-6 에 적었다.
- **vet-db 이미지가 1.27GB 다.** 2-15 에 적었다.
- **자원 사용량은 부하 없이 잰 값이다.** 2-14 에 적었다.
- **상태 쪽지의 "정상"은 DB 까지 본 결과가 아니다.** 3-3 에 적었다.
- **S3 미리보기에서는 상태 쪽지가 뜻이 없다.** 서비스가 없어 모든 줄이 "응답 없음"으로 나온다. 바닥글 링크는 미리보기에도 들어간다.
