# 문제와 해결

작업하면서 실제로 부딪힌 문제를 적는다. 문제마다 같은 순서다.

- **증상**: 무엇이 어떻게 잘못됐나 (실제 출력)
- **원인을 찾은 과정**: 무엇을 보고 원인을 알았나
- **원인**
- **해결**: 무엇을 어떻게 고쳤나
- **확인**: 고친 뒤의 실제 결과
- **배운 점**

앞의 11개는 만드는 대상(앱, 이미지, DB)의 문제이고, 뒤의 5개는 Windows 에서 테스트 스크립트를 쓰다 만난 문제다.

## 1. 멈춘 서비스의 경로가 JSON 이 아니라 500 HTML 을 돌려줬다

- **단계**: ② 컨테이너 (Apache)
- **증상**: 서비스를 하나 멈추고 smoke 를 돌리니 3개가 실패했다.

```
-- auth 를 멈춘 상태
[실패] 5-1 멈춘 서비스 경로는 503 JSON — /api/auth/me → 500 <!DOCTYPE HTML PUBLIC "-//W3C//DTD HTML 4.01//EN" …
…
결과: 통과 34, 실패 3
```

- **원인을 찾은 과정**: 화면은 오류 응답의 `code` 와 `message` 를 읽으므로 JSON 이어야 한다. 그래서 Apache 가 내는 502·503·504 를 JSON 으로 바꾸도록 설정해 두었는데 500 이 나왔다. web 컨테이너의 로그를 봤다.

```
[proxy:error] (EAI 2)Name does not resolve: AH00898: DNS lookup failure for: reservation returned by /api/reservations/me
[proxy:error] (111)Connection refused: AH00957: http: attempt to connect to 172.22.0.6:8080 (reservation:8080) failed
```

- **원인**: Apache 2.4.71 은 상황에 따라 다른 코드를 낸다. 이름을 못 찾으면(컨테이너가 멈춰 이름이 사라짐) **500**, 주소는 있는데 연결이 거절되면 503 이다. 이름 조회 실패가 502 일 것이라 짐작하고 500 을 빼놓았다.
- **해결**: `msa/web/apache/httpd.conf` 의 `/api/` 구역에 `ErrorDocument 500` 을 더했다. 서비스가 스스로 돌려준 500 은 그대로 통과하고(`ProxyErrorOverride` 가 꺼져 있다), Apache 가 직접 만든 것만 바뀐다.
- **확인**

```
HTTP/1.1 503 Service Unavailable
Content-Type: application/json
{"code":"SERVICE_UNAVAILABLE","message":"지금 이 기능에 연결할 수 없습니다. 잠시 후 다시 시도해 주세요."}
```

smoke 가 Apache 와 nginx 양쪽에서 모두 통과했다.

- **배운 점**: 오류 코드는 짐작하지 말고 로그에서 확인한다. 같은 "서비스가 죽었다"도 원인(이름 없음, 연결 거절, 응답 없음)에 따라 코드가 다르다.

## 2. Apache 의 오류 문서로는 상태 코드를 바꿀 수 없었다

- **단계**: ② 컨테이너 (Apache)
- **증상**: 1번을 풀려면 500·502·504 를 전부 503 하나로 맞춰야 한다. nginx 는 `error_page 502 503 504 = @unavailable` 한 줄로 되는데, Apache 의 `ErrorDocument` 는 본문만 바꾸고 상태 코드는 원래 것을 그대로 둔다.
- **원인을 찾은 과정**: 오류 문서 안에서 다시 503 을 내게 하면 "오류 문서를 처리하다가 또 오류"가 된다. 상태 코드를 문서 쪽에서 정할 수 있는 방법을 찾았다.
- **원인**: 정적 파일을 오류 문서로 쓰면 상태 코드는 처음 난 오류의 것이 유지된다.
- **해결**: `mod_asis` 를 썼다. `.asis` 파일은 첫 줄에 적은 상태와 헤더를 그대로 보낸다. `msa/web/errors/unavailable.asis`:

```
Status: 503 Service Unavailable
Content-Type: application/json
Cache-Control: no-store

{"code":"SERVICE_UNAVAILABLE","message":"…"}
```

- **확인**: 1번의 확인과 같다. 원래 오류가 500 이든 503 이든 응답은 503 JSON 이다.
- **배운 점**: 두 웹 서버가 같은 응답을 내게 하려면 한쪽에만 있는 기능에 기대지 말고 각자의 방법을 찾아야 한다. CGI 로도 되지만 요청마다 프로세스를 띄워야 해서 고르지 않았다.

## 3. 초기 데이터의 예약과 진료 시간이 전부 과거였다

- **단계**: ② 컨테이너 (DB)
- **증상**: `db/seed.sql` 을 그대로 넣으면 데모 계정(owner001)의 예약 3건과 할인 이벤트 기간이 전부 지난 날짜로 들어간다.
- **원인을 찾은 과정**: 시드 파일의 머리와 슬롯 날짜를 확인했다.

```
-- 생성: 2026-10-23T02:52:41.643Z (db/gen-seed.mjs)
슬롯 날짜: 2026-10-23 ~ 2026-11-05
```

- **원인**: 시드는 "만든 날부터 14일"을 담은 고정 파일이다. 11월 12일에 넣으면 전부 과거다.
- **해결**: 파일을 넣지 않고, DB 가 빈 상태로 뜰 때 생성기(`db/gen-seed.mjs`)를 그 자리에서 돌린다. MySQL 이미지에 Node 실행 파일과 생성기를 넣었다(`msa/db/Dockerfile`, `vet-provision.sh`). `db/` 의 파일은 고치지 않았다.
- **확인**

```
[vet] slots=576 reservations=175 users=305 notices=5 first_slot=2026-11-13 now=2026-11-13 09:34:23
```

- **배운 점**: "지웠다 만들어도 같은 모습"이려면 날짜에 기대는 데이터는 만들 때 계산해야 한다. 대신 이미지가 하나(`vet-db`) 늘었다.

## 4. clinic 이 DB 보다 먼저 뜨면 예약할 시간이 비었다

- **단계**: ② 컨테이너
- **증상**: clinic 의 슬롯 생성기는 시작할 때와 매일 00:05 에만 돈다. 시작할 때 DB 가 없으면 경고만 남기고 다음 날까지 다시 시도하지 않는다.

```
WARN … SlotGenerator : 슬롯 채우기 실패 (DB 초기화 전일 수 있음): Failed to obtain JDBC Connection
```

- **원인**: 원본 코드의 동작이다. EC2 에서는 DB 가 항상 먼저 있었지만, 쿠버네티스에서는 뜨는 순서를 정할 수 없다.
- **해결**: 앱 코드를 고치지 않기로 했으므로 3번의 시드가 14일 치 슬롯을 넣게 했다. 생성기가 실패해도 예약할 시간이 있고, 다음 날 00:05 에 생성기가 하루 치를 잇는다.
- **확인**: 전부 지운 뒤 web → 서비스 → DB·Redis 순으로 거꾸로 띄웠다. 서비스를 다시 띄우지 않고(재시작 0회) smoke 가 통과했고 예약 가능 시간이 정상으로 나왔다.
- **배운 점**: 순서에 기대는 구성은 재구축 때 한 번씩 실패한다. compose 에서도 일부러 `depends_on` 을 쓰지 않고 이 상황을 시험했다.

## 5. 서비스 컨테이너를 다시 만들면 웹 서버가 옛 주소로 보냈다

- **단계**: ② 컨테이너 (Apache)
- **증상**: (설계하면서 예상한 문제) Apache 는 백엔드 연결을 재사용하는 동안 처음 찾은 IP 를 계속 쓴다. 서비스가 새 IP 로 다시 뜨면 요청이 실패한다. 또 한 번 실패한 백엔드는 기본 60초 동안 다시 시도하지 않는다.
- **해결**: 프록시 설정에 `disablereuse=On`(요청마다 이름을 다시 찾는다)과 `retry=0`(쉬는 시간을 없앤다)을 줬다.
- **확인**: clinic 컨테이너를 지우고, 그 IP 를 다른 컨테이너가 차지하게 한 뒤 다시 만들었다.

| 웹 서버 | clinic IP | 새 컨테이너가 응답하기까지 | 웹 서버 재시작 |
|---|---|---|---|
| nginx | 172.22.0.4 → 172.22.0.8 | 2초 | 없음 |
| Apache | 172.22.0.8 → 172.22.0.5 | 3초 | 없음 |

- **배운 점**: 대가가 있다. Apache 는 요청마다 백엔드 연결을 새로 맺는다. 쿠버네티스에서는 Service 의 주소가 고정이라 이 설정이 꼭 필요하지는 않지만, Service 자체가 다시 만들어지는 경우를 위해 남겼다.

## 6. 서비스가 없으면 nginx 가 아예 뜨지 않는다

- **단계**: ② 컨테이너 (nginx)
- **증상**: (설계하면서 예상한 문제) `proxy_pass http://auth:8080` 처럼 주소를 직접 적으면 nginx 는 시작할 때 이름을 찾는다. 서비스가 아직 없으면 nginx 가 시작부터 실패한다. 웹 서버가 서비스보다 먼저 뜰 수 있어야 한다.
- **해결**: 주소를 변수에 담아 `proxy_pass $auth_upstream` 으로 쓰고 `resolver` 를 지정했다. 이러면 요청할 때 이름을 찾는다. DNS 서버 주소는 Docker 와 쿠버네티스가 달라서, nginx 이미지의 진입 스크립트가 `/etc/resolv.conf` 에서 읽어 넣게 했다.
- **확인**: 서비스가 하나도 없는 상태에서 nginx 만 띄웠다. `/health` 는 200, `/api/notices` 는 503 JSON 이었다.
- **배운 점**: 변수 방식은 검색 도메인을 쓰지 않는다. 쿠버네티스에서는 `auth.dev.svc.cluster.local` 같은 전체 이름을 줘야 한다.

## 7. 상태 쪽지에서 멈춘 서비스의 줄이 4초씩 늦게 바뀌었다

- **단계**: ② 컨테이너 (상태 쪽지)
- **증상**: clinic 을 멈추고 상태 응답을 재 보니 멈춘 서비스만 응답이 늦었다.

```
auth         200 0.007s
clinic       503 3.849s
reservation  200 0.006s
```

- **원인**: Apache 가 이름 조회에 실패할 때까지 기다린다. 화면이 넷을 한꺼번에 기다리면 정상인 줄까지 4초씩 늦게 갱신된다.
- **해결**: 화면(`status.js`)이 네 곳에 따로 묻고 답이 오는 대로 그 줄만 고친다. 3초 안에 답이 없으면 그 줄을 "응답 없음"으로 적는다.
- **확인**: clinic 을 멈추니 clinic 줄만 "응답 없음"이 되고 나머지 줄은 바로 갱신됐다. 다시 켜니 새로고침 없이 "정상"으로 돌아왔다.
- **배운 점**: 느린 실패는 빠른 성공을 막으면 안 된다. 요청을 묶지 않고 줄마다 나눈 것이 "그 줄만 바뀐다"를 만든다.

## 8. Windows 에서 받은 파일이 CRLF 라 컨테이너에서 실행되지 않는다

- **단계**: ② 컨테이너
- **증상**: (이미지를 만들기 전에 확인해 막은 문제) Windows 에서 저장소를 받으면 Git 이 줄 끝을 CRLF 로 바꾼다.

```
msa/gradlew: POSIX shell script … with CRLF line terminators
```

이 파일을 리눅스 컨테이너에서 실행하면 첫 줄의 `\r` 때문에 "그런 파일이 없다"로 실패한다. 설정 파일은 값 끝에 `\r` 이 붙는다.

- **해결**: 두 군데서 막았다. Dockerfile 이 복사한 직후 `sed -i 's/\r$//'` 로 LF 로 바꾼다. `.gitattributes` 에 `msa/` 아래의 스크립트와 설정 파일을 LF 로 고정했다.
- **확인**: Windows 에서 받은 그대로 이미지 6개가 빌드되고 실행됐다.
- **배운 점**: 개발 PC 와 실행 환경의 운영체제가 다르면 줄 끝부터 의심한다.

## 9. 호스트의 8080 포트를 쓸 수 없었다

- **단계**: ② 컨테이너
- **증상**: web 을 8080 으로 열려는데 이미 쓰이고 있었다.

```
TCP    0.0.0.0:8080    LISTENING    5224
httpd.exe    5224 Services
```

- **원인**: PC 에 Apache 가 Windows 서비스로 깔려 있다.
- **해결**: `.env` 의 `WEB_PORT` 기본값을 8088 로 했다. 컨테이너 안의 포트는 8080 그대로다.
- **배운 점**: 포트는 설정으로 빼 둔다. 다른 PC 에서는 값만 바꾸면 된다.

## 10. 세 서비스가 계정 하나로 모든 테이블을 읽고 쓸 수 있었다

- **단계**: DB
- **증상**: 서비스는 3개로 나눴는데 DB 는 계정 하나(`vet_app`), 스키마 하나였다. 그 계정의 권한(SELECT·INSERT·UPDATE)이 스키마 전체에 열려 있어서, 로그인만 맡는 auth 서비스도 예약 테이블을 읽고 고칠 수 있었다. "MSA 인데 DB 는 그대로"였다.
- **원인을 찾은 과정**: 서비스의 SQL 을 전부 다시 읽어 누가 어느 테이블을 쓰는지 표로 만들었다. 쓰기가 겹치는 테이블은 `slots` 하나뿐이고(clinic 이 추가, reservation 이 수정) 나머지는 주인이 하나씩이었다.
- **검토한 방법**: 서비스마다 MySQL 을 따로 두면 예약 넣기와 슬롯 잡기를 한 트랜잭션으로 묶을 수 없어 중복 예약 방지가 깨진다. SQL 에 스키마 이름을 붙이면 파일 7개쯤을 고쳐야 한다. 자세한 비교는 `검토한-대안.md` 2번에 있다.
- **해결**: MySQL 하나 안에 스키마 셋(`vet_auth`, `vet_clinic`, `vet_reservation`)과 계정 셋을 뒀다. reservation 이 필요한 남의 데이터는 뷰로만 읽는다. 뷰 이름을 원래 테이블 이름과 같게 해서 **앱 코드는 고치지 않았다**. 권한은 `msa/db/grants.sql`, 뷰는 `msa/db/split.sql` 에 있다.
- **확인**

```
[통과] auth 가 예약 읽기 — vet_auth: ERROR 1142 … SELECT command denied
[통과] reservation 이 비밀번호 해시 읽기 (뷰) — ERROR 1054 … Unknown column 'password_hash'
[통과] reservation 이 반려동물 고치기 — ERROR 1142 … UPDATE command denied
```

보호자 9명이 같은 시간을 신청하니 1명만 예약되고 8명은 409 였다. 실패한 쪽의 예약은 남지 않았다.

- **배운 점**: DB 를 나누는 것은 "하나냐 여럿이냐"만이 아니다. 서버는 하나여도 주인과 창구를 DB 가 강제하게 할 수 있다.

## 11. 바깥 DB 를 지우고 다시 만드는 실행이 실패했다

- **단계**: DB (prod 의 RDS 용 초기화 도구)
- **증상**: 빈 MySQL 을 RDS 대신 세워 놓고 초기화 도구를 시험했다. 처음 실행과 재실행(건너뜀)은 됐는데, 강제 재생성만 실패했다.

```
--- 4) VET_FORCE=1 (지우고 다시 만든다)
[vet] 초기화 실패
pet 1 age = 99  (3 이면 초기화된 것)
```

- **원인을 찾은 과정**: 실패한 곳이 스키마를 지우는 단계였다. 10번에서 테이블을 스키마별로 옮기면서 외래 키가 스키마를 가로지르게 됐다는 점을 떠올렸다.
- **원인**: `vet_auth.users` 는 `vet_clinic.vets` 를, `vet_clinic.pets` 는 `vet_auth.users` 를 참조한다. 서로 물려 있어서 어느 스키마를 먼저 지워도 "참조되고 있다"며 막힌다.
- **해결**: `vet-provision.sh` 가 스키마를 지우는 동안만 `SET FOREIGN_KEY_CHECKS = 0` 을 건다.
- **확인**

```
[vet] slots=576 reservations=175 users=305 notices=5 first_slot=2026-11-13 …
exit=0
pet 1 age = 3  (3 이면 초기화된 것)
```

- **배운 점**: 평소 쓰지 않는 길(강제 재생성, 오류 처리)도 한 번은 실행해 봐야 한다. 이 시험을 하지 않았다면 prod 에서 처음 만났을 문제다.

## 12. 로그인은 되는데 그 쿠키로 보낸 다음 요청이 401 이었다

- **단계**: ① 앱 (테스트 스크립트)
- **증상**

```
PASS  auth-login  status=200 cookieName=SESSION
FAIL  auth-me  status=401
FAIL  clinic-sees-auth-session  status=401
FAIL  reservation-sees-auth-session  status=401
```

- **원인을 찾은 과정**: 로그인이 200 이고 쿠키도 받았으니 서비스는 정상으로 보였다. 세션 공유가 안 되는 것이라면 auth 자신의 `/api/auth/me` 는 됐어야 하는데 그것도 401 이었다. 쿠키가 아예 안 가고 있다고 판단했다.
- **원인**: Windows PowerShell 5.1 의 `Invoke-WebRequest` 는 `-Headers` 로 준 `Cookie` 를 보내지 않는다. 자체 쿠키 통만 쓴다.
- **해결**: `System.Net.HttpWebRequest` 로 요청을 직접 만들고 `CookieContainer` 를 넘긴다. 한글 응답이 깨지던 문제도 응답을 UTF-8 로 직접 읽어 함께 풀었다.
- **확인**: `scripts\test-app.ps1` 의 "같은 쿠키로 clinic 의 반려동물 — 200, 2마리", "reservation 의 내 예약 — 200, 3건".
- **배운 점**: 테스트가 실패하면 대상보다 테스트 도구를 먼저 의심해 볼 만한 단서가 있다. 여기서는 "로그인한 서비스 자신도 401"이 그 단서였다.

## 13. DB 접속 명령이 `127:3306` 으로 붙으려 했다

- **단계**: ① 앱 (테스트 스크립트)
- **증상**

```
ERROR 2003 (HY000): Can't connect to MySQL server on '127:3306' (111)
```

- **원인**: PowerShell 5.1 이 `-h127.0.0.1` 을 `-h127` 과 `.0.0.1` 로 잘라 넘겼다.
- **해결**: `--host=127.0.0.1` 로 쓴다.
- **배운 점**: PowerShell 에서 외부 명령에 인자를 넘길 때는 `--이름=값` 형태가 안전하다. 같은 이유로 SQL 에 큰따옴표를 쓰지 않고, 빈 문자열 인자도 피했다.

## 14. "슬롯 자동 생성은 clinic 에만" 검사가 틀리게 실패했다

- **단계**: ① 앱 (테스트 스크립트)
- **증상**

```
[실패] 슬롯 자동 생성은 clinic 에만 — 로그 줄 수: auth 0, clinic 0, reservation 0
결과: 통과 26, 실패 1
```

- **원인을 찾은 과정**: 11월 12일에는 통과하던 검사였다. 그때와 달라진 것은 3번(시드를 그날 기준으로 생성)이다.
- **원인**: 검사가 clinic 로그의 "슬롯 N개 추가" 줄을 셌다. 시드가 14일 치를 이미 넣으니 생성기가 추가할 것이 없었고, 생성기는 추가한 것이 없으면 로그를 남기지 않는다. 생성기는 돌았는데 검사가 못 본 것이다.
- **해결**: 테스트가 마지막 이틀의 빈 슬롯을 먼저 지우고, clinic 이 뜬 뒤 다시 채워졌는지를 센다.
- **확인**

```
[통과] clinic 이 빈 슬롯을 다시 채운다 — 슬롯 수: 처음 576 → 지운 뒤 517 → 서비스가 뜬 뒤 576
[통과] 슬롯 자동 생성은 clinic 에만 — 로그 줄 수: auth 0, clinic 1, reservation 0
```

- **배운 점**: 로그 유무로 판정하는 검사는 다른 곳을 고치면 조용히 틀려진다. 결과(슬롯 수)를 직접 센다.

## 15. 컨테이너를 띄우는 명령이 `invalid mount path: 'C'` 로 실패했다

- **단계**: ② 컨테이너 (명령 실행)
- **증상**

```
docker: Error response from daemon: invalid mount path: 'C' mount path must be absolute
```

- **원인**: Git Bash 가 `/var/lib/mysql` 같은 리눅스 경로를 Windows 경로로 바꿔 넘겼다.
- **해결**: 명령 앞에 `MSYS_NO_PATHCONV=1` 을 둔다. 문서의 실행 명령은 이 문제가 없는 PowerShell 기준으로 적었다.
- **배운 점**: 컨테이너 안의 경로를 인자로 줄 때는 셸이 경로를 바꾸지 않는지 확인한다.

## 16. 중복 예약 시험이 두 번 무효가 됐다

- **단계**: DB (10번의 검증)
- **증상**: 두 보호자가 같은 시간을 신청하는 시험에서 둘 다 400 이 나왔다.

```
date=2026-11-15 slot=
owner002 400
owner003 400
```

- **원인**: 고른 날이 일요일(휴진)이라 빈 시간이 없었고, 시간 번호 없이 요청이 나갔다.
- **다시 했을 때**: 진료일로 바꾸니 한 명은 201, 다른 한 명은 409 였는데 오류 코드가 `PET_SAME_DAY` 였다. 그 보호자의 반려동물이 그날 이미 예약이 있었던 것이라, 확인하려던 "같은 시간 경합"이 아니었다.
- **해결**: 보호자를 9명으로 늘리고 결과를 오류 코드와 예약 수로 구분해 봤다.
- **확인**

```
owner020 → [201] 예약됨        내 예약 수 0 → 1
owner021 → [409] SLOT_TAKEN    내 예약 수 0 → 0
…
owner028 → [409] PET_SAME_DAY  내 예약 수 1 → 1
```

- **배운 점**: "409 가 났다"만으로는 통과가 아니다. 어떤 이유의 409 인지까지 봐야 확인하려던 것을 확인한 것이다.
