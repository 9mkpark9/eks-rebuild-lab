# 직접 해 보기 — 이미지를 만들어 AWS 에 올리기까지

스크립트를 쓰지 않고 명령을 하나씩 직접 쳐서, 소스에서 시작해 AWS 에서 서비스가 뜨는 데까지 간다. 단계마다 **무엇을 하는지 → 명령 → 이렇게 나오면 된다 → 뜻** 순서로 적었다.

```mermaid
flowchart LR
  A[1장<br>앱을 그냥 실행] --> B[2장<br>이미지 만들기]
  B --> C[3장<br>컨테이너로 실행]
  C --> D[4장<br>레지스트리에 올리기]
  D --> E[5장<br>쿠버네티스에 올리기<br>EC2 3대]
  E --> F[6장<br>EKS 에 올리기]
```

| 장 | 과제 | 어디서 | 쓰는 도구 |
|---|---|---|---|
| 1 | ① | WSL 2 Ubuntu | `java`, `docker`, `curl` |
| 2, 3, 4 | ② | WSL 2 Ubuntu | `docker` |
| 5 | ③ | AWS EC2 3대 (kubeadm) | `aws`, `ssh`, `kubectl` |
| 6 | ④ | AWS EKS | `aws`, `eksctl`, `kubectl`, `docker` |

## 먼저: 어디서 치나

**이 문서의 명령은 전부 WSL 의 Ubuntu 터미널에서 친다.** Windows 의 PowerShell 이나 명령 프롬프트가 아니다. PowerShell 에서 치면 첫 명령부터 아래처럼 실패한다.

```
'&&' 토큰은 이 버전에서 올바른 문 구분 기호가 아닙니다.
```

PowerShell 과 Ubuntu 는 명령을 적는 방법이 다르다. `&&`, `(cd …)`, 줄 끝의 `\`, `$(…)`, `이름=값 명령` 같은 것은 Ubuntu(bash)의 문법이다. 과제도 ① ② 를 WSL 2 Ubuntu 에서 하라고 정해 두었다.

| 지금 어디인지 | 프롬프트의 모양 |
|---|---|
| PowerShell (여기서 치지 않는다) | `PS C:\Users\…>` |
| Ubuntu (여기서 친다) | `이름@PC이름:~$` |

Ubuntu 터미널을 여는 방법은 둘 중 하나다.

- 시작 메뉴에서 **Ubuntu** 를 실행한다.
- PowerShell 에서 `wsl -d Ubuntu` 를 친다. 프롬프트가 `…:~$` 모양으로 바뀐다. 나올 때는 `exit`.

Ubuntu 에 들어가면 먼저 홈 폴더로 간다. 저장소는 Windows 폴더(`C:\…`)에 있는 것을 쓰지 않고 Ubuntu 안에 새로 받는다(1-1). Windows 폴더는 Ubuntu 에서 `/mnt/c/…` 로 보이지만 느리고, Windows 에서 만든 빌드 결과가 섞여 있다.

```bash
cd ~
```

**확인한 범위.** 1 ~ 4장은 WSL 2 Ubuntu 에서, 5장의 쿠버네티스 명령은 내 PC 의 클러스터에서 2026년 11월 17일에 이 순서대로 실행했다. **5장의 EC2 부분과 6장 전체는 실행해 보지 않았다.** AWS 조회 명령만 실제 계정에서 확인했다.

**이 문서에서 쓰는 값**

| 표시 | 뜻 |
|---|---|
| `<…>` | 직접 채우는 값 |
| `rootpw1234` 같은 비밀번호 | 1 ~ 3장의 연습용 값. 내 PC 안에서만 쓰고 지운다. 쿠버네티스에서는 무작위 값을 만든다 |
| `test-only` | 테스트 계정(`owner001`, `admin1`)의 비밀번호. 모의 데이터다 |

# 0장. 이 앱이 무엇으로 이루어져 있나

| 구성 요소 | 하는 일 | 포트 |
|---|---|---|
| `auth` | 로그인 | 8080 |
| `clinic` | 반려동물, 진료 시간, 공지 | 8080 |
| `reservation` | 예약, 승인, 일정 | 8080 |
| `web` | 화면을 주고, `/api/…` 요청을 위 셋 중 맞는 곳으로 넘긴다 | 8080 |
| MySQL | 데이터를 저장한다 | 3306 |
| Redis | 로그인 상태(세션)를 저장한다 | 6379 |

앞의 셋은 Java 로 만든 프로그램이고, 각각 jar 파일 하나로 실행된다. 이 셋을 묶어 "서비스"라고 부른다.

**설정은 전부 환경 변수로 준다.** 이것이 이 문서 전체의 열쇠다. 프로그램 안에 DB 주소가 적혀 있지 않기 때문에, 같은 프로그램을 내 PC 에서도, 컨테이너에서도, 쿠버네티스에서도 주소만 바꿔 쓸 수 있다.

| 환경 변수 | 뜻 |
|---|---|
| `SPRING_DATASOURCE_URL` | DB 주소 |
| `SPRING_DATASOURCE_USERNAME`, `SPRING_DATASOURCE_PASSWORD` | DB 계정과 비밀번호 |
| `SPRING_DATA_REDIS_HOST`, `SPRING_DATA_REDIS_PASSWORD` | Redis 주소와 비밀번호 |
| `REDIS_TLS`, `DB_POOL_MAX` | Redis 암호화 여부, DB 연결 수 |

## 동작을 확인하는 법 (모든 장에서 쓴다)

장마다 주소만 바뀐다. 먼저 주소를 변수에 넣는다.

| 장 | 넣을 값 |
|---|---|
| 1장 | `AUTH=http://127.0.0.1:18081 CLINIC=http://127.0.0.1:18082 RES=http://127.0.0.1:18083` |
| 3장 | `AUTH=http://localhost:8088; CLINIC=$AUTH; RES=$AUTH` |
| 5장 | `AUTH=http://<노드 IP>:30080; CLINIC=$AUTH; RES=$AUTH` |
| 6장 | `AUTH=http://<ALB 주소>; CLINIC=$AUTH; RES=$AUTH` |

그다음 아래를 차례로 친다.

```bash
# 1) 로그인. 쿠키를 cookie.txt 에 받는다
curl -s -c cookie.txt -H 'Content-Type: application/json' \
  -d '{"loginId":"owner001","password":"test-only"}' $AUTH/api/auth/login

# 2) 조회: 내 반려동물
curl -s -b cookie.txt $CLINIC/api/pets

# 3) 조회: 예약할 수 있는 시간. 결과에서 slotId 하나를 고른다
curl -s -b cookie.txt "$CLINIC/api/slots?date=$(date -d '+2 day' +%F)&type=GENERAL"

# 4) 등록: 예약한다
curl -s -b cookie.txt -H 'Content-Type: application/json' \
  -d '{"petId":1,"slotId":<고른 slotId>}' -w '\nHTTP %{http_code}\n' $RES/api/reservations

# 5) 조회: 내 예약
curl -s -b cookie.txt $RES/api/reservations/me

# 6) 수정: 취소한다
curl -s -b cookie.txt -X DELETE -w 'HTTP %{http_code}\n' $RES/api/reservations/<예약 번호>
```

| 단계 | 이렇게 나오면 된다 |
|---|---|
| 1 | `{"userId":6,"loginId":"owner001","name":"안소율","role":"OWNER",…}` |
| 2 | `[{"petId":1,"name":"콩이",…},{"petId":2,"name":"나비",…}]` |
| 3 | `[{"slotId":97,…},…]`. `[]` 면 그날이 일요일(휴진)이다. `+3 day` 로 바꾼다 |
| 4 | `HTTP 201` 과 `"reservationId":176,…,"status":"REQUESTED"` |
| 5 | 방금 만든 예약이 목록에 있다 |
| 6 | `HTTP 204` |

4번에서 `409` 가 나오면 그 반려동물이 그날 이미 예약이 있는 것이다. 날짜를 바꾸거나 `"petId":2` 로 한다.

# 2장. 이미지를 만든다

이미지는 **프로그램과 그것을 실행하는 데 필요한 것(Java 등)을 한 덩어리로 묶은 것**이다. 이미지가 있으면 Java 가 없는 PC 에서도 실행된다.

## 2-1. Dockerfile 을 읽는다

이미지를 만드는 순서를 적은 파일이다. `msa/auth-service/Dockerfile` 을 연다. 두 부분으로 나뉜다.

**앞부분 — jar 를 만든다 (빌드 단계)**

```dockerfile
FROM eclipse-temurin:21-jdk-alpine AS build
WORKDIR /src
COPY gradlew settings.gradle build.gradle ./
COPY gradle gradle
COPY common/build.gradle common/
COPY auth-service/build.gradle auth-service/
…
RUN … ./gradlew --no-daemon -q :auth-service:dependencies …
COPY common/src common/src
COPY auth-service/src auth-service/src
ARG VERSION=dev
RUN ./gradlew --no-daemon -q :auth-service:bootJar -Pversion=${VERSION} \
 && java -Djarmode=tools -jar … extract --layers --destination /layers …
```

| 줄 | 하는 일 |
|---|---|
| `FROM …jdk… AS build` | Java 개발 도구(JDK)가 든 이미지에서 시작한다. 이 단계에 `build` 라는 이름을 붙인다 |
| `WORKDIR /src` | 작업할 폴더를 정한다 |
| `COPY gradlew …`, `COPY …/build.gradle` | 빌드 설정 파일만 먼저 복사한다 |
| `RUN … dependencies` | 필요한 라이브러리를 받는다 |
| `COPY …/src` | 이제 소스를 복사한다 |
| `ARG VERSION=dev` | 빌드할 때 밖에서 받는 값. 버전 번호를 받는다 |
| `RUN … bootJar` | jar 를 만든다. 1장의 `gradlew build` 와 같은 일이다 |
| `… extract --layers` | jar 를 "라이브러리"와 "내 코드"로 나눠 푼다 |

설정 파일을 먼저 복사하고 소스를 나중에 복사하는 이유: Docker 는 줄마다 결과를 기억해 둔다(캐시). 소스만 고쳤으면 그 위의 줄들은 다시 하지 않는다. 라이브러리를 받는 데 시간이 가장 오래 걸리므로, 그 줄이 소스보다 위에 있어야 다시 받지 않는다.

**뒷부분 — 실행할 것만 담는다 (실행 단계)**

```dockerfile
FROM eclipse-temurin:21-jre-alpine
RUN addgroup -S -g 10001 app && adduser -S -u 10001 -G app -H -s /sbin/nologin app
WORKDIR /app
COPY --from=build /layers/dependencies/ ./
COPY --from=build /layers/spring-boot-loader/ ./
COPY --from=build /layers/snapshot-dependencies/ ./
COPY --from=build /layers/application/ ./
ARG VERSION=dev
ENV APP_VERSION=${VERSION} JAVA_TOOL_OPTIONS="…"
USER 10001:10001
EXPOSE 8080
ENTRYPOINT ["java", "-jar", "/app/app.jar"]
```

| 줄 | 하는 일 |
|---|---|
| `FROM …jre…` | **새로 시작한다.** 이번에는 실행만 되는 작은 Java(JRE)다. 앞 단계의 컴파일러와 소스는 따라오지 않는다 |
| `RUN addgroup … adduser …` | 실행 전용 사용자(번호 10001)를 만든다 |
| `COPY --from=build …` 4줄 | 앞 단계에서 만든 것만 가져온다. 덜 바뀌는 라이브러리부터 넣는다 |
| `ENV …` | 컨테이너 안의 환경 변수. 버전과 Java 옵션 |
| `USER 10001:10001` | root 가 아닌 사용자로 실행한다 |
| `EXPOSE 8080` | 이 프로그램이 8080 포트를 쓴다고 적어 둔다 |
| `ENTRYPOINT […]` | 컨테이너가 뜰 때 실행할 명령. 1장의 `java -jar …` 다 |

단계를 둘로 나눈 이유: 만들 때 필요한 것(컴파일러, 소스)과 실행할 때 필요한 것(JRE, jar)이 다르다. 실행할 것만 담으면 이미지가 작아진다.

## 2-2. 빌드한다

```bash
docker build -f msa/auth-service/Dockerfile --build-arg VERSION=1.0.0 -t vet-auth:1.0.0 msa
```

| 부분 | 뜻 |
|---|---|
| `-f msa/auth-service/Dockerfile` | 어느 Dockerfile 로 만들지 |
| `--build-arg VERSION=1.0.0` | Dockerfile 의 `ARG VERSION` 에 넣을 값 |
| `-t vet-auth:1.0.0` | 만든 이미지에 붙일 이름과 태그 (`이름:태그`) |
| `msa` (마지막) | 빌드 위치. `COPY` 가 파일을 찾는 기준 폴더다 |

나머지도 만든다. web 과 db 는 저장소 맨 위(`.`)가 빌드 위치다.

```bash
docker build -f msa/clinic-service/Dockerfile      --build-arg VERSION=1.0.0 -t vet-clinic:1.0.0 msa
docker build -f msa/reservation-service/Dockerfile --build-arg VERSION=1.0.0 -t vet-reservation:1.0.0 msa
docker build -f msa/web/Dockerfile.apache --build-arg VERSION=1.0.0-apache -t vet-web:1.0.0-apache .
docker build -f msa/db/Dockerfile -t vet-db:1.0.0 .
```

## 2-3. 만들어진 것을 본다

```bash
docker image ls | grep vet-
```

```
vet-auth:1.0.0          357MB
vet-clinic:1.0.0        357MB
vet-reservation:1.0.0   357MB
vet-web:1.0.0-apache    115MB
vet-db:1.0.0            1.27GB
```

이미지 안이 어떻게 쌓였는지 본다. Dockerfile 의 줄이 아래에서 위로 쌓여 있다.

```bash
docker history vet-auth:1.0.0 | head -10
```

```
ENTRYPOINT ["java" "-jar" "/app/app.jar"]      0B
EXPOSE [8080/tcp]                              0B
USER 10001:10001                               0B
ENV APP_VERSION=1.0.0 …                        0B
COPY /layers/application/ ./                   41kB     ← 내 코드
COPY /layers/dependencies/ ./                  37MB     ← 라이브러리
```

내 코드는 41kB 이고 라이브러리가 37MB 다. 코드만 고치면 41kB 짜리 층만 새로 만들어진다.

```bash
docker image inspect vet-auth:1.0.0 --format '{{.Os}}/{{.Architecture}}  user={{.Config.User}}'
```

`linux/amd64  user=10001:10001` 이 나온다. `linux/amd64` 는 6장에서 중요하다. AWS 의 노드가 `linux/amd64` 라서, 다른 종류로 만든 이미지는 거기서 실행되지 않는다.

## 2-4. 캐시를 확인한다

같은 명령을 한 번 더 친다. 대부분의 줄이 `CACHED` 로 지나가고 몇 초 만에 끝난다. 2-1 에서 말한 "줄마다 결과를 기억해 둔다"가 이것이다.

# 3장. 이미지를 컨테이너로 실행한다

컨테이너는 **이미지를 실행한 것**이다. 1장에서 터미널 3개로 하던 일을 `docker run` 으로 한다.

## 3-1. 네트워크를 만든다

```bash
docker network create vet-net
```

뜻: 컨테이너끼리 **이름으로** 서로를 찾을 수 있는 네트워크를 만든다. 1장에서는 `127.0.0.1` 로 찾았지만, 컨테이너는 각자 자기만의 `127.0.0.1` 을 가지므로 이름이 필요하다.

## 3-2. DB 와 Redis

```bash
docker run -d --name vet-mysql --network vet-net --network-alias mysql \
  -e MYSQL_ROOT_PASSWORD=rootpw1234 -e VET_AUTH_PASSWORD=authpw1234 \
  -e VET_CLINIC_PASSWORD=clinicpw1234 -e VET_RESERVATION_PASSWORD=respw1234 vet-db:1.0.0

docker run -d --name vet-redis --network vet-net --network-alias redis \
  redis:7-alpine redis-server --requirepass redispw1234
```

| 옵션 | 뜻 |
|---|---|
| `-d` | 뒤에서 실행한다. 터미널을 붙잡지 않는다 |
| `--name vet-mysql` | 컨테이너의 이름. `docker logs`, `docker stop` 에서 쓴다 |
| `--network vet-net` | 3-1 에서 만든 네트워크에 넣는다 |
| `--network-alias mysql` | 그 네트워크 안에서 불리는 이름. 다른 컨테이너가 `mysql` 로 찾는다 |
| `-e 이름=값` | 환경 변수를 준다 |
| 마지막 `vet-db:1.0.0` | 실행할 이미지 |

## 3-3. 서비스 3개

1장의 명령과 나란히 놓고 보면 달라진 것은 두 가지다. 환경 변수를 `-e` 로 주고, 주소가 `127.0.0.1` 에서 `mysql`, `redis` 로 바뀌었다.

```bash
docker run -d --name vet-auth --network vet-net --network-alias auth \
  -e SPRING_DATASOURCE_URL='jdbc:mysql://mysql:3306/vet_auth?connectionTimeZone=LOCAL&characterEncoding=UTF-8' \
  -e SPRING_DATASOURCE_USERNAME=vet_auth -e SPRING_DATASOURCE_PASSWORD=authpw1234 \
  -e SPRING_DATA_REDIS_HOST=redis -e SPRING_DATA_REDIS_PASSWORD=redispw1234 \
  -e REDIS_TLS=false -e DB_POOL_MAX=5 vet-auth:1.0.0

docker run -d --name vet-clinic --network vet-net --network-alias clinic \
  -e SPRING_DATASOURCE_URL='jdbc:mysql://mysql:3306/vet_clinic?connectionTimeZone=LOCAL&characterEncoding=UTF-8' \
  -e SPRING_DATASOURCE_USERNAME=vet_clinic -e SPRING_DATASOURCE_PASSWORD=clinicpw1234 \
  -e SPRING_DATA_REDIS_HOST=redis -e SPRING_DATA_REDIS_PASSWORD=redispw1234 \
  -e REDIS_TLS=false -e DB_POOL_MAX=5 vet-clinic:1.0.0

docker run -d --name vet-reservation --network vet-net --network-alias reservation \
  -e SPRING_DATASOURCE_URL='jdbc:mysql://mysql:3306/vet_reservation?connectionTimeZone=LOCAL&characterEncoding=UTF-8' \
  -e SPRING_DATASOURCE_USERNAME=vet_reservation -e SPRING_DATASOURCE_PASSWORD=respw1234 \
  -e SPRING_DATA_REDIS_HOST=redis -e SPRING_DATA_REDIS_PASSWORD=redispw1234 \
  -e REDIS_TLS=false -e DB_POOL_MAX=5 vet-reservation:1.0.0
```

## 3-4. web

```bash
docker run -d --name vet-web --network vet-net -p 8088:8080 vet-web:1.0.0-apache
```

`-p 8088:8080` 은 "내 PC 의 8088 로 들어온 것을 컨테이너의 8080 으로 보낸다"는 뜻이다. **`-p` 를 준 것은 web 하나뿐이다.** 서비스와 DB 는 밖에서 직접 접속할 수 없고 web 을 거쳐야만 한다.

## 3-5. 확인한다

```bash
docker ps --filter name=vet-
```

6개가 `Up` 이면 된다. 15초쯤 뒤:

```bash

curl -s -i http://localhost:8088/api/status/auth
AUTH=http://localhost:8088; CLINIC=$AUTH; RES=$AUTH
```

- 첫 줄: `HTTP/1.1 200 OK` 와 `X-Web-Version: 1.0.0-apache`.
- 둘째 줄: `X-Served-By: e7c588a1e688` 처럼 컨테이너 ID 가 나온다. 어느 컨테이너가 답했는지를 알려 준다.

이어서 0장의 "동작을 확인하는 법"을 한다. 브라우저에서 `http://localhost:8088` 과 `http://localhost:8088/status` 도 연다.

## 3-6. 로그와 상태를 본다

첫 줄은 `503`(clinic 이 맡은 경로), 둘째 줄은 `200`(reservation 이 맡은 경로)이다. 하나가 멈춰도 나머지는 동작한다.

# 4장. 이미지를 레지스트리에 올린다

지금 이미지는 내 PC 에만 있다. AWS 의 서버가 이 이미지를 쓰려면 인터넷에서 받을 수 있는 곳에 올려야 한다. 그곳이 레지스트리다.

## 4-1. 이름을 레지스트리 주소로 붙인다

이미지 이름의 맨 앞이 "어디에 올릴지"다.

```
docker.io/<내 아이디>/vet-auth:1.0.0
└ 레지스트리 ┘└ 계정 ─┘└ 이름 ┘└태그┘
```

```bash
docker login                                         # 아이디와 토큰을 직접 입력한다
docker tag vet-auth:1.0.0 docker.io/<내 아이디>/vet-auth:1.0.0
docker push docker.io/<내 아이디>/vet-auth:1.0.0
```

`docker tag` 는 복사가 아니라 같은 이미지에 이름을 하나 더 붙이는 것이다. 나머지 4개(`vet-clinic:1.0.0`, `vet-reservation:1.0.0`, `vet-web:1.0.0-apache`, `vet-db:1.0.0`)도 같은 방법으로 올린다.

## 4-2. 올라갔는지 확인한다

```bash
docker rmi docker.io/<내 아이디>/vet-auth:1.0.0      # 내 PC 에서 그 이름을 지우고
docker pull docker.io/<내 아이디>/vet-auth:1.0.0     # 레지스트리에서 다시 받는다
```

받아지면 된다. 레지스트리의 웹 화면에서 저장소가 **공개(public)** 인지도 본다. 비공개면 5장의 서버가 받지 못한다.

미리 확인한 것: `docker tag` 와 `docker push` 는 내 PC 에 띄운 임시 레지스트리로 시험했다. 실제 레지스트리에는 올리지 않았다.

# 5장. 쿠버네티스에 올린다 (AWS EC2 3대)

3장에서는 내가 `docker run` 을 하나씩 쳤고, 멈추면 내가 다시 켜야 했다. 쿠버네티스에서는 **"이런 상태로 있어야 한다"를 파일(YAML)에 적어 주면** 쿠버네티스가 그 상태를 만들고 유지한다.

이미지는 바뀌지 않는다. 2장에서 만든 그 이미지를 그대로 쓴다. 바뀌는 것은 "어떻게 실행할지를 적는 방법"이다.

## 5-1. `docker run` 의 옵션이 YAML 의 어디로 가나

| 3장에서 | 쿠버네티스에서 | 어느 파일 |
|---|---|---|
| `vet-auth:1.0.0` (이미지) | `Deployment` 의 `image` | `gitops/apps/vet/base/auth.yaml` |
| 컨테이너 1개 | `replicas: 2` — Pod 2개 | 같은 파일 |
| `-e` 로 준 설정 (DB 주소 등) | `ConfigMap` | `base/config.yaml` |
| `-e` 로 준 비밀번호 | `Secret` | 파일이 아니라 명령으로 만든다 (5-6) |
| `--network-alias auth` | `Service` 의 이름 `auth` | `base/auth.yaml` 아래쪽 |
| `-p 8088:8080` | `Service` 의 `type: NodePort` | `overlays/kubeadm/web-nodeport.yaml` |
| 멈추면 그대로 | `Deployment` 가 다시 띄운다 | |
| DB 데이터가 컨테이너 안에 | `PersistentVolumeClaim` — 볼륨 | `components/db-in-cluster/mysql.yaml` |

## 5-2. YAML 을 읽는다

`base/auth.yaml` 에서 핵심만 추리면 이렇다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: auth
spec:
  replicas: 2                                  # Pod 를 2개 유지한다
  selector:
    matchLabels:
      app: auth                                # 이 라벨이 붙은 Pod 를 내가 관리한다
  template:                                    # ↓ Pod 를 이렇게 만든다
    metadata:
      labels:
        app: auth
    spec:
      containers:
        - name: auth
          image: vet-auth                      # 이미지 (주소와 태그는 5-3 에서 붙는다)
          ports:
            - name: http
              containerPort: 8080
          envFrom:
            - configMapRef:
                name: vet-config               # 설정을 ConfigMap 에서 통째로 받는다
          env:
            - name: SPRING_DATASOURCE_URL
              value: jdbc:mysql://$(DB_HOST):3306/vet_auth?…
            - name: SPRING_DATASOURCE_USERNAME
              value: vet_auth
            - name: SPRING_DATASOURCE_PASSWORD
              valueFrom:
                secretKeyRef:                  # 비밀번호는 Secret 에서 받는다
                  name: vet-db
                  key: auth-password
          readinessProbe:                      # 준비됐는지 묻는다. 준비된 Pod 에만 요청을 보낸다
            httpGet:
              path: /health
              port: http
          livenessProbe:                       # 살아 있는지 묻는다. 답이 없으면 다시 띄운다
            httpGet:
              path: /health
              port: http
---
apiVersion: v1
kind: Service
metadata:
  name: auth                                   # 다른 Pod 가 auth 라는 이름으로 찾는다
spec:
  selector:
    app: auth                                  # 이 라벨이 붙은 Pod 들에게 나눠 보낸다
  ports:
    - port: 8080
      targetPort: http
```

3장의 `docker run … vet-auth` 한 줄과 견줘 보면 같은 정보다. 이미지, 환경 변수, 이름이 자리를 옮겼을 뿐이다.

실제 파일에는 아래 항목이 더 있다. 과제의 필수는 아니고, 지우거나 몰라도 앱은 뜬다.

| 항목 | 하는 일 | 과제에서 |
|---|---|---|
| `strategy` (`maxSurge`, `maxUnavailable`) | 새 Pod 가 준비된 뒤에 옛 Pod 를 내린다 | 선택 (무중단 롤링 업데이트) |
| `startupProbe` | 뜨는 데 오래 걸려도 기다려 준다 | Probe 의 한 종류 |
| `lifecycle.preStop`, `terminationGracePeriodSeconds` | 내려갈 때 처리 중인 요청을 마친다 | 선택 (무중단) |
| `resources` | CPU 와 메모리를 얼마나 쓸지 | 선택 |
| `topologySpreadConstraints` | 두 Pod 를 서로 다른 노드에 놓는다 | 선택 (분산 배치) |
| `securityContext` | root 가 아닌 사용자로, 권한을 줄여서 실행 | 선택 |
| `volumes: tmp` | 임시 파일용 빈 폴더 | 위 보안 설정 때문에 필요 |

`clinic.yaml`, `reservation.yaml` 은 이름만 다르다. `web.yaml` 은 DB 설정이 없고, `redis.yaml` 은 `Service` 와 `Deployment` 하나씩, `mysql.yaml` 은 볼륨이 붙은 것이 다르다.

## 5-3. 파일들을 하나로 합쳐 본다

배포 파일이 여러 폴더에 나뉘어 있어 복잡해 보인다. **합치면 평범한 YAML 한 파일**이다.

```bash
kubectl kustomize gitops/apps/vet/overlays/kubeadm > vet.yaml
grep -c '^kind:' vet.yaml
grep '^kind:' vet.yaml | sort | uniq -c
```

```
19
      1 kind: ConfigMap
      5 kind: Deployment
      1 kind: Namespace
      1 kind: PersistentVolumeClaim
      4 kind: PodDisruptionBudget
      6 kind: Service
      1 kind: StatefulSet
```

`vet.yaml` 을 열어 보면 5-2 에서 본 것과 같은 모양이 19개 이어져 있다. 이 파일이 실제로 클러스터에 들어가는 내용이다.

폴더가 나뉜 이유는 하나다. EC2 클러스터와 EKS 에서 **다른 부분만** 따로 적으려는 것이다.

| 폴더 | 내용 |
|---|---|
| `base/` | 어디서나 같은 것 (Deployment, Service, ConfigMap) |
| `components/db-in-cluster/` | MySQL |
| `overlays/kubeadm/` | EC2 클러스터에서만 다른 것: 이미지 주소, NodePort, 볼륨 종류 |
| `overlays/eks/` | EKS 에서만 다른 것: 이미지 주소, ALB, 볼륨 종류 |

`kubectl kustomize` 는 이것들을 합쳐 주는 명령이고, `kubectl apply -k` 는 합친 것을 바로 적용하는 명령이다. 이 문서에서는 합친 파일을 눈으로 보고 `kubectl apply -f vet.yaml` 로 적용한다.

**4장에서 다른 레지스트리에 올렸다면** `gitops/apps/vet/overlays/kubeadm/kustomization.yaml` 의 `images` 에서 `newName` 다섯 줄을 고친 뒤 다시 합친다.

```yaml
images:
  - name: vet-auth
    newName: docker.io/<내 아이디>/vet-auth      # ← 올린 주소로
    newTag: 1.0.0
```

```bash
grep 'image:' vet.yaml        # 주소가 맞는지 확인한다
```

## 5-4. EC2 를 켜고 접속한다

내 PC 에서 한다. 수업에서 만든 EC2 3대(컨트롤 플레인 1, 워커 2)를 쓴다.

```bash
# 상태를 본다
aws ec2 describe-instances \
  --filters 'Name=tag:Name,Values=k8s-core-cluster-*' 'Name=instance-state-name,Values=running,stopped' \
  --query 'Reservations[].Instances[].[Tags[?Key==`Name`]|[0].Value,InstanceId,State.Name,PublicIpAddress,PrivateIpAddress]' \
  --output table

# 꺼져 있으면 켠다 (위 표의 InstanceId 3개)
aws ec2 start-instances --instance-ids <ID> <ID> <ID>
```

켜고 1 ~ 2분 뒤 첫 명령을 다시 치면 `PublicIpAddress` 가 채워진다. 껐다 켜면 공인 IP 가 바뀐다.

```bash
# 보안 그룹에 30080 이 열려 있는지 본다
aws ec2 describe-security-groups --group-ids <보안 그룹 ID> \
  --query 'SecurityGroups[0].IpPermissions[].[IpProtocol,FromPort,ToPort,IpRanges[].CidrIp|[0]]' --output table
```

2026년 11월 17일에 조회했을 때 이 보안 그룹에는 `22`, `30000-32767`, 그리고 "같은 보안 그룹끼리 전부 허용"이 있었다. 30080 이 그 범위 안이라 따로 열 것이 없다. 허용된 주소가 지금 내 IP 와 다르면 접속이 안 된다. 내 IP 는 `curl -s https://checkip.amazonaws.com` 으로 본다.

컨트롤 플레인에 들어간다.

```bash
ssh -i <키 파일> ubuntu@<컨트롤 플레인의 공인 IP>
kubectl get nodes -o wide
```

3대가 모두 `Ready` 여야 한다. `NotReady` 면 수업에서 만든 클러스터의 상태부터 살린다.

## 5-5. 볼륨을 준비한다

MySQL 의 데이터를 둘 곳이다. 직접 만든 클러스터에는 볼륨을 자동으로 만들어 주는 장치가 없어서, 워커 한 대의 폴더를 볼륨으로 등록한다.

```bash
# (DB 를 둘 워커에 ssh 로 들어가서)
sudo mkdir -p /var/lib/vet-mysql
```

컨트롤 플레인으로 돌아와 저장소를 받고 등록한다.

```bash
git clone https://github.com/9mkpark9/eks-rebuild-lab.git && cd eks-rebuild-lab
kubectl label node <그 워커의 이름> vet-db=true
kubectl apply -f gitops/cluster/kubeadm/
kubectl get sc,pv
```

`vet-local` 과 `vet-mysql`(`Available`)이 보이면 된다. 뜻: "라벨 `vet-db=true` 가 붙은 노드의 `/var/lib/vet-mysql` 폴더를 5Gi 짜리 볼륨으로 쓴다"고 등록했다.

## 5-6. 네임스페이스와 Secret 을 만든다

```bash
kubectl create namespace vet

kubectl -n vet create secret generic vet-db \
  --from-literal=root-password="$(openssl rand -hex 18)" \
  --from-literal=auth-password="$(openssl rand -hex 18)" \
  --from-literal=clinic-password="$(openssl rand -hex 18)" \
  --from-literal=reservation-password="$(openssl rand -hex 18)"

kubectl -n vet create secret generic vet-redis --from-literal=password="$(openssl rand -hex 18)"

kubectl -n vet describe secret vet-db
```

`openssl rand -hex 18` 이 무작위 36자를 만든다. 비밀번호가 화면에도 파일에도 남지 않는다. `describe` 는 키 이름과 길이(`36 bytes`)만 보여 준다.

Secret 을 파일로 두지 않는 이유: 저장소가 공개다. 비밀번호는 Git 에 올리지 않는다. `kubectl get secret -o yaml` 은 값을 보여 주므로 화면을 남길 때 쓰지 않는다.

## 5-7. 적용한다

```bash
kubectl kustomize gitops/apps/vet/overlays/kubeadm > vet.yaml
kubectl apply -f vet.yaml
kubectl -n vet get pods -o wide -w
```

처음에는 이미지를 받느라 `ContainerCreating` 이 몇 분 간다. 전부 `1/1 Running` 이 되면 `Ctrl+C`.

```bash
kubectl -n vet get deploy,sts          # auth, clinic, reservation, web 이 2/2. redis 1/1. mysql 1/1
kubectl -n vet get pods -o wide        # 같은 앱의 두 Pod 가 서로 다른 워커에 있다
kubectl -n vet get svc                 # web 만 NodePort(80:30080), 나머지는 ClusterIP
kubectl -n vet get pvc                 # mysql-data 가 Bound
kubectl -n vet get configmap vet-config -o yaml
kubectl -n vet describe deploy auth    # Liveness, Readiness, Startup 줄
```

막히면: `kubectl -n vet describe pod <이름>` 의 맨 아래 Events 를 본다. `ImagePullBackOff` 면 이미지 주소가 틀렸거나 저장소가 비공개다. `Pending` 이면 5-5 의 라벨이나 폴더를 다시 본다.

## 5-8. 밖에서 접속한다

내 PC 에서:

```bash
curl -s -i http://<워커의 공인 IP>:30080/health
AUTH=http://<워커의 공인 IP>:30080; CLINIC=$AUTH; RES=$AUTH
```

0장의 "동작을 확인하는 법"을 한다. 브라우저로 `http://<워커의 공인 IP>:30080` 도 연다. 어느 노드의 IP 로 해도 된다.

DB 는 밖에서 안 보이는지도 확인한다.

```bash
nc -zv -w 3 <워커의 공인 IP> 3306       # 접속되지 않아야 한다
```

## 5-9. 쿠버네티스가 해 주는 일을 본다

컨트롤 플레인에서 한다. 주소는 `http://localhost:30080` 이다.

**자동 복구** — 3장에서는 멈추면 그대로였다.

```bash
kubectl -n vet get pods -l app=auth
kubectl -n vet delete pod <auth Pod 하나>
kubectl -n vet get pods -l app=auth -w
```

지운 Pod 대신 새 이름의 Pod 가 생겨 2개로 돌아온다. `replicas: 2` 라고 적어 두었기 때문이다.

**롤링 업데이트와 롤백** — 터미널 두 개로 한다.

```bash
# 터미널 A: 60초 동안 계속 요청한다. 끝나면 응답 코드별 개수가 나온다
for i in $(seq 1 300); do curl -s -m 3 -o /dev/null -w '%{http_code}\n' http://localhost:30080/api/status/clinic; sleep 0.2; done | sort | uniq -c
```

```bash
# 터미널 B: 버전을 바꾼다
curl -s http://localhost:30080/api/status/clinic            # "version":"1.0.0"
kubectl -n vet set env deployment/clinic APP_VERSION=1.0.1
kubectl -n vet rollout status deployment/clinic
curl -s http://localhost:30080/api/status/clinic            # "version":"1.0.1"

# 되돌린다
kubectl -n vet rollout history deployment/clinic
kubectl -n vet rollout undo deployment/clinic
kubectl -n vet rollout status deployment/clinic
curl -s http://localhost:30080/api/status/clinic            # "version":"1.0.0"
```

터미널 A 에 `300 200` 한 줄만 나오면 버전을 바꾸는 동안 실패한 요청이 없는 것이다. Pod 가 하나씩 새것으로 바뀌고, 새 Pod 가 준비된 뒤에 옛 Pod 가 내려가기 때문이다.

**데이터 유지** — 예약을 하나 만들어 두고(0장의 4번까지) 번호를 적는다.

```bash
kubectl -n vet get pod mysql-0 -o jsonpath='{.metadata.creationTimestamp}{"\n"}'
kubectl -n vet delete pod mysql-0
kubectl -n vet rollout status statefulset/mysql
kubectl -n vet get pod mysql-0 -o jsonpath='{.metadata.creationTimestamp}{"\n"}'
curl -s -b cookie.txt http://localhost:30080/api/reservations/me
```

만든 시각이 바뀌었으면 새 Pod 다(이름은 `mysql-0` 그대로다). 그런데도 예약이 남아 있다. 데이터가 Pod 안이 아니라 볼륨에 있기 때문이다.

미리 확인한 것(내 PC 의 클러스터): 버전이 `1.0.0` → `1.0.1` → `1.0.0` 으로 바뀌는 동안 요청 250건 중 실패 0건. auth Pod 를 지우면 12초 안에 새 Pod 가 `Running`. `mysql-0` 을 지운 뒤에도 예약이 남아 있었다.

## 5-10. 끝나면 끈다

```bash
kubectl delete -f vet.yaml                    # 앱을 지운다 (컨트롤 플레인에서)
```

```bash
aws ec2 stop-instances --instance-ids <ID> <ID> <ID>      # 내 PC 에서
```

EC2 는 켜 둔 시간만큼 요금이 나온다. 정지해도 디스크 요금은 나온다. 다 썼으면 종료(terminate)한다.

앱을 지운 뒤 다시 올리려면 볼륨도 비우고 다시 등록해야 한다. 그대로 올리면 `mysql-0` 이 `Pending` 에 머문다. 지운 볼륨이 "쓰던 것"으로 표시돼 새로 묶이지 않기 때문이다.

```bash
# (DB 를 둔 워커에서)  sudo rm -rf /var/lib/vet-mysql/mysql
kubectl delete pv vet-mysql
kubectl apply -f gitops/cluster/kubeadm/
```

그다음 5-6 부터 다시 한다.

> **내 PC 에서 먼저 연습하려면.** Docker Desktop 의 쿠버네티스가 있으면 5-5 ~ 5-9 를 비용 없이 해 볼 수 있다. 다른 점은 세 가지다. `overlays/kubeadm` 대신 `overlays/local` 을 쓴다. 주소가 `http://localhost` 다. 5-5 의 폴더는 `docker exec desktop-control-plane mkdir -p /var/lib/vet-mysql` 로 만들고 노드 이름은 `desktop-control-plane` 이다.

# 6장. EKS 에 올린다

**이 장의 명령은 실행해 보지 않았다.** AWS 문서와 배포 파일을 보고 적었다. 클러스터를 만드는 방법은 수업에서 배운 것을 우선한다.

5장과 무엇이 다른가:

| | 5장 (직접 만든 클러스터) | 6장 (EKS) |
|---|---|---|
| 클러스터 | EC2 에 직접 설치 | 명령 하나로 만들어진다 |
| 이미지 | 공개 레지스트리 | ECR (AWS 의 레지스트리) |
| 밖으로 여는 법 | NodePort 30080 | ALB (로드밸런서) |
| DB 의 볼륨 | 워커의 폴더를 직접 등록 | EBS 가 자동으로 만들어진다 |

앱의 YAML(`base/`)은 그대로다. 위 네 가지만 `overlays/eks/` 에 다르게 적혀 있다.

```bash
diff -r gitops/apps/vet/overlays/kubeadm gitops/apps/vet/overlays/eks      # 차이를 직접 본다
```

## 6-1. 준비

내 PC 의 WSL 에서 한다.

```bash
aws sts get-caller-identity --query Arn --output text      # 로그인 확인
REGION=ap-northeast-2
REG=$(aws sts get-caller-identity --query Account --output text).dkr.ecr.$REGION.amazonaws.com
```

`$REG` 는 ECR 의 주소다. **AWS 계정 번호가 들어 있다.** `echo $REG` 의 출력이나 그것이 보이는 화면은 문서에 그대로 올리지 않는다.

## 6-2. 이미지를 ECR 로 옮긴다

```bash
# 저장소를 만든다. 이미지 하나에 저장소 하나다
for r in vet-web vet-auth vet-clinic vet-reservation vet-db; do
  aws ecr create-repository --region $REGION --repository-name $r --query repository.repositoryName --output text
done

# 로그인한다. 임시 비밀번호가 화면에 나오지 않고 docker 로 바로 넘어간다
aws ecr get-login-password --region $REGION | docker login --username AWS --password-stdin $REG

# 4장과 같다. 이름 앞의 주소만 ECR 로 바뀐다
for i in vet-auth:1.0.0 vet-clinic:1.0.0 vet-reservation:1.0.0 vet-db:1.0.0 vet-web:1.0.0-apache; do
  docker tag $i $REG/$i && docker push $REG/$i
done

# 올라갔는지 본다
aws ecr describe-images --region $REGION --repository-name vet-auth --query 'imageDetails[].imageTags[]' --output text
```

4장과 하는 일이 같다. `docker tag` 로 이름을 붙이고 `docker push` 로 올린다.

## 6-3. 클러스터를 만든다

수업의 방법으로 만든다. 참고로 `eksctl` 로는 이렇다(AWS 문서). 15 ~ 20분 걸린다.

```bash
eksctl create cluster --name=vet --region=$REGION --enable-auto-mode
aws eks update-kubeconfig --name vet --region $REGION
kubectl get nodes
```

`kubectl get nodes` 가 비어 있어도 정상이다. EKS Auto Mode 는 Pod 가 생길 때 그에 맞춰 EC2 를 만든다. 5장에서는 EC2 3대를 먼저 만들고 그 위에 올렸다. 여기서는 올리면 EC2 가 생긴다.

## 6-4. 클러스터에 한 번 준비한다

```bash
kubectl apply -f gitops/cluster/eks/
kubectl get sc,ingressclass
```

두 가지를 만든다.

| 이름 | 하는 일 |
|---|---|
| StorageClass `vet-ebs` | "볼륨을 달라고 하면 EBS 를 만들어 붙여라". 5-5 에서 손으로 하던 일을 대신한다 |
| IngressClass `vet-alb` | "Ingress 를 만들면 ALB 를 만들어라" |

네임스페이스와 Secret 은 5-6 과 똑같이 만든다.

## 6-5. 적용한다

```bash
kubectl kustomize gitops/apps/vet/overlays/eks | sed "s|ECR_REGISTRY/|$REG/|g" > vet-eks.yaml
grep 'image:' vet-eks.yaml | sed -E 's/[0-9]{12}/************/'       # 주소가 채워졌는지 (계정 번호는 가려서)
kubectl apply -f vet-eks.yaml
```

`sed` 가 하는 일: 배포 파일에는 이미지 주소가 `ECR_REGISTRY/vet-auth` 라고 자리 표시로 적혀 있다. 계정 번호를 Git 에 올리지 않으려는 것이다. 이 명령이 그 자리를 실제 주소로 바꾼다. **`vet-eks.yaml` 에는 계정 번호가 들어 있으니 Git 에 올리지 않는다.**

```bash
kubectl -n vet get pods -o wide -w
```

처음 1 ~ 2분은 `Pending` 이다. EC2 가 만들어지는 중이다.

```bash
kubectl get nodes -L topology.kubernetes.io/zone       # 만들어진 EC2 와 가용 영역
kubectl -n vet get pvc,pv                              # mysql-data 가 Bound. EBS 볼륨이 생겼다
kubectl -n vet get ingress web                         # ADDRESS 에 ALB 의 주소 (몇 분 걸린다)
```

## 6-6. 확인한다

```bash
ALB=$(kubectl -n vet get ingress web -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
curl -s -o /dev/null -w '%{http_code}\n' http://$ALB/health
AUTH=http://$ALB; CLINIC=$AUTH; RES=$AUTH
```

`200` 이 나오면 0장의 "동작을 확인하는 법"을 한다. 그리고 5-9(자동 복구, 롤링 업데이트와 롤백, 데이터 유지)를 주소만 `http://$ALB` 로 바꿔 그대로 한다.

5장과 견줘 볼 것: 포트 번호(30080)가 없어졌고, 주소가 서버의 IP 가 아니라 ALB 의 이름이다. 서버 하나가 죽어도 주소가 바뀌지 않는다.

## 6-7. 지운다

**순서가 중요하다.** ALB 와 EBS 볼륨은 클러스터가 만든 것이다. 클러스터를 먼저 지우면 둘이 주인 없이 남아 요금이 계속 나온다.

```bash
# 1) 앱을 지운다. ALB 와 EBS 볼륨이 함께 지워진다
kubectl delete -f vet-eks.yaml
kubectl -n vet get ingress,pvc 2>&1        # 없다고 나올 때까지 기다린다
kubectl get pv

# 2) 6-4 에서 만든 것
kubectl delete -f gitops/cluster/eks/

# 3) 클러스터 (만든 방법으로 지운다)
eksctl delete cluster --name=vet --region=$REGION

# 4) ECR 저장소
for r in vet-web vet-auth vet-clinic vet-reservation vet-db; do
  aws ecr delete-repository --region $REGION --repository-name $r --force --query repository.repositoryName --output text
done

rm -f vet-eks.yaml
```

## 6-8. 남은 것이 없는지 본다

요금이 나오는 것을 하나씩 조회한다. 전부 비어 있어야 한다. 출력에 계정 번호가 섞여 나오면 가린다.

```bash
aws eks list-clusters --region $REGION --query 'clusters[]' --output text
aws ec2 describe-instances --region $REGION --filters 'Name=instance-state-name,Values=pending,running,stopping,stopped' \
  --query 'Reservations[].Instances[].[InstanceId,InstanceType,State.Name]' --output text
aws elbv2 describe-load-balancers --region $REGION --query 'LoadBalancers[].[LoadBalancerName,Type]' --output text
aws ec2 describe-nat-gateways --region $REGION --filter 'Name=state,Values=pending,available' --query 'NatGateways[].NatGatewayId' --output text
aws ec2 describe-addresses --region $REGION --query 'Addresses[].PublicIp' --output text
aws ec2 describe-volumes --region $REGION --query 'Volumes[].[VolumeId,Size,State]' --output text
aws ecr describe-repositories --region $REGION --query 'repositories[].repositoryName' --output text
```

5장의 EC2 3대도 여기서 보인다. 다 썼으면 종료한다.
