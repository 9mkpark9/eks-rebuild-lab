# 직접 해 보기 — 스크립트 없이 ① ~ ④

`scripts/` 의 스크립트는 아래 명령을 묶어 둔 것이다. 이 문서는 그 명령을 하나씩 직접 치는 순서다. 무엇이 어떻게 뜨는지 손으로 확인하고 싶을 때 쓴다.

- 쓰는 도구는 `git`, `java`, `docker`, `curl`, `kubectl`, `aws` 뿐이다.
- 비밀번호는 연습용으로 직접 정한 값을 쓴다(① ②). 내 PC 안에서만 쓰고 끝나면 지운다. 쿠버네티스(③ ④)에서는 무작위 값을 만들어 넣는다.
- `<…>` 는 직접 채우는 값이다.
- ① ② ③ 의 순서는 2026년 11월 17일에 그대로 실행해 확인했다(① ② 는 WSL 2 Ubuntu, ③ 은 내 PC 의 클러스터). **④ 는 실행해 보지 않았다.**

| 스크립트 | 이 문서에서 대신하는 명령 |
|---|---|
| `run-app.sh` | `./gradlew build`, `docker run`(MySQL, Redis), `java -jar` 3번 |
| `new-env.sh`, `docker compose` | `docker build` 5번, `docker network create`, `docker run` 6번 |
| `smoke.sh` | `curl` 로 로그인 → 조회 → 등록 → 조회 → 수정 |
| `push-images.sh` | `docker tag`, `docker push`, (ECR) `aws ecr …` |
| `new-k8s-secrets.sh` | `kubectl create secret generic` |
| `test-k8s-ops.sh` | `kubectl set env`, `rollout status / history / undo`, `delete pod`, `curl` 반복 |
| `eks-apply.sh` | `kubectl kustomize … \| sed … \| kubectl apply -f -` |
| `aws-leftovers.sh` | `aws … describe-…` 로 남은 자원 조회 |

# 공통: curl 로 하는 테스트 시나리오

단계마다 주소만 바뀐다. 아래에서 `$AUTH`, `$CLINIC`, `$RES` 를 단계에 맞게 정한다.

| 단계 | 정하는 값 |
|---|---|
| ① (서비스에 직접) | `AUTH=http://127.0.0.1:18081 CLINIC=http://127.0.0.1:18082 RES=http://127.0.0.1:18083` |
| ② ③ ④ (웹 서버를 거침) | 셋 다 같은 주소. 예: `AUTH=http://localhost:8088; CLINIC=$AUTH; RES=$AUTH` |

```bash
# 로그인 (쿠키를 파일에 받는다)
curl -s -c cookie.txt -H 'Content-Type: application/json' \
  -d '{"loginId":"owner001","password":"test-only"}' $AUTH/api/auth/login

# 조회: 반려동물, 예약 가능한 시간
curl -s -b cookie.txt $CLINIC/api/pets
curl -s -b cookie.txt "$CLINIC/api/slots?date=$(date -d '+2 day' +%F)&type=GENERAL"

# 등록: 위에서 고른 slotId 로 예약한다 → 201 과 reservationId
curl -s -b cookie.txt -H 'Content-Type: application/json' \
  -d '{"petId":1,"slotId":<slotId>}' -w '\nHTTP %{http_code}\n' $RES/api/reservations

# 조회: 방금 만든 예약이 REQUESTED
curl -s -b cookie.txt $RES/api/reservations/me

# 수정 1: 간호사가 승인 → CONFIRMED
curl -s -c nurse.txt -H 'Content-Type: application/json' \
  -d '{"loginId":"admin1","password":"test-only"}' $AUTH/api/auth/login
curl -s -b nurse.txt -X POST $RES/api/admin/reservations/<예약 번호>/approve

# 수정 2: 보호자가 취소 → 204
curl -s -b cookie.txt -X DELETE -w 'HTTP %{http_code}\n' $RES/api/reservations/<예약 번호>
```

- 빈 시간 조회가 `[]` 면 그날이 일요일(휴진)이다. `+3 day` 로 바꾼다.
- 같은 반려동물로 같은 날 두 번 예약하면 `409` 가 나온다. 정상이다. 다른 날짜나 `petId: 2` 로 한다.
- 로그인은 auth 가, 반려동물과 시간은 clinic 이, 예약은 reservation 이 처리한다. auth 에서 받은 쿠키를 다른 서비스가 알아보는 것은 세션이 Redis 에 있기 때문이다.


# ② 이미지 빌드 · 컨테이너 테스트 (WSL 2 Ubuntu)

## 이미지를 하나씩 만든다

서비스 이미지는 `msa/` 를, web 과 db 는 저장소 맨 위(`.`)를 빌드 위치로 준다. 마지막 인자가 빌드 위치다.

```bash
docker build -f msa/auth-service/Dockerfile        --build-arg VERSION=1.0.0 -t vet-auth:1.0.0 msa
docker build -f msa/clinic-service/Dockerfile      --build-arg VERSION=1.0.0 -t vet-clinic:1.0.0 msa
docker build -f msa/reservation-service/Dockerfile --build-arg VERSION=1.0.0 -t vet-reservation:1.0.0 msa
docker build -f msa/web/Dockerfile.apache --build-arg VERSION=1.0.0-apache -t vet-web:1.0.0-apache .
docker build -f msa/db/Dockerfile -t vet-db:1.0.0 .

docker image ls | grep vet-
docker image inspect vet-auth:1.0.0 --format '{{.Os}}/{{.Architecture}}'      # linux/amd64
```

nginx 판은 `-f msa/web/Dockerfile.nginx --build-arg VERSION=1.0.0-nginx -t vet-web:1.0.0-nginx` 다.

소스 한 줄을 고치고 같은 명령을 다시 치면 대부분의 단계가 `CACHED` 로 지나간다. Dockerfile 이 의존성을 받는 단계와 소스를 복사하는 단계를 나눠 두었기 때문이다.

## 네트워크와 컨테이너 6개

컨테이너끼리 이름으로 찾게 하려고 네트워크를 하나 만든다. `--network-alias` 가 그 네트워크 안에서 불리는 이름이다. 서비스는 DB 를 `mysql`, Redis 를 `redis` 라는 이름으로 찾고, web 은 서비스를 `auth`, `clinic`, `reservation` 으로 찾는다.

```bash
docker network create vet-net

docker run -d --name vet-mysql --network vet-net --network-alias mysql \
  -e MYSQL_ROOT_PASSWORD=rootpw1234 -e VET_AUTH_PASSWORD=authpw1234 \
  -e VET_CLINIC_PASSWORD=clinicpw1234 -e VET_RESERVATION_PASSWORD=respw1234 vet-db:1.0.0

docker run -d --name vet-redis --network vet-net --network-alias redis \
  redis:7-alpine redis-server --requirepass redispw1234

docker run -d --name vet-auth --network vet-net --network-alias auth \
  -e SPRING_DATASOURCE_URL='jdbc:mysql://mysql:3306/vet_auth?connectionTimeZone=LOCAL&characterEncoding=UTF-8' \
  -e SPRING_DATASOURCE_USERNAME=vet_auth -e SPRING_DATASOURCE_PASSWORD=authpw1234 \
  -e SPRING_DATA_REDIS_HOST=redis -e SPRING_DATA_REDIS_PASSWORD=redispw1234 \
  -e REDIS_TLS=false -e DB_POOL_MAX=5 vet-auth:1.0.0

docker run -d --name vet-clinic --network vet-net --network-alias clinic \
  -e SPRING_DATASOURCE_URL='jdbc:mysql://mysql:3306/vet_clinic?connectionTimeZone=LOCAL&characterEncoding=UTF-8' \
  -e SPRING_DATASOURCE_USERNAME=vet_clinic -e SPRING_DATASOURCE_PASSWORD=clinicpw1234 \
  -e SPRING_DATA_REDIS_HOST=redis -e SPRING_DATA_REDIS_PASSWORD=redispw1234 \
  -e REDIS_TLS=false -e DB_POOL_MAX=5 vet-clinic:1.0.0

docker run -d --name vet-reservation --network vet-net --network-alias reservation \
  -e SPRING_DATASOURCE_URL='jdbc:mysql://mysql:3306/vet_reservation?connectionTimeZone=LOCAL&characterEncoding=UTF-8' \
  -e SPRING_DATASOURCE_USERNAME=vet_reservation -e SPRING_DATASOURCE_PASSWORD=respw1234 \
  -e SPRING_DATA_REDIS_HOST=redis -e SPRING_DATA_REDIS_PASSWORD=redispw1234 \
  -e REDIS_TLS=false -e DB_POOL_MAX=5 vet-reservation:1.0.0

# 밖으로 여는 것은 web 하나다 (-p)
docker run -d --name vet-web --network vet-net -p 8088:8080 vet-web:1.0.0-apache
```

①과 같은 환경 변수이고 주소만 `127.0.0.1` 에서 컨테이너의 이름으로 바뀌었다. 포트를 연 것은 web 뿐이라 서비스와 DB 는 밖에서 접속할 수 없다.


# ③ Kubernetes 전환 (EC2, kubeadm)

## 네임스페이스와 Secret

비밀번호를 무작위로 만들어 바로 넣는다. 화면에 값이 나오지 않는다.

```bash
kubectl create namespace vet

kubectl -n vet create secret generic vet-db \
  --from-literal=root-password="$(openssl rand -hex 18)" \
  --from-literal=auth-password="$(openssl rand -hex 18)" \
  --from-literal=clinic-password="$(openssl rand -hex 18)" \
  --from-literal=reservation-password="$(openssl rand -hex 18)"

kubectl -n vet create secret generic vet-redis --from-literal=password="$(openssl rand -hex 18)"

kubectl -n vet describe secret vet-db        # 키 이름과 바이트 수만 나온다
```

`kubectl get secret -o yaml` 은 값을 base64 로 보여 주므로 화면을 남길 때 쓰지 않는다.

## 배포

```bash

kubectl apply -k gitops/apps/vet/overlays/kubeadm
kubectl -n vet get pods -o wide -w
```

네임스페이스를 먼저 만들었기 때문에 `namespace/vet configured` 와 함께 경고가 한 줄 나온다. 문제없다.

```bash
kubectl -n vet get deploy,sts

kubectl -n vet describe deploy auth                   # Liveness, Readiness, Startup, RollingUpdateStrategy
```

## 롤링 업데이트와 롤백

터미널을 하나 더 열어 요청을 계속 보내 둔다. 끝나면 응답 코드별 개수가 나온다.

```bash
# 터미널 A — 75초 동안 0.2초마다 요청한다
for i in $(seq 1 300); do curl -s -m 3 -o /dev/null -w '%{http_code}\n' http://localhost:30080/api/status/clinic; sleep 0.2; done | sort | uniq -c
```

```bash
# 터미널 B — 버전을 바꾼다. Pod 가 하나씩 새것으로 바뀐다
curl -s http://localhost:30080/api/status/clinic                 # "version":"1.0.0"
kubectl -n vet set env deployment/clinic APP_VERSION=1.0.1
kubectl -n vet rollout status deployment/clinic
curl -s http://localhost:30080/api/status/clinic                 # "version":"1.0.1"

# 되돌린다
kubectl -n vet rollout history deployment/clinic
kubectl -n vet rollout undo deployment/clinic
kubectl -n vet rollout status deployment/clinic
curl -s http://localhost:30080/api/status/clinic                 # "version":"1.0.0"
```

터미널 A 의 결과가 `200` 한 줄이면 배포하는 동안 실패한 요청이 없는 것이다. `rollout undo` 뒤에 경고가 한 줄 나오는데, 되돌린 상태가 `kubectl apply` 의 기록과 달라졌다는 뜻이다. 나중에 `kubectl apply -k` 를 다시 하면 배포 파일의 상태로 맞춰진다.

**무중단이 아닐 때와 비교하려면** reservation 을 "전부 내리고 다시 띄우는" 방식으로 바꿔 같은 일을 해 본다. 끝나면 원래대로 돌린다.

```bash
kubectl -n vet patch deployment reservation --type merge -p '{"spec":{"strategy":{"type":"Recreate","rollingUpdate":null}}}'
# 터미널 A 의 반복을 /api/status/reservation 으로 돌리면서
kubectl -n vet rollout restart deployment/reservation
kubectl -n vet patch deployment reservation --type merge -p '{"spec":{"strategy":{"type":"RollingUpdate","rollingUpdate":{"maxSurge":1,"maxUnavailable":0}}}}'
```

```bash
# 예약을 하나 만들어 두고 (공통 시나리오의 "등록"까지), 번호를 적어 둔다
kubectl -n vet get pod mysql-0 -o jsonpath='{.metadata.creationTimestamp}{"\n"}'
```

MySQL Pod 는 다시 떠도 이름이 `mysql-0` 그대로다(StatefulSet). 새것인지는 만든 시각으로 본다.

미리 확인한 결과(내 PC 의 클러스터, `overlays/local`): Pod 10개가 뜨고, 버전이 `1.0.0` → `1.0.1` → `1.0.0` 으로 바뀌는 75초 동안 요청 250건 중 실패 0건, auth Pod 하나를 지우면 12초 안에 새 Pod 가 `Running`, `mysql-0` 을 지운 뒤에도 예약 176번이 `REQUESTED` 로 남아 있었다. EC2 에서는 실행하지 않았다.

# ④ EKS 전환

**이 절의 명령은 실행해 보지 않았다.** AWS 문서와 배포 파일을 보고 적었다. 클러스터는 수업의 방법으로 만든다.

`$REG` 에는 AWS 계정 번호가 들어 있다. `echo $REG` 의 출력이나 그것이 보이는 화면을 문서에 그대로 올리지 않는다.

## 이미지를 ECR 로 옮긴다

```bash
REGION=ap-northeast-2
REG=$(aws sts get-caller-identity --query Account --output text).dkr.ecr.$REGION.amazonaws.com

# 저장소를 만든다
for r in vet-web vet-auth vet-clinic vet-reservation vet-db; do
  aws ecr create-repository --region $REGION --repository-name $r --query repository.repositoryName --output text
done

# 로그인 (토큰이 화면에 나오지 않고 docker 로 바로 넘어간다)
aws ecr get-login-password --region $REGION | docker login --username AWS --password-stdin $REG

# 태그를 붙이고 올린다
for i in vet-auth:1.0.0 vet-clinic:1.0.0 vet-reservation:1.0.0 vet-db:1.0.0 vet-web:1.0.0-apache; do
  docker tag $i $REG/$i && docker push $REG/$i
done

aws ecr describe-images --region $REGION --repository-name vet-auth --query 'imageDetails[].imageTags[]' --output text
```

## 클러스터 준비

```bash
kubectl get nodes                          # Auto Mode 는 Pod 가 생길 때 노드를 만든다. 처음에는 비어 있을 수 있다
kubectl apply -f gitops/cluster/eks/       # StorageClass(vet-ebs), IngressClass(vet-alb)
kubectl get sc,ingressclass
```

네임스페이스와 Secret 은 ③과 똑같이 만든다.

## 배포

배포 파일의 이미지 주소는 `ECR_REGISTRY/vet-auth` 처럼 자리 표시로 되어 있다. 적용할 때 실제 주소로 바꿔 넣는다.

```bash
kubectl kustomize gitops/apps/vet/overlays/eks | sed "s|ECR_REGISTRY/|$REG/|g" | kubectl apply -f -

kubectl -n vet get pods -o wide -w                              # 노드가 만들어지는 동안 Pending (1~2분)
kubectl get nodes -L topology.kubernetes.io/zone
kubectl -n vet get pvc,pv                                       # EBS 볼륨이 만들어져 Bound
kubectl -n vet get ingress web                                  # ADDRESS 에 ALB 주소 (몇 분 걸린다)
```

`kubectl apply -k` 를 그대로 쓰면 주소가 바뀌지 않아 `ImagePullBackOff` 가 된다.

## 테스트

```bash
ALB=$(kubectl -n vet get ingress web -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
curl -s -o /dev/null -w '%{http_code}\n' http://$ALB/health
AUTH=http://$ALB; CLINIC=$AUTH; RES=$AUTH
```

## 지운다

순서를 지킨다. 클러스터를 먼저 지우면 ALB 와 EBS 가 남는다.

```bash
# 1) 앱. Ingress 가 지워지며 ALB 가, PVC 가 지워지며 EBS 볼륨이 함께 지워진다
kubectl kustomize gitops/apps/vet/overlays/eks | sed "s|ECR_REGISTRY/|$REG/|g" | kubectl delete -f -
kubectl -n vet get ingress,pvc 2>&1          # 없다고 나올 때까지 기다린다
kubectl get pv

# 2) 클러스터 준비물
kubectl delete -f gitops/cluster/eks/

# 3) 클러스터를 지운다 (만든 방법으로)

# 4) ECR 저장소
for r in vet-web vet-auth vet-clinic vet-reservation vet-db; do
  aws ecr delete-repository --region $REGION --repository-name $r --force --query repository.repositoryName --output text
done
```

## 남은 자원이 없는지 본다

하나씩 조회해 전부 비어 있는지 확인한다. 출력에 계정 번호가 섞여 나오는 것(ARN)은 가린다.

```bash
aws eks list-clusters --region $REGION --query 'clusters[]' --output text
aws ec2 describe-instances --region $REGION --filters 'Name=instance-state-name,Values=pending,running,stopping,stopped' \
  --query 'Reservations[].Instances[].[InstanceId,InstanceType,State.Name]' --output text
aws elbv2 describe-load-balancers --region $REGION --query 'LoadBalancers[].[LoadBalancerName,Type]' --output text
aws ec2 describe-nat-gateways --region $REGION --filter 'Name=state,Values=pending,available' --query 'NatGateways[].NatGatewayId' --output text
aws ec2 describe-addresses --region $REGION --query 'Addresses[].PublicIp' --output text
aws ec2 describe-volumes --region $REGION --query 'Volumes[].[VolumeId,Size,State]' --output text
aws ecr describe-repositories --region $REGION --query 'repositories[].repositoryName' --output text
```

③의 EC2 3대도 여기서 보인다. 다 썼으면 종료한다.
