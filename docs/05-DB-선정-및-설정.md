# DB 선정 및 설정

- 대상: 예약 데이터베이스(RDS for MySQL), 로그인 세션 저장소(ElastiCache), DB 초기화용 관리 EC2
- 작성일: 2026-10-19
- 정의 위치: `cfn/data.yaml` (스택 `vet01-data`), 스키마 `db/schema.sql`, 시드 생성 `db/gen-seed.mjs`, 초기화 `db/init.sh`

> 이 DB에 들어 있는 데이터는 모두 임시(가짜) 데이터다. 보호자 300명의 이름은 무작위 조합이고 연락처는 010-0000-XXXX다. 반려동물·예약·공지도 시드 생성기가 만든 값이다. 테스트 계정의 비밀번호는 공통 테스트 값이며 DB에는 BCrypt 해시만 저장된다.

### 4.1 후보 (서울, MySQL, 2026-10-19 Pricing API 조회)

| 후보 | vCPU · 메모리 | Single-AZ 시간당 | Multi-AZ 시간당 | 기본 연결 한도 | 검토 |
| --- | --- | --- | --- | --- | --- |
| db.t3.micro | 2 · 1 GiB | 0.026달러 | 0.052달러 | 약 60 (문서 8장) | 필요 조건 57 이상을 겨우 넘어 여유가 없다 |
| **db.t3.small** | 2 · 2 GiB | 0.052달러 | **0.104달러** | **144 (실측)** | **채택** |
| db.t4g.small | 2 · 2 GiB (Arm) | 0.051달러 | 0.102달러 | db.t3.small과 비슷 | 비용 차이 미미(시간당 0.002달러). 다음 고객사에서 비교 가능 |
| db.t3.medium | 2 · 4 GiB | 0.104달러 | 0.208달러 | 더 큼 | 2배 비용. 테스트 결과 DB CPU·메모리가 부족할 때만 |

### 4.2 연결 수 계산 (8장)

| 항목 | 값 |
| --- | --- |
| WAS 연결 풀 (인스턴스당) | 10개 (HikariCP `maximum-pool-size`) |
| WAS 최대 대수 × 풀 | 4 × 10 = 40개 |
| 관리·모니터링 접속 여유 | 5개 |
| 최대 사용량 | 45개 |
| 필요한 `max_connections` | 45 ÷ 0.8 ≈ 57개 이상 (최대 사용량이 한도의 80% 이하) |
| db.t3.small 실측 `max_connections` | **144** (DB 초기화 때 `SHOW GLOBAL VARIABLES`로 확인) |
| 사용률 (최대 45 기준) | 약 31% |

평균 필요량은 「DB를 쓰는 요청 수/초 × 요청당 DB 사용 시간」이다. 140명에서 RPS 약 30, 그중 절반이 DB를 쓰고 요청당 20ms라고 가정하면 15 × 0.02 = 0.3개다. 순간 몰림을 감안해도 WAS 1대당 풀 10개면 충분하다. 가정값은 TC-02 실측(RPS, DB 쿼리 시간)으로 바꿔 다시 계산한다. ASG 최대 대수를 늘리면 이 표를 다시 계산한다.

### 4.3 선정 이유 요약

- db.t3.micro는 연결 한도 여유가 없다. 메모리가 1 GiB라 InnoDB 버퍼 풀도 매우 작다.
- db.t3.small은 한도 144로 필요량(57)의 2.5배다. 슬롯·예약 데이터 전체(수 MB)가 버퍼 풀에 다 들어간다.
- T 계열은 기본이 unlimited 모드라 테스트 중 CPU가 묶이지 않는다. RDS CPU 경보(80%)로 지속 부하를 감시한다.

## 5. 가용성 구성: Multi-AZ (인스턴스 배포)

| 옵션 | 구성 | 장애 조치 | 비용 | 판단 |
| --- | --- | --- | --- | --- |
| Single-AZ | 1대 | 수동 복구·재생성 | 1배 | 제외. 문서가 테스트에서도 Multi-AZ로 TC-06 ③을 확인하라고 한다 |
| **Multi-AZ 인스턴스 배포** | 주 1대 + 대기 1대(동기 복제, 읽기 불가) | 자동 전환, 보통 60~120초 | 2배 | **채택** |
| Multi-AZ DB 클러스터 | 주 1대 + 읽기 가능한 대기 2대 | 더 빠름 | 약 3배 | 제외. 읽기 확장이 필요 없다 |

실제 배치: **주 인스턴스 `ap-northeast-2c`, 대기 인스턴스 `ap-northeast-2a`**. AZ는 RDS가 서브넷 그룹(db-a, db-c) 안에서 정했다.

장애 조치 때 RDS 엔드포인트의 DNS 레코드가 대기 인스턴스로 바뀐다. 기존 연결은 끊긴다. WAS는 JVM DNS 캐시 TTL을 60초로 두어 새 주소를 따라간다. HikariCP는 끊긴 연결을 버리고 새로 맺는다.

## 7. DB 계정과 권한

| 계정 | 권한 | 비밀 위치 | 사용처 |
| --- | --- | --- | --- |
| `admin` (마스터) | 전체 | Secrets Manager `rds!db-...` (RDS 관리) | 관리 EC2에서 스키마·시드·초기화·검증 SQL만 |
| `vet_app` (앱 전용) | `SELECT, INSERT, UPDATE ON vet.*` + `DELETE ON vet.notices` | Secrets Manager `vet01/db/app` (CloudFormation이 24자 생성) | WAS |

WAS는 마스터 계정을 쓰지 않는다. 앱에 문제가 생겨도 테이블을 지우거나 구조를 바꿀 수 없다(10.3장). 문서는 SELECT·INSERT·UPDATE만 주라고 했다. 간호사 화면의 공지 삭제 기능 때문에 `notices` 테이블에만 DELETE를 더했다. 예약·슬롯은 삭제하지 않고 상태만 바꾼다(취소 = `status = 'CANCELLED'`).

## 8. 스키마 (`db/schema.sql`)

| 테이블 | 주요 열 | 제약·인덱스 | 이유 |
| --- | --- | --- | --- |
| `vets` | vet_id, name, title, field | PK | 수의사 3명 |
| `users` | user_id, login_id, password_hash(BCrypt), name, role(OWNER·NURSE·DIRECTOR), phone, vet_id | `uq_login`, FK vet_id | 보호자·간호사·원장. 원장은 vet_id로 수의사와 연결 |
| `pets` | pet_id, owner_id, name, species, age | FK owner_id, `ix_owner` | 보호자 1 : 반려동물 N |
| `slots` | slot_id, vet_id, start_at, visit_type, is_event, is_open, reservation_id | `uq_vet_time(vet_id, start_at)`, `uq_resv(reservation_id)`, `ix_avail(start_at, visit_type, reservation_id)` | 슬롯마다 행 하나. 같은 수의사·같은 시각은 하나. 예약 1건이 슬롯 2개를 잡지 못함(NULL은 여러 개 허용) |
| `reservations` | reservation_id, owner_id, pet_id, slot_id, visit_date, status, served_by, created_at, active_pet_day(저장 생성 열) | `uq_pet_day(active_pet_day)`, `ix_visit(visit_date, status)` | 활성 예약일 때만 `pet_id|visit_date` 값이 생겨 같은 반려동물·같은 날 1건으로 제한. 취소되면 NULL이 되어 제약에서 빠짐 |
| `notices` | notice_id, category(NOTICE·EVENT·CLOSED), title, content, pinned, created_at | `ix_created` | 소개 페이지 공지 |

예약 판정 SQL (6장)
- 신청: `INSERT reservations`(uq_pet_day 위반 → 409 PET_SAME_DAY) → `UPDATE slots ... WHERE slot_id=? AND reservation_id IS NULL AND is_open=1`(0행 → 409 SLOT_TAKEN, INSERT까지 롤백)
- 변경: 내 예약 행 `FOR UPDATE` → 기존 슬롯 비우기 → 새 슬롯 조건부 확보(실패 시 전체 롤백) → 예약 행 갱신
- 격리 수준은 InnoDB 기본 REPEATABLE READ 그대로. 조건부 UPDATE는 최신 커밋 값을 잠그고 읽으므로 바꾸지 않아도 판정이 맞다.

WAS의 슬롯 채우기 작업(`SlotGenerator`)은 매일 00:05와 기동 시에 오늘부터 14일의 슬롯을 `INSERT IGNORE`로 채운다. WAS가 여러 대여도 `uq_vet_time` 덕분에 중복이 생기지 않는다.

## 10. DB 초기화 절차와 결과

관리 EC2(`vet01-ops`, `i-05cd5a8fa3f04bf9d`, t3.micro, app-a 서브넷)에서 Session Manager 명령으로 실행했다(`bash deploy/aws.sh dbinit`).

1. RDS 엔드포인트와 마스터 비밀 ARN 조회
2. Secrets Manager에서 마스터·앱 계정 비밀을 읽어 환경 변수로만 사용
3. S3 `db/`에서 `schema.sql`, `seed.sql` 다운로드
4. `CREATE DATABASE vet` → 스키마 → 시드
5. `vet_app` 계정 생성·권한 부여
6. 검증 출력

| 확인 | 결과 |
| --- | --- |
| `max_connections` | 144 |
| slots / reservations / users / notices | 576 / 171 / 305 / 5 |
| `@@time_zone`, `NOW()` | Asia/Seoul, 2026-10-19 15:57:33 |

관리 EC2를 t3.micro로 고른 이유: mysql 클라이언트로 SQL 파일을 실행하는 일만 한다. 가장 작은 범용 사양(2 vCPU · 1 GiB, 시간당 0.013달러)으로 충분하다. RDS가 VPC 밖에서 닿지 않으므로 VPC 안에 이런 작업 지점이 하나 필요하다. 인바운드 규칙은 없다.

## 11. 세션 저장소: ElastiCache 선정 및 설정

### 11.1 비교

| 후보 | 검토 결과 |
| --- | --- |
| **ElastiCache for Redis OSS 7.1 (노드 기반)** | **채택.** Spring Session이 그대로 지원한다. 문자열 카운터(로그인 시도 제한)도 같은 저장소에 둔다 |
| ElastiCache for Valkey | Redis 호환이고 노드 요금이 더 낮게 책정되어 있다. 다음 고객사에서 전환 후보. 문서가 「Valkey 또는 Redis OSS」라고 한 범위 안이다 |
| ElastiCache Memcached | 제외. 영속성·복제가 없고 카운터 만료 처리 등 기능이 부족하다 |
| ElastiCache Serverless | 제외. 최소 사용량 요금이 노드 1개보다 크다 |
| DB 세션 테이블 | 제외. 매 요청 세션 조회가 RDS에 몰려 예약 판정과 자원을 다툰다 |
| ALB 고정 세션 | 제외. 분산이 치우치고, WAS 1대가 죽으면 그 세션이 모두 끊긴다 |
| JWT | 제외. 관리자 계정 정지·강제 로그아웃을 즉시 반영하기 어렵다(3.1장) |

## 13. 모니터링·백업·검증 계획

| 항목 | 설정·방법 | 기준 |
| --- | --- | --- |
| 경보 `vet01-db-cpu` | RDS `CPUUtilization` 평균, 3분 연속 | 80% 이상이면 경보 |
| 경보 `vet01-db-connections` | RDS `DatabaseConnections` 최대 | 45 이상이면 경보 |
| 대시보드 | RDS CPU, `DatabaseConnections`, `FreeableMemory` | TC-04 20분 동안 메모리가 계속 줄지 않음 |
| 정합성 (TC-07) | 관리 EC2에서 검증 SQL 4개 (같은 슬롯 활성 2건↑, 같은 반려동물·같은 날 활성 2건↑, 채워진 슬롯 수 = 활성 예약 수, WAS별 처리 건수) | 앞의 둘은 0행, 셋째는 두 값 일치 |
| DB 장애 조치 (TC-06 ③) | `aws rds reboot-db-instance --db-instance-identifier vet01-db --force-failover` | 전환(보통 60~120초) 동안의 오류는 허용하고 시간 기록. 전환 후 WAS 재시작 없이 2분 안에 오류 0, 직후 TC-07 통과 |
| 테스트 사이 초기화 | `UPDATE slots SET reservation_id = NULL; TRUNCATE TABLE reservations;` (마스터 계정) | 슬롯 576개가 모두 빈 상태 |
| 백업 | 자동 백업 7일, 각 테스트 전후 수동 스냅샷, 스냅샷 복원 1회 확인 | 복원한 인스턴스에서 예약 데이터 확인 |
