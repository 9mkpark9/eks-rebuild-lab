### 3.2 보호자 화면 (React SPA)

무엇을: 로그인, 보호자 홈, 온라인 예약, 내 예약, 내 반려동물.

어떻게
- TypeScript + React 19 + Vite 6으로 만들고 `base: '/app/'`로 빌드한다. nginx의 `location /app/`이 그대로 서비스한다.
- 라우터는 의존성 없이 History API로 직접 만들었다(약 50줄).
- 예약 흐름은 반려동물 → 진료 항목 → 날짜(오늘부터 14일, 일요일 휴진) → 시간(오전·오후, 마감 표시) → 담당 수의사 순서다. 오른쪽 요약 카드에서 신청하고, 모바일은 하단 고정 바에서 신청한다.
- 409 응답을 문서 6장 규칙대로 안내한다.
  - `SLOT_TAKEN`: 「방금 다른 보호자님이 예약한 시간」 → 시간 목록 새로고침
  - `PET_SAME_DAY`: 같은 반려동물·같은 날
  - `CANCELLED`, `NOT_REQUESTED`, 로그인 시도 제한 `429`
- 예약 변경이 실패하면 「기존 예약은 그대로 유지됩니다」를 함께 보여 준다(서버가 전체를 롤백하므로).
- 모든 API 응답에서 `X-Web-Node`·`X-Served-By` 헤더를 읽어 화면 하단에 표시한다. 분산을 눈으로 확인할 수 있다.

왜
- 근거 문서 3.1장: 로그인 뒤 화면이라 검색 노출이 필요 없고 상호작용이 많다. 빌드 결과가 정적 파일이라 WEB 계층이 그대로 제공한다. 타입 검사로 API 응답 형식이 바뀐 것을 빌드 때 잡는다.

### 3.3 로컬 모의 서버

무엇을: `node server/mock-server.mjs` 하나로 소개 페이지·SPA·API를 모두 띄운다. 기본 포트는 8090이다.

어떻게
- 라우팅은 nginx 설정(부록 E.3)을 그대로 흉내 낸다: `/health`, `/api/*`, `/app/*`(없으면 index.html), `/`(`$uri`, `$uri.html`, `$uri/`).
- API는 메모리에 슬롯·예약을 두고 DB 판정 규칙을 그대로 따른다. 슬롯 조건부 확보, 같은 반려동물·같은 날 1건, 변경 실패 시 전체 롤백, 승인 상태 확인이다.
- WEB·WAS 노드 이름 2개씩을 번갈아 헤더에 넣는다(ALB 라운드 로빈 흉내).

왜: AWS 없이 화면 전 흐름을 검증하기 위해서다. 실제 WAS의 API 명세 역할도 한다. WAS는 같은 경로·JSON 키·오류 코드를 낸다.

### 3.4 간호사 전용 / 원장 전용 분리

| 기능 | 간호사 (admin1·admin2) | 원장 (vet1~vet3) |
|---|:-:|:-:|
| 전체 예약 현황·승인 | O | – |
| 공지 등록·삭제 | O | – |
| 내 진료 일정 (내가 맡은 예약만) | – | O |
| 진료 시간 열기·닫기 (본인 진료만) | – | O |
| 병원 현황 (14일 통계, WAS 분산) | – | O |

어떻게: 역할을 `OWNER`·`NURSE`·`DIRECTOR` 셋으로 나누고, 원장 계정마다 수의사 ID(`vetId`)를 연결했다. API는 간호사 `/api/admin/*`, 원장 `/api/director/*`다. 서로의 화면은 「○○ 전용 화면입니다」로 막고 API는 403이다. 원장이 남의 진료 시간을 바꾸면 403이다.

왜
- 접수 데스크 업무와 진료 업무를 나누기 위해서다(담당자와 정한 「업무별로 나누기」 안).
- 간호사 API 경로를 문서의 관리자 API 경로 그대로 두었다. 계정 이름도 admin1·admin2로 유지했다. 그래서 부록 A의 Locust `AdminUser`를 고치지 않아도 된다.

### 3.5 직원 화면 디자인: ChartNote EMR

무엇을: 간호사·원장 화면을 담당자가 만든 ChartNote와 같은 EMR 모양으로 다시 만들었다.

어떻게
- ChartNote 계정을 잊어 로그인 화면 안쪽은 볼 수 없었다. 대신 공개된 스타일시트에서 디자인 시스템을 그대로 가져왔다: 색 토큰(`--emr-*`)과 부품(`.emr-panel`, `.emr-title`, `.emr-table`, `.emr-btn`, `.emr-pill`, `.emr-menu`, `.emr-tabs`, `.emr-statusbar`).
- 배치는 상단 남색 메뉴 막대 → 폴더 탭 → 요약 줄 → 「날짜 목록 | 목록 표 | 상세 패널」 3단 → 하단 상태 막대다. 상태 막대에는 접속자, WEB·WAS 인스턴스, 현재 시각을 보여 준다.
- 처음 12.5px였던 글자를 담당자 요청으로 14.5px(표 14px)로 키웠다. 버튼·입력칸 높이도 24px에서 30~32px로 키웠다.

왜: 직원은 밀도 높은 표와 목록·상세 배치에 익숙하다. 보호자용 홈페이지와 시각적으로 구분되어 「지금 직원 화면」임이 분명하다.

### 3.6 병원 현황 차트

- 날짜별 예약은 누적 막대(확정 + 승인 대기)로 그리고, 뒤에 그날 받을 수 있는 시간을 옅은 막대로 깔았다. 마우스·키보드 초점에 툴팁이 뜨고, 「표로 보기」가 있다.
- 수의사별·진료 항목별 활성 예약, WAS별 처리 건수(문서 8장 ±20% 기준 판정)는 표 안 막대로 보여 준다.
- 색은 색각 이상 검사 스크립트로 확인한 조합만 썼다. 홈페이지 쪽은 `#00876a` + `#e3961f`, EMR 쪽은 `#1c5cab` + `#e3961f`다. 처음 쓰려던 브랜드 청록 `#0f7a64`는 채도가 낮아 회색처럼 보여 차트 색에서 뺐다. 주황은 흰 배경 대비가 3:1 미만이라 범례·툴팁·표를 반드시 함께 둔다.

### 3.7 S3 정적 미리보기

무엇을: WAS 없이 소개 페이지만 다른 사람에게 보여 주는 S3 정적 웹사이트(버킷 `bodeum-vet-web-f72cb1`).

어떻게
- S3는 nginx처럼 `/about` → `about.html`을 해 주지 않는다. 그래서 확장자 없는 키(`about`)도 함께 올렸다.
- 공지 API 대신 시드 공지를 JSON 파일(`/api/notices`, `/api/notices/5`)로 올려 읽기 전용으로 보이게 했다.
- `/app/*`(로그인·예약)는 라우팅 규칙으로 「미리보기 안내」 페이지에 보낸다.
- 버킷은 객체 읽기만 공개하고 ACL은 막아 둔다.

왜: 월 몇백 원으로 디자인을 공유하기 위해서다. 3-Tier를 내려도 미리보기는 남는다.

## 4. 리전·가용 영역·네트워크

### 4.1 리전과 가용 영역

| 항목 | 값 |
|---|---|
| 리전 | `ap-northeast-2` (서울) |
| 사용 AZ | `ap-northeast-2a` = apne2-az1, `ap-northeast-2c` = apne2-az3 |
| 사용하지 않은 AZ | `ap-northeast-2b` = apne2-az2, `ap-northeast-2d` = apne2-az4 |

2a·2c를 고른 이유
1. ALB는 서로 다른 AZ의 서브넷이 최소 2개 필요하다. RDS Multi-AZ와 DB·캐시 서브넷 그룹도 2개 AZ가 필요하다.
2. AZ 하나가 장애 나도 남은 AZ로 서비스가 계속된다(TC-06). WEB·WAS를 AZ마다 1대씩 두었다.
3. 사용할 인스턴스 유형(t3.micro·t3.small·t3.medium·m7i.large)이 2a·2c 모두에서 제공되는 것을 확인했다(`describe-instance-type-offerings`).
4. 3~4개 AZ는 서브넷·NAT·AZ 간 전송 비용이 늘지만, 동시 140명 규모에서 가용성 이득이 작다.
5. 근거 문서 5장과 과정 실습이 2a·2c 조합이라 팀 기준을 유지했다.
6. AZ 이름은 계정마다 물리 AZ와의 대응이 다를 수 있다. 그래서 AZ ID(apne2-az1, az3)도 함께 기록했다.

### 5.2 WEB 인스턴스: t3.small × 2~3

WEB이 하는 일은 정적 파일 응답과 `/api` 프록시뿐이다. CPU 연산은 모두 WAS에서 일어난다.

| 후보 | vCPU·메모리 | 시간당 | 2대 월(730시간) | 판단 |
|---|---|---|---|---|
| t3.micro | 2·1 GiB | 0.013달러 | 약 19.0달러 | 여유가 작고 기준 CPU 10% |
| **t3.small** | 2·2 GiB | 0.026달러 | 약 38.0달러 | **채택** |
| t4g.small | 2·2 GiB (Arm) | 0.0208달러 | 약 30.4달러 | 20% 절감. TC-02 뒤 비교 후보 |
| t3.medium | 2·4 GiB | 0.052달러 | 약 75.9달러 | 메모리 부족 확인 시 |
| c7i.large | 2·4 GiB | 0.1008달러 | 약 147.2달러 | CPU 병목 확인 시 |
| m7i.large | 2·8 GiB | 0.1239달러 | 약 180.9달러 | 지속 부하 확인 시 |

- t3.small을 고른 이유: nginx에는 과분할 만큼 충분하다. dnf 설치·CloudWatch 에이전트·OS 캐시 여유를 위해 2 GiB·기준 CPU 20%를 기준으로 두었다. WAS와 같은 x86_64 AMI를 쓴다.
- 최소 2대: 대상 추적 확장은 1분 지표 → 경보 → 기동 → 헬스 체크를 거쳐 30초 급증에 늦다. 그래서 기존 2대(2a·2c)로 첫 몇 분과 AZ 장애를 버틴다. 최대 3대는 보험이다.
- 구성: 시작 템플릿 `vet01-lt-web`(IMDSv2, 세부 모니터링, 키 페어 없음). 사용자 데이터가 nginx 설치 → S3에서 화면 묶음과 nginx.conf 받기 → 내부 ALB 이름 치환 → 시작까지 한다. ASG `vet01-asg-web`(ELB 헬스 체크, 유예 120초, CPU 50% 대상 추적).

### 5.3 내부 로드 밸런서: 내부 ALB (NLB 검토 후 미채택)

| 항목 | NLB | ALB |
|---|---|---|
| 분산 단위 | TCP 연결 | HTTP 요청 |
| HTTP 지표 | 없음 | `TargetResponseTime`, 대상 그룹 5xx |
| 교차 영역 분산 | 기본 꺼짐 (켜면 AZ 간 요금) | 항상 켜짐 |
| 고정 IP / PrivateLink | 가능 | 불가 |
| 요금 | 0.0225달러 + LCU 0.006달러 | 0.0225달러 + LCU 0.008달러 |

ALB를 고른 이유
1. 나중에 nginx 업스트림 keepalive를 켜면 NLB는 연결이 붙은 WAS로만 보낸다. 그러면 WAS별 처리 건수(±20% 기준)가 치우친다.
2. 문서 8장의 WAS 지표가 ALB 지표다.
3. WAS가 AZ마다 1대인 구성에서 NLB는 기본으로 같은 AZ에만 보낸다.
4. nginx가 내부 ALB DNS를 10초마다 다시 조회하므로 고정 IP가 필요 없다.
5. 비용 차이가 없다.

NLB를 다시 검토할 조건: HTTP가 아닌 프로토콜, 다른 고객사 VPC에 PrivateLink로 제공, 고정 IP 허용 목록, 초당 수만 건 이상.

설정: `vet01-alb-int`(internal, app 서브넷), 리스너 HTTP 8080 → `vet01-tg-was`, 헬스 체크는 외부와 같은 값. `/health`는 일부러 DB를 확인하지 않는다. DB 장애 때 모든 WAS가 비정상이 되면 ASG가 멀쩡한 인스턴스까지 교체하고 ALB가 fail open이 되기 때문이다.

### 5.4 WAS 인스턴스: t3.medium × 2~4

| 후보 | vCPU·메모리 | 시간당 | 2대 월 | 판단 |
|---|---|---|---|---|
| t3.small | 2·2 GiB | 0.026달러 | 약 38.0달러 | 힙 2 GiB를 둘 수 없음 |
| **t3.medium** | 2·4 GiB | 0.052달러 | 약 75.9달러 | **채택** (문서 5장 선정값) |
| t4g.medium | 2·4 GiB (Arm) | 0.0416달러 | 약 60.7달러 | 같은 jar 실행 가능, 20% 절감 후보 |
| c7i.large | 2·4 GiB | 0.1008달러 | 약 147.2달러 | 로그인 해시 병목 확인 시 |
| m7i.large | 2·8 GiB | 0.1239달러 | 약 180.9달러 | 8 GiB를 쓰지 않으면 낭비 |

- 메모리: 힙 최대 2 GiB에 메타스페이스·스레드·코드 캐시·OS·에이전트를 더하면 3 GiB 안팎이다. 4 GiB가 가장 작은 적정 사양이다.
- CPU: 스파이크 때 몰리는 로그인 BCrypt 해시(강도 10)를 2 vCPU가 나눠 처리한다. T3 unlimited라 시험 중 묶이지 않는다.
- 최소 2대: JVM 기동이 느려 30초 급증에 확장이 늦다.
- 최대 4대: 4대 × 풀 10 = 40, 여유 5를 더해 45. 「최대 사용량이 한도의 80% 이하」 조건이 필요 한도 57을 만든다. 실측 한도는 144다.
- 헬스 체크 유예 300초: 문서는 120초다. 첫 부팅에 JDK 설치(dnf)가 들어가 여유를 두었다.

### 5.5 WAS 언어와 구현

| 결정 | 이유 |
|---|---|
| Java 21 + Spring Boot 4.1.1 | `@Transactional`이 실패 시 전체 롤백, Spring Session으로 무상태, HikariCP 기본 포함, jar 하나로 배포, 팀 경험, 4.1 OSS 지원 2027-07-31 |
| Spring Boot 4의 새 스타터 사용 | 4.0부터 자동 설정이 모듈로 나뉘었다. `spring-boot-starter-webmvc`, `spring-boot-starter-session-data-redis`를 Maven Central에서 확인 후 사용 |
| JdbcTemplate (ORM 없음) | 문서 6장의 SQL(조건부 UPDATE, FOR UPDATE)을 그대로 쓴다 |
| 교착 상태 재시도 | 교착 상태(1213)·잠금 대기 초과(1205)는 트랜잭션 밖에서 50~150ms 대기 후 최대 2회 재시도. 그래도 실패하면 409 `BUSY` |
| `@SessionAttribute(required = false)` | `HttpSession`을 인자로 받으면 로그인하지 않은 요청에도 세션이 생겨 ElastiCache에 쌓인다. 기존 세션만 읽도록 바꿨다 |
| `X-Served-By` 필터 | 분산 확인. 처리한 WAS 이름은 예약 행의 `served_by`에도 남긴다 |
| JVM DNS TTL 60초 | RDS 장애 조치 후 바뀐 주소를 따라간다 |
| 기본 시간대 Asia/Seoul | EC2 기본은 UTC. 슬롯은 병원 현지 시각 |
| 로그인 시도 제한 | 계정별 실패를 ElastiCache 카운터로 세어 5회면 1분간 429. 캐시가 잠시 안 돼도 로그인은 막지 않는다 |
| 슬롯 자동 채우기 | 기동 시와 매일 00:05에 오늘부터 14일 슬롯을 `INSERT IGNORE`. 유니크 키 덕분에 WAS가 여러 대여도 중복 없음 |
| 연결 풀 10, 연결 대기 3초 | 8장 계산. 연결 부족을 30초 지연이 아니라 바로 오류로 드러낸다 |

### 5.6 데이터베이스: RDS for MySQL 8.4.11, db.t3.small, Multi-AZ

| 후보 | 판단 |
|---|---|
| **RDS for MySQL** | **채택.** 행 잠금 조건부 UPDATE, 유니크 제약, 저장 생성 열 지원, 과정 실습 엔진 |
| Aurora MySQL | 제외. 576슬롯 규모에 비해 크고 비싸다 |
| DynamoDB | 제외. 보호자–반려동물–예약을 묶어 보는 관리자 조회가 많아 관계형이 맞다 |
| EC2에 직접 설치 | 제외. 백업·장애 조치를 직접 해야 하고, IT 담당자가 없는 고객사 모델과 안 맞는다 |

| 결정 | 이유 |
|---|---|
| 버전 8.4.11 | 8.0은 RDS 표준 지원이 2026-07-31에 끝났다. 8.4는 2029-07-31까지. 서울 리전 최신 8.4 버전 |
| db.t3.small (Multi-AZ 시간당 0.104달러) | db.t3.micro는 연결 한도(약 60)가 필요량 57에 여유가 없다. small 실측 한도 144 |
| Multi-AZ 인스턴스 배포 | 장애 시 자동 전환(보통 60~120초). 테스트에서도 TC-06 ③을 확인. 실제 배치는 주 2c, 대기 2a |
| gp3 20 GiB, 암호화 | 데이터가 수 MB |
| 파라미터 그룹 | `time_zone = Asia/Seoul`, utf8mb4 |
| 마스터 비밀번호 | RDS가 Secrets Manager로 관리 |
| 앱 계정 `vet_app` | SELECT·INSERT·UPDATE + notices DELETE만. 앱 문제로 테이블을 지우거나 바꿀 수 없다 |
| 백업 7일, 삭제 시 최종 스냅샷 | 복구 지점 확보 |

중복 예약을 막는 스키마
- `slots`: `uq_vet_time(vet_id, start_at)` — 같은 수의사·시각의 슬롯은 하나. `uq_resv(reservation_id)` — 예약 1건이 슬롯 2개를 잡지 못함.
- `reservations`: 활성 상태일 때만 `pet_id|visit_date` 값을 갖는 저장 생성 열 `active_pet_day`에 유니크 키 — 같은 반려동물은 같은 날 1건. 취소되면 NULL이라 제약에서 빠진다.

### 5.7 세션 저장소: ElastiCache Redis 7.1, cache.t3.micro

| 후보 | 판단 |
|---|---|
| **ElastiCache Redis OSS 7.1** | **채택.** Spring Session이 그대로 지원. 로그인 실패 카운터도 같은 곳에 |
| Valkey | Redis 호환에 노드 요금이 더 낮다. 다음 고객사 전환 후보 |
| ALB 고정 세션 | 제외. 분산이 치우치고 WAS 1대가 죽으면 그 세션이 끊긴다 |
| DB 세션 테이블 | 제외. 매 요청 조회가 RDS에 몰린다 |
| JWT | 제외. 계정 정지·강제 로그아웃을 즉시 반영하기 어렵다 |

설정: cache.t3.micro(시간당 0.025달러) 노드 1개, 전송 중·저장 중 암호화, AUTH 토큰은 Secrets Manager, 자동 장애 조치 끔(노드 1개에서는 켤 수 없음). 세션 1건이 수 KB라 0.5 GiB로 충분하다.

## 7. 인프라 코드와 배포 방법

### 7.1 CloudFormation 스택

| 스택 | 리소스 | 소요 |
|---|---|---|
| `vet01-network` | VPC, 서브넷 8, IGW, NAT 1, 라우팅 테이블 2, S3 엔드포인트 | 약 3분 |
| `vet01-security` | 보안 그룹 7(+Locust 1은 loadgen), IAM 역할·인스턴스 프로필 4 | 약 1분 |
| `vet01-data` | RDS Multi-AZ, DB 서브넷·파라미터 그룹, ElastiCache, 비밀 2, 관리 EC2 | 약 20분 |
| `vet01-was` | 내부 ALB, WAS 대상 그룹·시작 템플릿·ASG·조정 정책, 로그 버킷, 경보 3 (WAS 비정상, DB CPU, DB 연결) | 약 2분 (+부팅 수 분) |
| `vet01-web` | 외부 ALB, WEB 대상 그룹·시작 템플릿·ASG·조정 정책, 5xx 경보, 대시보드 | 약 2분 (+부팅 수 분) |
| `vet01-loadgen` | 부하 생성 VPC, 서브넷, IGW, Locust EC2, EIP | 약 2분 |

앞 스택의 값(서브넷 ID, 보안 그룹 ID, 엔드포인트)은 Export/ImportValue로 넘긴다. 고객사 이름과 VPC 대역만 매개변수로 바꿔 재사용한다.

### 7.2 배포 순서 (`deploy/aws.sh`)

```
bash deploy/aws.sh build     # 화면 빌드 → tar, WAS jar, 시드 SQL
bash deploy/aws.sh upload    # s3://vet01-artifacts-<계정>/{was,web,db,loadgen}/
bash deploy/aws.sh infra     # network → security → data
bash deploy/aws.sh dbinit    # 관리 EC2에서 스키마·시드·앱 계정 (Session Manager)
bash deploy/aws.sh was       # 내부 ALB·WAS (먼저)
bash deploy/aws.sh web       # 외부 ALB·WEB (was 다음)
bash deploy/aws.sh loadgen   # Locust
bash deploy/aws.sh verify    # 헬스·라우팅·분산 확인
bash deploy/aws.sh status    # 스택 상태와 접속 주소
bash deploy/aws.sh destroy   # 전부 삭제 (RDS 최종 스냅샷과 배포 버킷은 남음)
```

인스턴스에 직접 접속해 파일을 고치지 않는다. 사용자 데이터가 S3에서 받아 설치한다. 그래서 ASG가 새로 띄운 인스턴스도 항상 같은 상태다.
