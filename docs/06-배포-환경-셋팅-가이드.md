# 배포 환경 셋팅 가이드

새 PC에서 이 프로젝트(`webserver` 폴더)를 AWS에 배포하기 위해 무엇을 내려받고 어떻게 설정하는지 정리했다. 2026-10-19에 실제로 배포한 Windows 11 환경을 기준으로 썼다. macOS·Linux는 7장에 따로 있다.

> 이 시스템은 베타 테스트용이다. 로컬·S3 미리보기·AWS 모두 임시(가짜) 데이터와 테스트 계정만 쓴다. 테스트 계정은 보호자 owner001~owner300, 간호사 admin1·admin2, 원장 vet1~vet3이고 비밀번호는 공통 `test-only`다.

## 1. 내려받을 것

### 1.1 필수

| 도구 | 오늘 쓴 버전 | 쓰는 곳 | 설치 (Windows, PowerShell) |
|---|---|---|---|
| Git for Windows (Git Bash 포함) | 2.56.0 | 배포 스크립트가 bash라 Git Bash에서 실행 | `winget install -e --id Git.Git` |
| Node.js (npm 포함) | 24.22.0 (npm 11.19.1) | 웹 화면 빌드(Vite), 로컬 모의 서버, 시드 SQL 생성 | `winget install -e --id OpenJS.NodeJS.LTS` |
| Amazon Corretto 21 (JDK) | 21.0.12 | WAS(Spring Boot) jar 빌드 | `winget install -e --id Amazon.Corretto.21.JDK` |
| AWS CLI v2 | 2.38.1 | 스택 배포, S3 업로드, Session Manager 명령 | `winget install -e --id Amazon.AWSCLI` |

- Node.js는 20 이상이면 된다(Vite 6 요구사항). 오늘은 24를 썼다.
- AWS CLI는 브라우저 로그인 명령 `aws login`이 있는 버전이 편하다. 오늘 쓴 2.38.1에는 있다.
- 설치가 끝나면 **열려 있던 터미널을 모두 닫고 새로 연다.** 그래야 PATH가 반영된다.

### 1.2 따로 설치하지 않아도 되는 것

| 도구 | 이유 |
|---|---|
| Gradle | 프로젝트에 Gradle Wrapper(`was/gradlew`)가 있어 처음 빌드할 때 9.8.1을 자동으로 받는다 |
| Spring Boot·라이브러리 | Gradle이 Maven Central에서 자동으로 받는다 (첫 빌드 1~2분) |
| React·Vite·TypeScript | `npm ci`가 `web/package-lock.json` 그대로 받는다 |
| MySQL 클라이언트 | DB 초기화는 AWS의 관리 EC2에서 실행된다 |
| Python·Locust | 부하 테스트는 AWS의 Locust EC2에서 실행된다 |
| Docker | 쓰지 않는다 |

### 1.3 인터넷 연결이 필요한 곳

| 대상 | 이유 |
|---|---|
| `registry.npmjs.org` | npm 패키지 |
| `repo1.maven.org`, `plugins.gradle.org`, `services.gradle.org` | Spring Boot 라이브러리, Gradle 배포판 |
| `*.amazonaws.com`, `*.signin.aws.amazon.com` | AWS API, 로그인 |
| `cdn.jsdelivr.net` | 화면 글꼴(Pretendard). 사용자 브라우저가 받는다 |

## 2. 설치 확인

새 PowerShell 또는 Git Bash를 열고 확인한다.

```bash
git --version
node -v
npm -v
java -version
aws --version
```

| 결과 | 조치 |
|---|---|
| `java -version`이 1.8 등 21이 아닌 버전을 보여 줌 | 다른 JDK가 PATH 앞에 있다. 배포 스크립트는 Windows에서 `C:\Program Files\Amazon Corretto\jdk21*`를 자동으로 찾아 쓰므로 그대로 진행해도 된다. 직접 빌드할 때는 `JAVA_HOME`을 Corretto 21 폴더로 지정한다 |
| `aws: command not found` (Git Bash) | 터미널을 새로 연다. 그래도 안 되면 스크립트가 `C:\Program Files\Amazon\AWSCLIV2\aws.exe`를 자동으로 쓴다 |
| `node`가 없음 | 터미널을 새로 연다 |

## 4. 로컬에서 먼저 확인 (AWS 없이)

```bash
cd web
npm ci
npm run build
npm start
```

브라우저에서 `http://localhost:8090`을 연다. 소개 페이지, `/app/login`(테스트 계정 채우기 버튼 있음), 예약, 간호사·원장 화면까지 모두 동작한다. 데이터는 메모리에 있어 서버를 끄면 처음 상태로 돌아간다.

- 포트를 바꾸려면 `PORT=8091 npm start`.
- 화면을 고치면서 보려면 `npm start`를 켠 채로 다른 터미널에서 `npm run dev`(Vite, 5173 포트).

WAS만 따로 빌드해 보려면

```bash
cd was
./gradlew bootJar -Pversion=1.0.0      # → was/build/libs/vet-api-1.0.0.jar
```

## 5. AWS 준비

### 5.1 계정 권한

오늘은 `AdministratorAccess`가 있는 IAM 사용자로 배포했다. 권한을 줄여야 한다면 아래 서비스의 생성·수정·삭제 권한이 필요하다.

| 서비스 | 쓰는 곳 |
|---|---|
| CloudFormation | 스택 6개 (network, security, data, was, web, loadgen) |
| EC2·VPC | VPC, 서브넷, NAT, 보안 그룹, 인스턴스, 시작 템플릿, EIP |
| Elastic Load Balancing | ALB 2개, 대상 그룹 |
| Auto Scaling | ASG 2개, 조정 정책 |
| RDS | MySQL Multi-AZ |
| ElastiCache | Redis |
| Secrets Manager | DB·AUTH 비밀 |
| IAM | 역할·인스턴스 프로필 생성(`CAPABILITY_NAMED_IAM`), `iam:PassRole` |
| Systems Manager | Session Manager 명령(DB 초기화) |
| S3 | 배포 버킷, ALB 로그 버킷, 미리보기 버킷 |
| CloudWatch | 경보, 대시보드, 로그 |

### 5.2 할당량

| 항목 | 필요 | 확인 |
|---|---|---|
| EC2 표준 인스턴스 vCPU (`L-1216C47A`) | 18 이상 (WEB 3 + WAS 4 + Locust 1 + 관리 1, 각 2 vCPU) | `aws service-quotas get-service-quota --service-code ec2 --quota-code L-1216C47A --region ap-northeast-2` |
| 리전당 VPC | 2개 사용 (서비스, 부하 생성) | 기본 5개 |
| 탄력적 IP | 2개 사용 (NAT, Locust) | 기본 5개 |

오늘 계정은 vCPU 할당량이 384였다. 부족하면 Service Quotas 콘솔에서 증설을 요청한다.

### 5.3 로그인

방법 1: 브라우저 로그인 (오늘 쓴 방법, 액세스 키 불필요)

```bash
aws login --region ap-northeast-2
```

브라우저가 열리면 AWS 콘솔 계정으로 로그인한다. 세션이 만료되면 같은 명령을 다시 실행한다.

방법 2: 액세스 키

```bash
aws configure
# AWS Access Key ID, Secret Access Key, Default region: ap-northeast-2, output: json
```

방법 3: IAM Identity Center(SSO)를 쓰는 조직이면 `aws configure sso`.

로그인 확인

```bash
aws sts get-caller-identity --region ap-northeast-2
```

### 5.4 환경 변수 (배포 스크립트가 알아서 정함)

| 변수 | 값 | 설명 |
|---|---|---|
| `AWS_REGION` | `ap-northeast-2` | 기본값 |
| `AWS_CLI_FILE_ENCODING` | `UTF-8` | Windows AWS CLI가 한글 템플릿을 CP949로 읽어 실패하는 것을 막는다 |
| `MSYS_NO_PATHCONV` | `1` | Git Bash가 `/aws/...` 같은 인자를 Windows 경로로 바꾸지 않게 |
| `JAVA_HOME` | Corretto 21 폴더 | 비어 있으면 Windows에서 자동 탐색 |
| `CLIENT` | `vet01` | 고객사 코드. 바꾸면 모든 리소스 이름이 바뀐다 |
| `VER` | `1.0.0` | 배포 버전 (jar·tar 파일 이름) |
| `ALLOWED_CIDR` | `0.0.0.0/0` | 외부 ALB 접속 허용 대역. 부하 테스트 때 `Locust IP/32`로 좁힌다 |

## 6. 배포하기

모든 명령은 **Git Bash**에서 프로젝트 폴더(`webserver`)를 기준으로 실행한다.

### 6.1 처음 배포 (전체)

| 순서 | 명령 | 하는 일 | 걸리는 시간 |
|---|---|---|---|
| ① | `bash deploy/aws.sh build` | 화면 빌드 → `build/vet-web-1.0.0.tar.gz`, WAS jar → `build/vet-api-1.0.0.jar`, 시드 SQL 생성(오늘부터 14일) | 2~3분 (첫 빌드는 다운로드 포함) |
| ② | `bash deploy/aws.sh upload` | 배포 버킷 `vet01-artifacts-<계정 ID>`에 올림. 버킷이 없으면 비공개로 자동 생성 | 1분 |
| ③ | `bash deploy/aws.sh infra` | network → security → data 스택 | 약 25분 (RDS Multi-AZ가 대부분) |
| ④ | `bash deploy/aws.sh dbinit` | 관리 EC2에서 스키마·임시 데이터·앱 DB 계정 생성 | 1분 |
| ⑤ | `bash deploy/aws.sh was` | WAS 계층: 내부 ALB, WAS 시작 템플릿·ASG, 로그 버킷, WAS·DB 경보 | 2분 + 인스턴스 부팅 약 3~5분 |
| ⑥ | `bash deploy/aws.sh web` | WEB 계층: 외부 ALB, WEB 시작 템플릿·ASG, 5xx 경보, 대시보드 (was 다음에) | 2분 + 부팅 약 2~3분 |
| ⑦ | `bash deploy/aws.sh loadgen` | Locust EC2 (부하 테스트할 때만) | 2분 |
| ⑧ | `bash deploy/aws.sh verify` | `/health`, `/about`, `/api/notices`, WEB·WAS 분산 확인 | 수십 초 |
| ⑨ | `bash deploy/aws.sh status` | 스택 상태와 접속 주소 출력 | |

⑤와 ⑥은 나눠서 하나씩 올린다. WEB 시작 템플릿이 WAS 스택의 내부 ALB 주소를 가져다 쓰므로 반드시 was → web 순서다. 둘을 이어서 하려면 `bash deploy/aws.sh app`.

한 번에 하려면 `bash deploy/aws.sh all`(build → upload → infra → dbinit → was → web → verify). 단, `web` 직후의 `verify`는 인스턴스가 아직 부팅 중이라 502가 날 수 있다. 3~5분 뒤 `verify`를 다시 실행한다.

### 6.2 접속

`bash deploy/aws.sh status`가 출력하는 `http://vet01-alb-ext-....elb.amazonaws.com`으로 접속한다. ALB를 새로 만들 때마다 주소가 바뀐다. 2026-10-19에 만든 환경(`vet01-alb-ext-72802186`)은 같은 날 삭제했다. CLI 없이 콘솔로 만드는 방법은 `docs/07`에 있다.

### 6.3 새 버전 배포 (코드를 고친 뒤)

버전 번호를 올려 빌드·업로드하고, WAS·WEB 스택을 갱신한 뒤 인스턴스를 차례로 교체한다(문서 10.7). 새 인스턴스가 healthy가 된 뒤 옛 인스턴스를 내리므로 서비스가 멈추지 않는다.

```bash
export VER=1.0.1
bash deploy/aws.sh build
bash deploy/aws.sh upload
bash deploy/aws.sh was        # WAS 시작 템플릿이 새 버전(AppVersion=1.0.1)으로 바뀐다
bash deploy/aws.sh web        # WEB 시작 템플릿도 같은 버전으로
aws autoscaling start-instance-refresh --auto-scaling-group-name vet01-asg-was --region ap-northeast-2 \
  --preferences '{"MinHealthyPercentage":100,"MaxHealthyPercentage":200,"AutoRollback":true}'
aws autoscaling start-instance-refresh --auto-scaling-group-name vet01-asg-web --region ap-northeast-2 \
  --preferences '{"MinHealthyPercentage":100,"MaxHealthyPercentage":200,"AutoRollback":true}'
```

- 화면만 고쳤으면 `web` 배포와 web 쪽 새로 고침만, WAS만 고쳤으면 `was` 배포와 was 쪽 새로 고침만 해도 된다.
- 문제가 생기면 `aws autoscaling rollback-instance-refresh --auto-scaling-group-name vet01-asg-was --region ap-northeast-2`.
- WAS가 4대로 늘어난 상태에서 새로 고침을 하면 잠시 8대 × 연결 10 = 80연결이 된다. 부하가 큰 시간에는 하지 않는다.

### 6.4 데이터를 처음 상태로 되돌리기

```bash
bash deploy/aws.sh build     # 시드를 오늘 날짜 기준으로 다시 만든다 (화면·jar도 다시 빌드됨)
bash deploy/aws.sh upload
bash deploy/aws.sh dbinit    # DB를 지우고 임시 데이터로 다시 채운다
```

시드만 바꾸려면 `node db/gen-seed.mjs > db/seed.sql` 후 `upload`, `dbinit`.

### 6.5 부하 테스트 준비 (선택)

```bash
ALLOWED_CIDR=<Locust 탄력적 IP>/32 bash deploy/aws.sh infra    # 외부 ALB를 Locust만 접속하게 좁힘
bash deploy/aws.sh loadgen
```

Locust EC2에는 Session Manager로 접속한다(AWS 콘솔 → EC2 → `vet01-locust` → 연결 → Session Manager). `/opt/loadtest`에서 실행한다.

```bash
cd /opt/loadtest
PROFILE=tc02 locust -f locustfile.py --headless -H http://<외부 ALB DNS> --csv results/tc02 --html results/tc02.html
```

테스트가 끝나면 `ALLOWED_CIDR=0.0.0.0/0 bash deploy/aws.sh infra`로 다시 연다.

### 6.6 S3 미리보기 배포 (소개 페이지만, 선택)

```bash
cd web
npm run build:s3
bash scripts/deploy-s3.sh bodeum-vet-web-f72cb1
```

Git Bash에서 `aws`를 못 찾으면 앞에 `AWS="/c/Program Files/Amazon/AWSCLIV2/aws.exe"`를 붙인다.

### 6.7 전부 지우기

```bash
bash deploy/aws.sh destroy
```

loadgen → app → data → security → network 순서로 지운다. RDS 최종 스냅샷과 배포 버킷은 남는다. 필요 없으면 콘솔에서 스냅샷과 버킷(`vet01-artifacts-<계정>`, `bodeum-vet-web-f72cb1`)도 지운다.

## 7. macOS·Linux에서 셋팅할 때

| 도구 | macOS (Homebrew) | Linux (Amazon Linux·Ubuntu 예) |
|---|---|---|
| Git | 기본 포함 또는 `brew install git` | `sudo dnf install git` / `sudo apt install git` |
| Node.js 20+ | `brew install node` | nvm 또는 NodeSource 저장소 |
| Corretto 21 | `brew install --cask corretto@21` | `sudo dnf install java-21-amazon-corretto-devel` |
| AWS CLI v2 | `brew install awscli` | AWS 공식 설치 파일(zip) |

- 배포 스크립트는 bash라 그대로 실행된다. `cygpath`가 없으면 경로 변환을 건너뛴다.
- Corretto 자동 탐색은 Windows 전용이다. `export JAVA_HOME=$(/usr/libexec/java_home -v 21)`(macOS)처럼 직접 지정한다.

## 8. 자주 만나는 문제

| 증상 | 원인 | 해결 |
|---|---|---|
| `Unable to load paramfile ... could not be decoded` | Windows AWS CLI가 한글 템플릿을 CP949로 읽음 | 배포 스크립트를 쓰면 자동 처리. 직접 실행할 때는 `export AWS_CLI_FILE_ENCODING=UTF-8` |
| `Invalid template path /c/Users/...` | Windows용 `aws.exe`가 Git Bash 경로를 못 읽음 | 스크립트가 `cygpath -m`으로 변환. 직접 실행할 때는 `C:/...` 경로 사용 |
| `NoRegion` 오류 | 기본 리전이 없음 | `--region ap-northeast-2` 또는 `export AWS_REGION=ap-northeast-2` |
| 스택이 `ROLLBACK_COMPLETE` | 생성 실패 후 롤백됨. 이 상태는 갱신이 안 된다 | 원인 확인: `aws cloudformation describe-stack-events --stack-name <스택>` → 스택 삭제 후 다시 배포 |
| 배포 직후 502 | WEB·WAS가 아직 부팅·설치 중 | 3~5분 뒤 다시 확인. 대상 그룹이 healthy인지 `aws elbv2 describe-target-health`로 확인 |
| 대상이 계속 unhealthy | WAS가 DB에 못 붙음(초기화 전 등), 설정 오류 | `dbinit`을 먼저 했는지 확인. Session Manager로 접속해 `sudo journalctl -u vet-api`, `/var/log/nginx/error.log` 확인. CloudWatch 로그 `/vet01/was`, `/vet01/web-error` |
| `/about`은 되는데 `/api`가 502·504 | WEB → 내부 ALB 구간 문제 | nginx 설정의 내부 ALB 이름, `vet01-sg-alb-int` 인바운드 확인 |
| 로그인 상태가 자꾸 풀림 | ElastiCache 연결 문제 | WAS 로그에서 Redis 오류 확인, `vet01-sg-cache` 인바운드 확인 |
| `dbinit`이 오래 걸리거나 실패 | 관리 EC2가 Session Manager에 아직 등록되지 않음 | 스크립트가 최대 5분 기다린다. `aws ssm describe-instance-information`으로 Online 확인 |
| 로컬 `npm start`에서 포트 충돌 | 8090을 다른 프로그램이 사용 | `PORT=8091 npm start` |
| AWS 명령이 갑자기 인증 오류 | `aws login` 세션 만료 | `aws login --region ap-northeast-2` 다시 실행 |
| `gradlew` 권한 오류 (macOS·Linux) | 실행 권한 없음 | `chmod +x was/gradlew` |

## 9. 비용 주의

| 상태 | 시간당 | 하루 |
|---|---|---|
| 전부 켜 둠 (app + data + network + loadgen) | 약 0.55달러 | 약 13달러 (약 1.8만 원) |
| loadgen만 지움 | 약 0.42달러 | 약 10달러 |

NAT Gateway, ALB, RDS, ElastiCache, EC2는 켜 둔 시간만큼 과금된다. 베타 테스트가 없는 날은 `destroy`로 지우고, 필요할 때 6.1 순서로 다시 배포한다(약 35분).
