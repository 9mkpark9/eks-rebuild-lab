# ⑤ 최종 문서

보듬 동물병원 예약 시스템을 소스에서 시작해 컨테이너, 쿠버네티스(kubeadm), EKS 로 옮긴 작업 전체의 정리다.
단계마다 가장 단순한 형태로 먼저 만들어 돌리고, 미리 정한 점검 기준에 걸린 것을 문제로 기록하고 고쳤다.
각 문제의 증상·원인·검토한 방법·해결·확인은 단계별 문서에 있다. 이 문서는 그것을 모은 것이다.
모든 측정은 2026-11-23 에 직접 실행한 결과다.

## 1. 전체 구조

```
                         사용자 (브라우저)
                               │
           ② localhost:28080 / ③ 노드IP:30080 / ④ ALB
                               │
                   web (Apache httpd, 복제본 2)
           화면(정적 파일) + /api 를 세 서비스로 나눔
          ┌────────────────────┼────────────────────┐
          ▼                    ▼                    ▼
   auth (복제본 2)       clinic (복제본 2)    reservation (복제본 2)
   로그인               반려동물·공지·시간표    예약·간호사·원장
          │  │                 │  │                 │  │
          │  └─────────────────┼──┴─────────────────┼──┴──▶ Redis (로그인 세션, 1개)
          ▼                    ▼                    ▼
                 MySQL (1개, 서비스마다 스키마와 계정이 다름)
                 볼륨: ② 도커 볼륨 / ③ 노드 디스크 / ④ EBS
```

| 구성 요소 | 이미지 | 크기 | 실행 사용자 |
|---|---|---|---|
| web | `httpd:2.4-alpine` + 화면 | 115MB | 82 |
| auth, clinic, reservation | `eclipse-temurin:21-jre-alpine` + jar | 각 366MB | 10001 |
| mysql | `mysql:8.4` + 스키마·시드·계정 초기화 | 1.27GB | 999 |
| redis | `redis:7-alpine` 그대로 | 58.5MB | 999 |

## 3. 문제 총람

모두 29건이다 (① 3, ② 11, ③ 11, ④ 4). 상태: ● 해결, ◐ 한계로 남김·맞바꿈, ○ 원인 미확정.

### ① 워크로드 테스트

| 번호 | 문제 | 해결 | |
|---|---|---|---|
| W-1 | 서비스가 8080 포트를 못 잡아 뜨지 않는다 | `SERVER_PORT` 환경 변수 | ● |
| W-2 | MySQL 을 띄운 직후 초기화하면 실패한다 | 준비 여부를 TCP 로 확인 (임시 서버는 소켓만 연다) | ● |
| W-3 | Redis 가 멈추면 로그인한 요청이 8초 뒤 500 | 소스의 동작. 고치지 않음 | ◐ |

### ② 이미지·컨테이너

| 번호 | 문제 | 해결 | |
|---|---|---|---|
| C-1 | 빌드 중 `./gradlew: not found` | Windows 의 CRLF. Dockerfile 에서 줄 끝을 고침 | ● |
| C-2 | 예약 화면이 읽는 응답 헤더가 없다 | Apache `mod_headers` | ● |
| C-3 | 폴더 안의 파일 목록이 보인다 | 필요한 것만 적은 Apache 설정 (모듈 25 → 11) | ● |
| C-4 | 종료 신호가 자바에 전달되지 않아 처리 중인 요청이 끊긴다 | `ENTRYPOINT` 대괄호 형식. 끊긴 요청 20 → 0건 | ● |
| C-5 | 컨테이너가 root 로 돈다 | `USER`, Apache 의 포트·PID 파일, Redis 의 `user` | ● |
| C-6 | 메모리 한도가 없어 힙 상한이 1.88GiB | `mem_limit` + `MaxRAMPercentage=50`, 실험으로 384MiB | ● |
| C-7 | 이미지 1.53GB, 한 줄 고쳐도 재빌드 109초 | 두 단계 빌드, JRE alpine, Gradle 캐시 → 366MB, 11초 | ● |
| C-8 | DB 가 빈 채로 뜨고, 초기화가 실패해도 "끝" | 초기화를 품은 DB 이미지, `set -euo pipefail`, 함수에 기대지 않음 | ● |
| C-9 | 멈춘 서비스로 가는 요청이 64초 매달린다 | Apache `connectiontimeout=2 retry=0`, DNS 대기 1초 → 3초 | ● |
| C-10 | 오래전에 만든 DB 이미지로 띄우면 예약할 시간이 없다 | 시드를 DB 가 처음 뜨는 날 기준으로 생성 | ● |
| C-11 | (nginx 일 때) 새로 띄운 직후 동시 요청 일부가 응답 없음 | Apache 에서는 재현 안 됨 | ○ |

### ③ 쿠버네티스

| 번호 | 문제 | 해결 | |
|---|---|---|---|
| K-1 | 다시 배포하면 수백 건이 503 | probe, 복제본 2, `maxUnavailable 0`, `preStop` | ● |
| K-2 | MySQL Pod 를 지우면 예약이 사라진다 | StatefulSet + 볼륨 | ● |
| K-3 | 비밀번호가 배포 정보에 보인다 | ConfigMap + Secret (Git 밖에서 넣음) | ● |
| K-4 | 자원 요청·한도가 없다 | ②의 측정값으로 | ● |
| K-5 | kubeadm 노드가 ECR 에서 이미지를 못 받는다 | ECR 로그인 Secret (12시간 만료) | ◐ |
| K-6 | kubeadm 에서 MySQL 볼륨이 만들어지지 않는다 | 워커 디스크를 볼륨으로 등록 | ● |
| K-7 | 볼륨 설정을 고쳐 다시 적용하면 거부된다 | StatefulSet·PVC 를 지우고 다시 | ● |
| K-8 | 다시 배포하면 복제본 둘이 한 노드에 몰린다 (5번 중 3번) | `matchLabelKeys: [pod-template-hash]` | ● |
| K-9 | 노드가 죽어도 5분 동안 Pod 를 옮기지 않는다 | `tolerationSeconds: 30` | ● |
| K-10 | 클러스터 DNS 둘이 한 노드에 있어 그 노드와 함께 모든 요청이 실패 | CoreDNS 에 노드 분산 패치 | ● |
| K-11 | DB 가 있는 노드가 죽으면 DB 가 옮겨 가지 못한다 | ④에서 EBS 로 일부 해결 | ◐ |

관찰(문제 아님): O-1 배포 직후 몇 초는 옛 버전이 답한다, O-2 MySQL 교체 중 일부가 500(소스), O-3 죽었던 노드가 돌아와도 Pod 는 돌아가지 않는다, O-4 EC2 에서 가끔 연결 끊김, O-5 `rollout undo` 는 Git 과 어긋난다.

### ④ EKS

| 번호 | 문제 | 해결 | |
|---|---|---|---|
| E-1 | 밖에서 접속할 길이 없다 (NodePort) | Ingress → ALB, 이 PC 의 IP 에만 | ● |
| E-2 | MySQL 볼륨이 안 만들어진다. 기본 `gp2` 로도 안 된다 | Auto Mode 드라이버(`ebs.csi.eks.amazonaws.com`)용 StorageClass | ● |
| E-3 | 노드 하나가 빠지자 모든 Pod 가 노드 1대에 몰렸다 | `minDomains: 2`, 가용 영역 분산 | ● |
| E-4 | DB 를 지키려는 표시 때문에 노드가 24시간 동안 안 지워진다 | 맞바꿈: DB 는 사람이 옮긴다 | ◐ |

## 4. 되풀이해 나타난 것

단계마다 다른 모습으로 같은 종류의 문제가 나왔다.

| 주제 | 나타난 곳 | 배운 것 |
|---|---|---|
| **"준비됨"을 무엇으로 판정하나** | W-2(소켓 ping 이 임시 서버에 속음), C-8(빈 DB 가 정상으로 보임), K-1(프로세스 시작 = 준비로 봄) | 준비 확인은 실제 사용 방식 그대로: TCP 로, 서비스 계정으로, 데이터를 읽어 본다 |
| **기다리는 시간의 기본값** | C-9(Apache 60초), K-9(쿠버네티스 300초), E-4(Auto Mode 24시간), W-3(Redis 2초 × 여러 번) | 기본값은 대개 "조심스럽게 오래 기다리기"다. 장애 때 사용자가 그만큼 기다린다 |
| **분산 규칙은 지금 있는 것만 본다** | K-8(곧 내려갈 Pod 까지 셈), K-10(kubeadm 의 CoreDNS), E-3(노드가 1대면 규칙이 지켜진 것으로 봄) | "둘로 나눴다"는 설정만으로는 부족하고, 배포·장애·정리 뒤의 실제 배치를 봐야 한다 |
| **환경이 해 주던 것이 사라짐** | K-5(ECR 로그인), K-6·E-2(볼륨), E-1(외부 접속), C-1(줄 끝 처리) | 한 환경에서 되던 것이 다음 환경에서 안 되면, 이전 환경이 무엇을 대신 해 주고 있었는지 찾는다 |
| **DB 가 하나뿐** | K-2, K-11, E-4, 모든 단계의 "MySQL 교체 중 7 ~ 17초 실패" | 앱은 무중단이 됐지만 DB 는 아니다. 이 구성의 가장 큰 한계 |

| 한계 | 영향 | 근거 |
|---|---|---|
| MySQL 과 Redis 가 하나씩이다 | 교체·장애 때 DB 요청 7 ~ 37초 실패, Redis 가 다시 뜨면 모두 로그아웃 | 2.2, 2.3 |

| ④ 갑작스런 노드 장애는 재 보지 못했다 | Auto Mode 노드에 손댈 권한이 없다 | ④ 6.3 |

| DB 연결이 끊기면 일부 요청이 503 이 아닌 500 | 소스의 동작 | ③ O-2 |

| Secret 은 암호화되지 않은 채 저장된다 (kubeadm) | Secret 을 읽을 권한이 있으면 비밀번호가 보인다 | K-3 |
| 수백 명이 동시에 쓰는 부하는 재지 않았다 | 동시 신청은 10명까지만 확인 | ① 6.4 |

EKS 의 앱을 줄이기 전의 복제본 수는 `v2/_run/4-eks/replicas-before-stop.txt` 에 있다 (web·auth·clinic·reservation 2, redis 1, mysql 1).

같은 AWS 계정에는 이 작업과 무관한 자원(EC2 3대 `k8s-core-cluster-instance-*`, ECR `mywebsd`)이 있다. 이 작업은 그것에 손대지 않았다. 이 작업의 자원은 모두 `Project=vet2` 태그와 `vet2-` 이름을 달고 있다.

### 6.1 다시 켜기

아래 절차는 **실행해 보지 않았다.**

**EKS**

```bash
export KUBECONFIG=v2/_run/kubeconfig-eks
kubectl -n vet2 scale sts mysql --replicas=1
kubectl -n vet2 scale deploy redis --replicas=1
kubectl -n vet2 scale deploy web auth clinic reservation --replicas=2
# Auto Mode 가 노드를 만든다 (앞서 2분 안팎). MySQL 은 EBS 가 있는 2a 에 뜬다.
kubectl -n vet2 get ingress web          # ALB 주소는 그대로다
```

API 서버는 이 PC 의 IP 에만, ALB 도 이 PC 의 IP 에만 열려 있다. IP 가 바뀌면 둘 다 고쳐야 한다 (`aws eks update-cluster-config`, `v2/k8s/apply.sh eks` 다시 실행).

**kubeadm**

```bash
aws ec2 start-instances --instance-ids <vet2-cp> <vet2-w1> <vet2-w2>
```

EC2 를 다시 켜면 공인 IP 가 바뀐다. 그래서 다음이 필요할 것이다.

- `v2/_run/kubeconfig-kubeadm` 의 API 서버 주소를 새 IP 로 바꾼다.
- API 서버 인증서에는 옛 공인 IP 만 들어 있어 새 IP 로는 인증서 검사에 실패할 것이다. 인증서를 새 IP 로 다시 만들어야 한다.
- ECR 로그인 Secret 이 만료됐을 것이다. `v2/k8s/kubeadm/ecr-pull-secret.sh -n vet2` 를 다시 실행한다. 노드에 이미 받아 둔 이미지로 뜨는 Pod 는 영향이 없다.
- 30080 은 노드의 새 공인 IP 로 접속한다.

### 6.2 지우기 (요금을 0 으로)

아래 순서로 지운다. **이것도 실행해 보지 않았다.** 지우면 되돌릴 수 없고, MySQL 의 예약 데이터도 사라진다.

1. EKS 의 Ingress 를 먼저 지운다 → ALB 가 지워진다 (`kubectl -n vet2 delete ingress web`)
2. `vet2` 네임스페이스를 지운다 → PVC 와 함께 EBS 가 지워진다 (`reclaimPolicy: Delete`)
3. EKS 클러스터를 지운다 (`aws eks delete-cluster --name vet2-eks`)
4. EC2 3대를 종료한다 (디스크도 함께 지워진다)
5. ECR 저장소 5개를 지운다
6. 서브넷, 라우팅 테이블, 인터넷 게이트웨이, 보안 그룹, VPC 를 지운다
7. IAM 역할 3개(`vet2-node`, `vet2-eks-cluster`, `vet2-eks-node`)와 인스턴스 프로파일 `vet2-node` 를 지운다
8. `Project=vet2` 태그와 `k8s-vet2` 로 남은 것이 없는지 조회한다

1 을 건너뛰고 3 을 먼저 하면, ALB 를 지워 줄 컨트롤러가 없어져 ALB 가 남는다.

├── tests/
│   ├── scenario.mjs      시나리오 테스트 (모든 단계 공통)
│   ├── traffic.mjs       요청을 계속 보내며 실패를 센다
│   ├── k8s-ops.sh        배포·업데이트·Pod 삭제·DB 교체 측정

## 8. 작업 중의 실수

단계별 문서에 각각 적었다. 모아 두면:

- ② `docker builder prune -af` 로 이 PC 의 도커 빌드 캐시를 전부 지웠다. 다른 프로젝트의 캐시도 포함이다.
- ② Redis 를 root 가 아니게 하려다 root 로 만들었고, 그 볼륨 때문에 Redis 가 재시작을 반복했다. 측정에서 발견해 고쳤다.
- ② C-11 의 원인을 처음에 "Docker Desktop 의 포트 전달"이라고 보고했다가, Apache 에서 재현되지 않아 철회했다.
- ③ 측정 도구의 버그(정규식, Windows 경로, `kill`, 명령 전체가 백그라운드로 가는 `&`, 로그인 실패를 세지 않음). 고친 뒤의 수치만 실었고, 영향을 받은 실험 하나(③ K-10 의 보정 전)는 그렇게 밝혔다.
- ④ AWS CLI 가 한글 주석이 든 user-data 를 읽지 못해 EC2 생성이 한 번 거부됐다 (만들어진 것 없음).

AWS 에 의도하지 않은 변경은 없었다.
