# ⑤ 최종 문서

보듬 동물병원 예약 시스템을 소스에서 시작해 컨테이너(②), 쿠버네티스(③ EC2 kubeadm), EKS(④)로 옮긴 작업 전체의 정리다.
단계마다 가장 단순한 형태로 먼저 만들어 돌리고, 미리 정한 점검 기준에 걸린 것을 문제로 기록하고 고쳤다. 각 문제는 단계별 문서에 **증상 → 원인 → 판단 기준 → 후보와 탈락 이유 → 고른 방법 → 확인 → 한계** 순서로 적었다. 이 문서는 그것을 모은 것이다.

명령의 결과는 모두 실제 터미널 화면의 캡처다 (`v2/docs/img/shot/`, 2026-11-24 ~ 25). 계정 번호·공인 IP·비밀번호는 가렸다. 캡처가 없는 옛 기록은 단계별 문서에서 "캡처 없음"으로 밝혔다.

## 0. 요약

### 0.1 워크로드

```
                         사용자 (브라우저)
                               │
           ② localhost:28090 / ③ 노드IP:30080 / ④ ALB
                               │
                   web (Apache httpd, 복제본 2)
           화면(정적 파일) + /api 를 세 서비스로 나눔
          ┌────────────────────┼────────────────────┐
          ▼                    ▼                    ▼
   auth (복제본 2)       clinic (복제본 2)    reservation (복제본 2)
   로그인               반려동물·공지·시간표    예약·간호사·원장
          │                    │                    │
          ├────────────────────┴────────────────────┴──▶ Redis (로그인 세션, 1개)
          ▼
   MySQL 8.4 (1개, 서비스마다 스키마와 계정이 다름)
   ①② 컨테이너 / ③ StatefulSet + 노드 디스크 / ④ StatefulSet + EBS / ⑥ RDS
```

## 2. 문제 총람

모두 32건이다 (① 4, ② 11, ③ 13, ④ 4). ● 해결, ◐ 한계로 남김·맞바꿈, ○ 원인 미확정. ⑥ 선택 과제에서 만난 것(R-1 ~ R-5)은 ⑥ 에 있다.

### ① 워크로드 테스트

| 번호 | 문제 | 해결 | |
|---|---|---|---|
| W-1 | 서비스가 8080 포트를 못 잡아 뜨지 않는다 (Windows) | `SERVER_PORT` 환경 변수 | ● |
| W-2 | MySQL 을 띄운 직후 초기화하면 실패한다 | 준비 여부를 TCP 로 확인 | ● |
| W-3 | Redis 가 멈추면 로그인한 요청이 8초 뒤 500 | 소스의 동작. 고치지 않음 | ◐ |
| W-4 | JDK 업데이트 뒤 빌드 실패 (`Failed to exec spawn helper`) | 옛 JDK 를 쥔 Gradle 데몬을 멈추고 다시 빌드 | ● |

### ② 이미지·컨테이너

| 번호 | 문제 | 해결 | |
|---|---|---|---|
| C-1 | 빌드 중 `./gradlew: not found` | 줄 끝(CRLF)을 Dockerfile 에서 고침 | ● |
| C-2 | 예약 화면이 읽는 응답 헤더가 없다 | Apache `mod_headers` | ● |
| C-3 | 폴더 안의 파일 목록이 보인다 | 필요한 것만 적은 Apache 설정 | ● |
| C-4 | 종료 신호가 자바에 전달되지 않는다 | `ENTRYPOINT` 대괄호 형식. 끊긴 요청 20 → 1 ~ 2건 | ◐ |
| C-5 | 컨테이너가 root 로 돈다 | `USER`, Apache 포트·PID, Redis `user` | ● |
| C-6 | 메모리 한도가 없어 힙 상한이 1.88GiB | 한도 + `MaxRAMPercentage=50` | ● |
| C-7 | 이미지 1.52GB, 한 줄 고쳐도 재빌드 54.8초 | 두 단계 빌드, JRE alpine, 캐시 → 366MB, 12.1초 | ● |
| C-8 | DB 가 빈 채로 뜨고, 초기화가 실패해도 "끝" | 초기화를 품은 DB 이미지, `set -euo pipefail` | ● |
| C-9 | 멈춘 서비스로 가는 요청이 64초 매달린다 | Apache `connectiontimeout=2 retry=0` | ● |
| C-10 | 오래전에 만든 DB 이미지로 띄우면 예약할 시간이 없다 | 시드를 DB 가 처음 뜨는 날 기준으로 | ● |
| C-11 | (nginx 일 때) 새로 띄운 직후 동시 요청 일부가 응답 없음 | Apache 에서는 재현 안 됨 | ○ |

### ③ 쿠버네티스

| 번호 | 문제 | 해결 | |
|---|---|---|---|
| K-1 | 다시 배포하면 수백 건이 503 | probe, 복제본 2, `maxUnavailable 0`, `preStop` | ● |
| K-2 | MySQL Pod 를 지우면 예약이 사라진다 | StatefulSet + 볼륨 | ● |
| K-3 | 비밀번호가 배포 정보에 보인다 | ConfigMap + Secret | ● |
| K-4 | 자원 요청·한도가 없다 | ② 의 측정값으로 | ● |
| K-5 | 노드가 ECR 에서 이미지를 못 받는다 | ECR 로그인 Secret (12시간 만료) | ◐ |
| K-6 | MySQL 의 볼륨이 만들어지지 않는다 | 워커 디스크 폴더를 PV 로 직접 등록 | ● |
| K-7 | 볼륨 설정을 고쳐 다시 적용하면 거부된다 | StatefulSet 과 PVC 를 지우고 다시 적용 (한 번도 묶인 적 없는 PVC 라 잃을 데이터가 없었다) | ● |
| K-8 | 다시 배포하면 복제본 둘이 한 노드에 몰린다 | `matchLabelKeys: [pod-template-hash]` | ● |
| K-9 | 노드가 죽어도 5분 동안 Pod 를 옮기지 않는다 | `tolerationSeconds: 30` | ● |
| K-10 | 클러스터 DNS 둘이 한 노드에 있다 | CoreDNS 에 노드 분산 | ● |
| K-11 | DB 가 있는 노드가 죽으면 DB 가 옮겨 가지 못한다 | 한계. ⑥ RDS 로 풀었다 | ◐ |
| K-12 | 밖으로 여는 방법 (MetalLB 가 EC2 에서 안 됨) | NodePort | ● |
| K-13 | 네트워크 플러그인 고르기 | Flannel | ● |

관찰(문제 아님): O-1 배포 직후 몇 초는 옛 버전이 답한다 (④ ALB 에서도 같음), O-2 DB 가 끊기면 일부가 500(소스), O-3 돌아온 노드로 Pod 가 돌아가지 않는다, O-4 kubeadm 에서 가끔 연결 끊김(원인 미확인), O-5 `rollout undo` 는 Git 과 어긋난다.

### ④ EKS

| 번호 | 문제 | 해결 | |
|---|---|---|---|
| E-1 | 밖에서 접속할 길이 없다 (NodePort) | Ingress → ALB, 이 PC 의 IP 에만 | ● |
| E-2 | 기본 `gp2` 로는 볼륨이 만들어지지 않는다 | StorageClass `vet2-ebs` (`ebs.csi.eks.amazonaws.com`, gp3) | ● |
| E-3 | 노드가 하나 빠지자 모든 Pod 가 한 노드에 몰렸다 | `minDomains: 2`, 가용 영역 분산 | ● |
| E-4 | MySQL·Redis 를 지키려는 표시 때문에 노드가 24시간 안 지워진다 | 맞바꿈: 사람이 옮긴다 | ◐ |

### 되풀이해 나타난 것

| 주제 | 나타난 곳 | 배운 것 |
|---|---|---|
| **"준비됨"을 무엇으로 판정하나** | W-2, C-8, K-1, ⑥ RDS 재시작(상태값이 실제보다 늦음) | 준비 확인은 실제 사용 방식 그대로 한다. 관리 도구의 상태값을 믿지 않는다 |
| **기다리는 시간의 기본값** | C-9(Apache 60초), K-9(300초), E-4(24시간), W-3 | 기본값은 대개 "오래 기다리기"다. 장애 때 사용자가 그만큼 기다린다 |
| **분산 규칙은 지금 있는 것만 본다** | K-8, K-10, E-3 | 설정만으로는 부족하고, 배포·장애·정리 뒤의 실제 배치를 봐야 한다 |
| **환경이 해 주던 것이 사라짐** | K-5(ECR 로그인), E-1(외부 접속), E-2(볼륨 드라이버), C-1(줄 끝) | 다음 환경에서 안 되면, 이전 환경이 무엇을 대신 해 주고 있었는지 찾는다 |
| **상태를 가진 것이 하나뿐** | K-2, K-11, E-4, W-3, 모든 단계의 "DB 교체 중 수십 건 실패" | 앱은 무중단이 됐지만 DB 와 Redis 는 아니다. 이 구성의 가장 큰 한계 |

| 요청·분산·PDB | PDB 가 노드 비우기에서 마지막 복제본을 지킴 | ⑥ 4장 |
| 가용 영역 분산 | 노드 2a, 2c | ④ E-3 |
| RDS | 사설 서브넷, 노드 보안 그룹 둘에서만 3306. 두 클러스터 65 / 65. 재시작 뒤 예약 230 유지 (약 20초 끊김). 워커 정지 때 실패 372 → 39 | ⑥ 2장 |
| Secrets Manager | 일부 (RDS 관리자 비밀번호만) | ⑥ 2.5 |

하지 않은 것: Helm, Gateway API, 전용 ServiceAccount 와 최소 권한, 도메인 · HTTPS, 자동 확장(HPA).

## 4. 회고

### 4.1 겪은 문제와 해결 두 가지

**① DB 가 노드에 묶인다 (③ K-2, K-11 → ④ E-2 → ⑥ RDS).**
v0 에서는 MySQL Pod 를 지우자 예약이 사라졌다. StatefulSet 과 볼륨으로 데이터는 지켰지만, kubeadm 에서는 볼륨이 워커1 의 디스크라 워커1 이 죽으면 DB 도 함께 멈췄다. EKS 에서는 EBS 로 노드와 떼어 냈지만 EBS 는 한 가용 영역에 묶인다. 단계마다 "데이터가 어디에 묶이는가"가 한 칸씩 넓어졌고, 마지막에 DB 를 클러스터 밖(RDS)으로 옮기자 노드 장애에서 DB 요청이 멈추는 구간이 없어졌다 (⑥ 2.7: 같은 워커를 멈췄을 때 클러스터 안 MySQL 은 약 1,000건 중 372건 실패, RDS 는 약 13,800건 중 39건).
배운 것: 상태를 가진 것은 "어디에 묶여 있고, 그것이 죽으면 어떻게 되는가"를 먼저 따진다.

**② 무중단 배포는 설정 하나가 아니라 세 가지가 겹쳐야 됐다 (③ K-1).**
v0 를 다시 배포하자 약 300건 중 240건이 503 이었다. 원인은 셋이 겹쳐 있었다: 준비되기 전에 요청을 받음(readinessProbe 없음), 복제본이 하나, 내려가는 Pod 가 받은 요청을 끊음. probe, 복제본 2 + `maxUnavailable: 0`, `preStop` 을 모두 넣자 0건이 됐다. 그래도 kubeadm 의 업데이트·롤백에서 연결 끊김 2건이 남았고 원인을 찾지 못했다 (③ O-4). 같은 파일로 EKS 에서는 0건이었다.
배운 것: 측정 없이 "무중단"이라고 말하지 않는다. 요청을 계속 보내며 실패를 세는 도구(`traffic.mjs`)를 먼저 만든 것이 모든 단계에서 판단의 근거가 됐다.

### 4.2 직접 구축(kubeadm) vs 관리형(EKS)

| 항목 | kubeadm (③) | EKS Auto Mode (④) |
|---|---|---|
| 만들기 | EC2 3대 + `kubeadm init/join` + Flannel + CoreDNS 분산 + 볼륨 PV. 스크립트 하나(`kubeadm-bootstrap.sh`)로 묶었다 | 스택 하나, 약 11분. 노드는 Pod 를 올리면 생긴다 |
| 밖으로 열기 | NodePort 를 직접 고르고 보안 그룹을 직접 (③ K-12) | Ingress 하나로 ALB 가 생긴다. IngressClass 만 직접 (④ E-1) |
| 볼륨 | provisioner 가 없어 PV 를 손으로 등록 (③ K-6) | EBS 드라이버가 들어 있다. StorageClass 는 직접 (④ E-2) |
| 이미지 받기 | ECR 로그인 Secret, 12시간마다 갱신 (③ K-5) | 노드 IAM 역할. 할 일 없음 |
| 노드 장애 | 노드를 멈추는 실험이 가능. 대기 시간을 직접 조정해 393 → 115초 (③ K-9) | 노드를 멈출 권한이 없다. 계획된 교체만 재 볼 수 있었다 |
| 노드 정리 | 고정 2대. 예측 가능 | Auto Mode 가 노드를 줄이며 Pod 를 몰아넣는다 (④ E-3), 정리 예외가 24시간 막음 (④ E-4) |
| 보이는 것 | 모든 부품(etcd, apiserver, CoreDNS)이 Pod 로 보이고 고칠 수 있다 | 컨트롤 플레인과 DNS 가 보이지 않는다 |
| 비용 (시간당) | EC2 t3.medium × 3 ≈ 0.16달러 | 컨트롤 플레인 0.10 + 노드 c5a.large × 2 ≈ 0.17 + ALB ≈ 0.03 + 관리 수수료 |

정리하면, **관리형은 "설치하고 연결하는 일"을 없애 주지만 "어떻게 동작할지 정하는 일"은 남긴다.** EKS 에서도 StorageClass, IngressClass, 분산 규칙, 정리 예외는 직접 정해야 했고, 그중 둘(E-3, E-4)은 관리형이 대신 해 주는 동작(노드 정리) 때문에 새로 생긴 문제였다. 반대로 kubeadm 은 손이 많이 가지만, 장애 실험과 대기 시간 조정처럼 "직접 만져 보는 것"이 가능했다. 배우는 단계에서는 kubeadm 이 무엇이 일어나는지 더 잘 보여 주었고, 운영한다면 EKS 가 사람이 할 일을 줄여 준다.

## 5. 남은 한계

| 한계 | 영향 | 근거 |
|---|---|---|
| DB 와 Redis 가 하나다 (필수 구성) | 교체하는 동안 DB 요청 실패 (③ 11초 26건, ④ 25초 44건). Redis 가 다시 뜨면 모두 로그아웃 | ③ 6.3, ④ 5.5, W-3 |
| ③ DB 가 워커1 디스크에 있다 | 워커1 이 죽으면 DB 도 멈춘다 | ③ K-11 |
| ④ EBS 가 한 영역(2a)에 있다 | 2a 에 노드가 없으면 MySQL 이 뜨지 못한다 (재 보지 않음) | ④ E-2 |
| ④ 갑작스런 노드 장애는 재 보지 못했다 | Auto Mode 노드를 멈출 권한이 없다 | ④ 5.6 |
| kubeadm 의 ECR 로그인은 12시간 뒤 만료된다 | 그 뒤 새로 이미지를 받는 Pod 가 실패 | ③ K-5 |
| Secret 은 암호화되지 않은 채 저장된다 (kubeadm) | Secret 을 읽을 권한이 있으면 비밀번호가 보인다 | ③ K-3 |
| 지표 서버·HPA 없음, HTTP 만 | 실제 사용량을 보지 못하고, 도메인·인증서가 없다 | |
| 수백 명 동시 부하는 재지 않았다 | 동시 신청은 10명까지만 | ① 6.4 |

## 6. 작업 중의 실수

- ② `docker builder prune -af` 로 이 PC 의 도커 빌드 캐시를 전부 지웠다. 다른 프로젝트의 캐시도 포함이다.
- ② Redis 를 root 가 아니게 하려다 볼륨 권한 때문에 재시작을 반복하게 만들었다. 측정에서 발견해 고쳤다.
- ② C-11 의 원인을 처음에 "Docker Desktop 의 포트 전달"이라고 보고했다가 철회했다.
- ③ v0 재현 스크립트가 한 줄에 적힌 `namespace: vet2 }` 를 바꾸지 못해 운영 중인 `vet2/auth` 를 v0 로 잠깐 덮어썼다. kubeadm overlay 를 다시 적용해 되돌렸고(auth 2/2, mysql-0 재시작 없음, 배포 정보에 비밀번호 0줄), 적용 전에 네임스페이스를 검사하게 고쳤다.
- ③ v0 를 DB 초기화가 끝나기 전에 재서 숫자가 틀렸다. 그 캡처를 버리고 DB 준비를 기다리게 고쳐 다시 쟀다.
- ④ 캡처 도구의 AWS 임시 키가 측정 중에 만료돼 두 캡처(4-08, gp2 재현)가 실패했다. 버리고 다시 찍었다.
- 측정 도구의 버그(정규식, Windows 경로, 로그인 실패를 세지 않음 등)를 고친 뒤의 수치만 실었다.

AWS 에 의도하지 않은 변경은 없었다.

## 7. 비용과 정리

### 7.1 AWS 자원 (CloudFormation 스택 5개)

| 스택 | 자원 | 요금 (온디맨드, 2026-11-24 조회) |
|---|---|---|
| `vet2-network` | VPC, 퍼블릭·사설 서브넷, 인터넷 게이트웨이, 노드 보안 그룹 | 0 |
| `vet2-ecr` | ECR 저장소 5개 | 저장량만 |
| `vet2-kubeadm` | EC2 t3.medium × 3 (③) | 시간당 0.052달러 × 3 |
| `vet2-eks` | EKS Auto Mode 클러스터 (④) | 시간당 0.10달러 + 노드 c5a.large × 2 (0.086달러 × 2) + 관리 수수료 |
| `vet2-rds` | RDS db.t4g.micro (⑥) | 시간당 0.025달러 + 저장 공간 |
| (스택 밖) | ALB 2개 (Ingress 가 만듦), EBS (PVC) | 시간당 약 0.03달러 × 2 |

**켜 두면 시간당 약 0.55달러, 하루 약 13달러** (Auto Mode 관리 수수료 제외).
같은 AWS 계정에 이 작업과 무관한 EC2 3대(`k8s-core-cluster-instance-*`)가 있다. 손대지 않았다.

만들고 지우는 것은 [stacks.sh](../infra/stacks.sh) 하나로 한다. 스택끼리 값을 내보내고 받아서(예: EKS 의 클러스터 보안 그룹 → RDS), 받는 스택이 남아 있으면 내보낸 스택이 지워지지 않는다. 지우는 순서를 도구가 지킨다.

### 7.2 멈추기

| 자원 | 멈추는 법 | 멈춘 뒤 남는 요금 |
|---|---|---|
| kubeadm EC2 | `aws ec2 stop-instances` | 디스크만 |
| EKS 노드 | 앱을 0 개로 줄이면 Auto Mode 가 노드를 없앤다 | 0 |
| EKS 컨트롤 플레인, ALB | 멈추는 기능이 없다 | 시간당 약 0.16달러 |
| RDS | `aws rds stop-db-instance` | 저장 공간만. **7일 뒤 AWS 가 저절로 다시 켠다** |

### 7.3 지우기 (되돌릴 수 없다)

```bash
v2/infra/stacks.sh down all      # rds → eks(안의 Ingress·PVC 먼저) → kubeadm → ecr → network
v2/infra/stacks.sh status        # 다섯 모두 "없음"
```

스택 밖에 생긴 것(ALB, EBS)은 `stacks.sh` 가 EKS 를 지우기 전에 클러스터 안의 `vet2`, `vet2-rds` 를 지워 없앤다. 끝나면 ALB, EBS 볼륨, 이름이 `vet2-` 로 시작하는 자원이 남지 않았는지 콘솔과 CLI 로 확인한다 (순서는 [⑦ 7장](7-실습-가이드.md)).
`stacks.sh down` 은 아직 실행해 보지 않았다 (자원을 유지하기로 했다). 지우는 순서는 CLI 로 만들었던 자원을 지울 때(2026-11-23) 실제로 검증한 순서를 옮긴 것이다.
