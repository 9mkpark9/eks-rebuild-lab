# 실습 가이드 — 보듬 동물병원 예약 시스템을 ① ~ ④ 순서로 직접 띄워 보기

강사님이 이 저장소만 가지고 같은 결과를 재현해 볼 수 있도록, **실제로 실행한 명령**을 순서대로 모았다.

> **단계별 실습 페이지:** [lab/](lab/README.md) 에 실습 8개가 있다 (실습 목표, 사전 준비, 명령마다 실제 출력, 결과 확인, 자원 정리). 이 파일은 그 명령들을 한곳에 모은 요약이다.
각 단계마다 "무엇을 하는지 → **손으로 하기**(실제 명령) → 기대 결과 → 어떤 설정으로 되어 있는지" 를 적었다.
저장소의 스크립트는 이 명령들을 묶어 둔 것이다. 단계 끝의 **한 번에 하기** 에 어떤 스크립트가 같은 일을 하는지 적었다. 처음 해 보는 사람은 손으로 하기를 따라가기를 권한다.
결과 화면은 [① ~ ⑥ 문서](#부록-c-더-읽을-곳)의 캡처와 같다.

| 단계 | 어디서 | 걸리는 시간 (대략) | 비용 |
|---|---|---|---|
| ① 워크로드 테스트 | WSL 2 Ubuntu | 15분 | 없음 |
| ② 이미지 빌드·컨테이너 | WSL 2 Ubuntu (Docker Engine) | 15분 | 없음 |
| ③ kubeadm 클러스터 | AWS EC2 3대 | 25분 (스택 8분 + 부트스트랩 10분) | 시간당 약 $0.16 |
| ④ EKS Auto Mode | AWS EKS | 25분 (클러스터 생성 11분 안팎) | 시간당 약 $0.25 (+ ALB) |
| ⑥ 선택: RDS | AWS RDS | 10분 | 시간당 약 $0.03 |

> 시간과 비용은 이 작업에서 본 값을 어림한 것이다 (서울 리전, 2026-11). 실습이 끝나면 반드시 [7장의 정리](#7-정리-반드시)를 한다.

### 0.3 비밀번호 — 어디에도 적지 않는다

비밀번호는 `v2/_run/secrets.env` 한 파일에만 있다. 이 폴더는 `.gitignore` 에 있다.
① 의 1.2 에서 무작위 값으로 만든다 (`stores.sh up` 도 처음 실행될 때 같은 일을 한다). 값을 직접 정하려면:

```bash
cp v2/docker/env.example v2/_run/secrets.env    # 값 5개를 채운다
```

| 단계 | 비밀번호를 넘기는 방법 |
|---|---|
| ① | 스크립트가 파일을 읽어 환경 변수로 |
| ② | `docker compose --env-file v2/_run/secrets.env` |
| ③④ | `v2/k8s/secrets.sh` 가 파일을 읽어 Secret `vet-db`, `vet-redis` 를 바로 만든다 (YAML 파일을 남기지 않는다) |
| ⑥ RDS | 관리자 비밀번호는 RDS 가 만들어 Secrets Manager 에 둔다. `rds-secret.sh` 가 읽어 Secret `vet-rds-admin` 으로 |

테스트 도구에 비밀번호를 넘길 때는 `v2/tests/with-secrets.sh <명령>` 을 쓴다. 화면에 값이 나오지 않는다.

## 1. ① 워크로드 테스트 (WSL 2)

**목표:** 컨테이너 없이 서비스 3개를 jar 로 띄우고 시나리오 테스트를 통과시킨다. MySQL 과 Redis 만 공식 이미지 컨테이너로 띄운다. 서비스의 설정은 모두 환경 변수다.

### 1.1 빌드

```bash
git clone <저장소 주소> ~/vet2-lab && cd ~/vet2-lab
(cd msa && ./gradlew clean build)          # BUILD SUCCESSFUL, jar 3개
ls msa/*-service/build/libs/               # vet-auth-1.0.0.jar, vet-clinic-1.0.0.jar, vet-reservation-1.0.0.jar
```

`Failed to exec spawn helper` 가 나오면 JDK 가 업데이트된 뒤 옛 Gradle 데몬이 남은 것이다 (① W-4). `(cd msa && ./gradlew --stop)` 뒤 다시 빌드한다.

### 1.2 비밀번호 파일

비밀번호 5개를 무작위로 만들어 `v2/_run/secrets.env` 에 둔다. 화면에 출력하지 않는다.

```bash
mkdir -p v2/_run
( umask 077
  for k in DB_ROOT_PASSWORD DB_AUTH_PASSWORD DB_CLINIC_PASSWORD DB_RESERVATION_PASSWORD REDIS_PASSWORD; do
      echo "$k=$(head -c 18 /dev/urandom | od -An -tx1 | tr -d ' \n')"
  done > v2/_run/secrets.env )
set -a; . v2/_run/secrets.env; set +a      # 이 셸에서만 환경 변수로 쓴다 (echo 하지 않는다)
```

### 1.3 MySQL 과 Redis 띄우기

```bash
docker run -d --name v2-mysql -p 127.0.0.1:23306:3306 -e MYSQL_ROOT_PASSWORD="$DB_ROOT_PASSWORD" mysql:8.4
docker run -d --name v2-redis -p 127.0.0.1:26379:6379 redis:7-alpine redis-server --requirepass "$REDIS_PASSWORD"
```

포트를 `127.0.0.1` 에만 묶어 이 PC 밖에서는 닿지 않게 했다.

### 1.4 DB 초기화

MySQL 이 **TCP 로** 응답할 때까지 기다린다. 공식 이미지는 처음 뜰 때 임시 서버를 소켓으로만 띄우므로, 소켓으로 물으면 준비 전인데도 답이 온다 (① W-2).

```bash
until docker exec -e MYSQL_PWD="$DB_ROOT_PASSWORD" v2-mysql \
      mysql -h127.0.0.1 -P3306 --protocol=tcp -uroot -e 'SELECT 1' >/dev/null 2>&1; do sleep 1; done
```

root 로 SQL 을 넣는 함수를 하나 만든다. 비밀번호는 명령줄이 아니라 컨테이너의 환경 변수(`MYSQL_PWD`)로 넘긴다.

```bash
sql() { docker exec -i -e MYSQL_PWD="$DB_ROOT_PASSWORD" v2-mysql mysql -uroot --default-character-set=utf8mb4 "$@"; }

# 1) 스키마 4개 — vet_load 에 원본 테이블과 시드를 넣고, 서비스별 스키마 3개로 나눈다
sql -e "CREATE DATABASE vet_load CHARACTER SET utf8mb4; CREATE DATABASE vet_auth CHARACTER SET utf8mb4;
        CREATE DATABASE vet_clinic CHARACTER SET utf8mb4; CREATE DATABASE vet_reservation CHARACTER SET utf8mb4;"

# 2) 테이블 (소스의 db/schema.sql)
sql vet_load < db/schema.sql

# 3) 시드 — 오늘 날짜 기준으로 만든다 (② C-10: 예약할 수 있는 시간이 늘 앞날에 있어야 한다)
node db/gen-seed.mjs > v2/_run/seed.sql
sql vet_load < v2/_run/seed.sql

# 4) 서비스 계정 3개 (서비스마다 다른 계정, 다른 비밀번호)
sql -e "CREATE USER 'vet_auth'@'%' IDENTIFIED BY '$DB_AUTH_PASSWORD';
        CREATE USER 'vet_clinic'@'%' IDENTIFIED BY '$DB_CLINIC_PASSWORD';
        CREATE USER 'vet_reservation'@'%' IDENTIFIED BY '$DB_RESERVATION_PASSWORD';"

# 5) 테이블을 서비스별 스키마로 옮기고 뷰를 만든다, 6) 권한 (둘 다 소스의 SQL)
sql < msa/db/split.sql
sql < msa/db/grants.sql

# 확인
sql -t -e "SELECT table_schema, table_name, table_type FROM information_schema.tables WHERE table_schema LIKE 'vet\_%' ORDER BY 1,3,2"
```

### 1.5 서비스 3개 실행

서비스가 읽는 설정은 모두 환경 변수다 (`msa/common/src/main/resources/vet-common.yml`). auth 를 예로:

```bash
mkdir -p v2/_run/1-workload
SERVER_PORT=28081 \
SPRING_DATASOURCE_URL="jdbc:mysql://127.0.0.1:23306/vet_auth?connectionTimeZone=LOCAL&characterEncoding=UTF-8" \
SPRING_DATASOURCE_USERNAME=vet_auth \
SPRING_DATASOURCE_PASSWORD="$DB_AUTH_PASSWORD" \
SPRING_DATA_REDIS_HOST=127.0.0.1 SPRING_DATA_REDIS_PORT=26379 SPRING_DATA_REDIS_PASSWORD="$REDIS_PASSWORD" \
REDIS_TLS=false \
nohup java -jar msa/auth-service/build/libs/vet-auth-1.0.0.jar > v2/_run/1-workload/auth.log 2>&1 &
```

clinic, reservation 도 같은 모양이다. 바뀌는 것만:

| 서비스 | `SERVER_PORT` | URL 의 스키마 | `USERNAME` | `PASSWORD` | jar |
|---|---|---|---|---|---|
| auth | 28081 | `vet_auth` | `vet_auth` | `$DB_AUTH_PASSWORD` | `msa/auth-service/build/libs/vet-auth-1.0.0.jar` |
| clinic | 28082 | `vet_clinic` | `vet_clinic` | `$DB_CLINIC_PASSWORD` | `msa/clinic-service/build/libs/vet-clinic-1.0.0.jar` |
| reservation | 28083 | `vet_reservation` | `vet_reservation` | `$DB_RESERVATION_PASSWORD` | `msa/reservation-service/build/libs/vet-reservation-1.0.0.jar` |

```bash
for p in 28081 28082 28083; do curl -s -o /dev/null -w "$p /health %{http_code}\n" http://127.0.0.1:$p/health; done   # 모두 200
grep -h 'Started .* seconds' v2/_run/1-workload/*.log
```

### 1.6 시나리오 테스트와 장애 확인

```bash
v2/tests/with-secrets.sh node v2/tests/scenario.mjs \
    --auth-url http://127.0.0.1:28081 --clinic-url http://127.0.0.1:28082 \
    --reservation-url http://127.0.0.1:28083 --db-container v2-mysql
v2/workload/fault-check.sh                 # 하나씩 멈추고 나머지가 어떻게 답하는지
```

**기대 결과**

- 시나리오: `결과: 통과 60 / 실패 0`
- 장애 확인: 서비스 하나가 멈춰도 나머지 둘은 정상. **Redis 를 멈추면 로그인한 요청이 약 8초 뒤 500** (① W-3, 소스의 동작이라 그대로 둔다)

**설정 (환경 변수)**

| 환경 변수 | ① 의 값 | 뜻 |
|---|---|---|
| `SPRING_DATASOURCE_URL` | `jdbc:mysql://127.0.0.1:23306/vet_<서비스>?...` | MySQL 주소와 서비스의 스키마. ② compose 는 호스트가 `mysql` 로 고정, ③④ 는 ConfigMap 의 `DB_HOST` 가 채운다 |
| `SPRING_DATASOURCE_USERNAME` / `PASSWORD` | `vet_<서비스>` / (secrets.env) | 서비스마다 다른 DB 계정 |
| `DB_POOL_MAX` | 기본 10 (②③④ 5, RDS 3) | 서비스 하나가 여는 DB 연결 수 |
| `SPRING_DATA_REDIS_HOST` / `PORT` / `PASSWORD` | `127.0.0.1` / `26379` / (secrets.env) | 로그인 세션 저장소 |
| `REDIS_TLS` | `false` | |
| `SERVER_PORT` | `28081` ~ `28083` | ① 에서만. ②부터는 모두 8080 |

**한 번에 하기 (스크립트):** 위 1.2 ~ 1.5 는 `v2/workload/stores.sh up` → `v2/workload/db-init.sh` → `v2/workload/services.sh start` 가 같은 명령을 그대로 실행한다. `services.sh status` 는 포트·PID·메모리·`/health` 를 한 줄씩 보여 준다.

정리: `kill $(ss -ltnpH 'sport = :28081' | grep -o 'pid=[0-9]*' | cut -d= -f2)` 를 세 포트에 (또는 `v2/workload/services.sh stop`), 그리고 `docker rm -f v2-mysql v2-redis` (데이터도 사라진다).

## 2. ② 이미지 빌드와 컨테이너 (WSL 2 Docker Engine)

**목표:** 이미지 5개(auth, clinic, reservation, web, db)를 만들고 compose 로 6개 컨테이너를 띄워 시나리오를 통과시킨다.

```bash
cd ~/vet2-lab
export WEB_PORT=28090        # 28080 을 다른 것이 쓰고 있지 않으면 생략해도 된다
C="docker compose -f v2/docker/compose.yaml --env-file v2/_run/secrets.env"

# 1) 빌드하고 띄우기 — 6개가 모두 healthy 가 될 때까지 기다린다
$C up -d --build --wait
$C ps

# 2) 시나리오 (web 을 거쳐서)
v2/tests/with-secrets.sh node v2/tests/scenario.mjs --base-url http://localhost:28090 --db-container v2-mysql-1

# 3) 이미지 확인 — 크기, 플랫폼(linux/amd64), 실행 사용자
docker image ls 'vet2-*'
docker image inspect vet2-auth:1.0.0 --format '{{.Os}}/{{.Architecture}} user={{.Config.User}}'

# 4) 정상 종료 확인 — 요청을 보내는 중에 auth 를 내린다 (stop 을 kill 로 바꾸면 강제 종료 비교)
(docker run --rm -i --network v2_default node:22-alpine node --input-type=module - http://auth:8080 20 \
    < v2/tests/shutdown-check.mjs) & sleep 4; docker stop v2-auth-1; wait; docker start v2-auth-1
```

브라우저: `http://localhost:28090/` (소개), `http://localhost:28090/app/` (예약 화면). 시드 계정은 [① 문서](1-워크로드-테스트.md) 3장.

**기대 결과**

- `docker compose ps`: 6개 `(healthy)`, 밖으로 열린 포트는 web 하나
- 시나리오: `결과: 통과 65 / 실패 0`
- 서비스 이미지 366MB, `linux/amd64`, 사용자 `10001`
- 정상 종료: 처리 중 끊긴 요청 1 ~ 2건 (강제 종료는 20건)

**설정 — Dockerfile 의 핵심 (서비스)** [service.Dockerfile](../docker/service.Dockerfile)

| 줄 | 왜 |
|---|---|
| `FROM eclipse-temurin:21-jdk AS build` → `FROM eclipse-temurin:21-jre-alpine` | 두 단계. 실행 이미지에는 JRE 와 jar 만 (1.52GB → 366MB) |
| `RUN --mount=type=cache,target=/root/.gradle ...` | Gradle 캐시를 빌드 사이에 남긴다 (한 줄 수정 뒤 54.8초 → 12.1초) |
| `.dockerignore` (Dockerfile 옆) | PC 의 `build/`, `.gradle` 을 보내지 않는다 (112.66MB → 6.88kB) |
| `USER 10001:10001` | root 가 아닌 사용자. 번호라 쿠버네티스가 `runAsNonRoot` 로 확인할 수 있다 |
| `ENTRYPOINT ["java","-jar","/app/app.jar"]` | 대괄호 형식이라 자바가 1번 프로세스 → 종료 신호를 직접 받는다 |
| `JAVA_TOOL_OPTIONS=-XX:MaxRAMPercentage=50` | 힙 = 컨테이너 메모리 한도의 50% |

**설정 — compose** [compose.yaml](../docker/compose.yaml)

| 설정 | 값 | 왜 |
|---|---|---|
| `depends_on` | 없음 | 쿠버네티스에는 뜨는 순서가 없다. 순서 없이 정상이 되는지 여기서 미리 본다 |
| `mem_limit` | 서비스 384m, MySQL 1g, web·Redis 64m | 사용량을 재 보고 정한 값 (② 6.4) |
| `healthcheck` | `/health`, MySQL 은 시드 조회 | `up --wait` 가 준비를 기다린다 |
| `stop_grace_period` | 40s | 처리 중인 요청을 마칠 시간 |
| 볼륨 | `mysql-data` | `down` 해도 데이터가 남는다. **비밀번호를 바꾸면 `down -v` 로 볼륨도 새로** |

**빌드 최적화를 단계별로 보고 싶다면** (② C-7): `v2/docker/bench/A ~ E.Dockerfile` 을 바꿔 가며

```bash
v2/tests/touch-src.sh msa/auth-service/src/main/java/kr/bodeum/vet/AuthServiceApplication.java
time docker build -f v2/docker/bench/A.Dockerfile --build-arg SERVICE=auth -t vet2-bench:A msa
git checkout -- msa/auth-service/src/main/java/kr/bodeum/vet/AuthServiceApplication.java
```

정리: `$C down` (데이터 유지) 또는 `$C down -v` (데이터까지)

## 3. AWS 공통 준비 (③④⑥ 앞에 한 번)

### 3.1 로그인과 변수

```bash
aws login                                   # 브라우저로 로그인. 세션은 몇 시간 뒤 끝난다
aws sts get-caller-identity --query Arn     # 로그인 확인

export AWS_REGION=ap-northeast-2 AWS_PAGER=""
export AWS_CLI_FILE_ENCODING=UTF-8          # Windows 의 AWS CLI 만: 템플릿의 한글 주석 때문에
MY_CIDR="$(curl -s https://checkip.amazonaws.com)/32"        # 웹·API 를 열어 줄 주소 = 이 PC 의 공인 IP
ACCOUNT=$(aws sts get-caller-identity --query Account --output text)
REG=$ACCOUNT.dkr.ecr.$AWS_REGION.amazonaws.com               # ECR 주소 (계정 번호가 들어 있다. 문서·Git 에 적지 않는다)
```

### 3.2 스택 만들기 (CloudFormation)

자원은 모두 CloudFormation 스택 5개로 만든다. 스택끼리 값을 내보내고 받으므로(예: network 의 서브넷 → kubeadm, eks) **순서가 있다**: `network → ecr → kubeadm, eks → rds`. 지울 때는 거꾸로.

```bash
cf() { aws cloudformation deploy --stack-name vet2-$1 --template-file v2/infra/$1.yaml \
         --capabilities CAPABILITY_NAMED_IAM --tags Project=vet2 --no-fail-on-empty-changeset "${@:2}"; }

aws cloudformation validate-template --template-body file://v2/infra/network.yaml   # 문법만 검사 (만들지 않는다)
cf network --parameter-overrides MyCidr=$MY_CIDR    # VPC 10.20.0.0/16, 퍼블릭 2·프라이빗 2 서브넷, 노드 보안 그룹 (약 40초)
cf ecr                                              # ECR 저장소 5개 (약 40초)

aws cloudformation describe-stacks --query 'Stacks[?starts_with(StackName,`vet2-`)].[StackName,StackStatus]' --output table
```

| 스택 | 만드는 것 | 파일 | 매개변수 |
|---|---|---|---|
| `vet2-network` | VPC, 서브넷, 라우팅, 노드 보안 그룹 | [network.yaml](../infra/network.yaml) | `MyCidr` |
| `vet2-ecr` | 저장소 5개 (지울 때 이미지도 함께) | [ecr.yaml](../infra/ecr.yaml) | |
| `vet2-kubeadm` | EC2 3대, 시작 템플릿(노드 준비 스크립트), IAM 역할 (SSM, ECR 읽기) | [kubeadm.yaml](../infra/kubeadm.yaml) | |
| `vet2-eks` | EKS Auto Mode 클러스터, IAM 역할 2개 | [eks.yaml](../infra/eks.yaml) | `MyCidr` |
| `vet2-rds` | RDS MySQL (프라이빗 서브넷), DB 보안 그룹 | [rds.yaml](../infra/rds.yaml) | |

`deploy` 는 스택이 이미 있으면 **바뀐 것만** 고친다. 이 PC 의 공인 IP 가 바뀌면 같은 명령을 새 `MY_CIDR` 로 다시 실행하면 된다.

### 3.3 이미지를 ECR 에 올리기

## 4. ③ kubeadm 클러스터 (EC2 3대)

**목표:** EC2 3대(컨트롤 플레인 1 + 워커 2)에 kubeadm 으로 클러스터를 만들고, 앱을 여러 Pod 로 올려 배포·업데이트·롤백·자동 복구를 확인한다.

### 4.1 EC2 3대 만들기

```bash
cf kubeadm                                  # t3.medium × 3, Ubuntu 24.04 (약 3분). 3장의 cf 함수
out() { aws cloudformation describe-stacks --stack-name vet2-kubeadm --query "Stacks[0].Outputs[?OutputKey=='$1'].OutputValue" --output text; }
CP=$(out ControlPlaneId); W1ID=$(out Worker1Id); W2ID=$(out Worker2Id)
CP_PRIV=$(out ControlPlanePrivateIp)
CP_PUB=$(aws ec2 describe-instances --instance-ids $CP --query 'Reservations[0].Instances[0].PublicIpAddress' --output text)
```

세 노드는 시작 템플릿의 준비 스크립트(user-data, [kubeadm.yaml](../infra/kubeadm.yaml))로 **스스로** 아래를 한다. 끝나면 `/var/lib/vet2-ready` 파일을 만든다. 새 Ubuntu 에 손으로 준비한다면 이 명령들을 각 노드에서 root 로 실행한다.

```bash
# (각 노드에서, root) — user-data 가 하는 일
hostnamectl set-hostname vet2-cp                       # 워커는 vet2-w1, vet2-w2 (user-data 는 인스턴스의 Name 태그에서 읽는다)
swapoff -a                                             # 스왑이 켜져 있으면 kubelet 이 뜨지 않는다
printf 'overlay\nbr_netfilter\n' > /etc/modules-load.d/k8s.conf && modprobe overlay && modprobe br_netfilter
printf 'net.bridge.bridge-nf-call-iptables = 1\nnet.bridge.bridge-nf-call-ip6tables = 1\nnet.ipv4.ip_forward = 1\n' > /etc/sysctl.d/k8s.conf
sysctl --system
apt-get update && apt-get install -y containerd apt-transport-https ca-certificates curl gpg
mkdir -p /etc/containerd && containerd config default > /etc/containerd/config.toml
sed -i 's/SystemdCgroup = false/SystemdCgroup = true/' /etc/containerd/config.toml     # kubelet 과 같은 cgroup 관리자
systemctl restart containerd
mkdir -p /etc/apt/keyrings
curl -fsSL https://pkgs.k8s.io/core:/stable:/v1.36/deb/Release.key | gpg --dearmor -o /etc/apt/keyrings/kubernetes-apt-keyring.gpg
echo "deb [signed-by=/etc/apt/keyrings/kubernetes-apt-keyring.gpg] https://pkgs.k8s.io/core:/stable:/v1.36/deb/ /" > /etc/apt/sources.list.d/kubernetes.list
apt-get update && apt-get install -y kubelet kubeadm kubectl && apt-mark hold kubelet kubeadm kubectl
systemctl enable --now kubelet
mkdir -p /var/lib/vet2-mysql                           # MySQL 볼륨 폴더 (vet2-w1 만 쓴다, ③ K-6)
```

### 4.2 노드에 들어가기 (SSH 없음)

노드에는 SSH 포트를 열지 않았다. **Session Manager** 로 셸을 연다. 노드의 IAM 역할에 `AmazonSSMManagedInstanceCore` 가 있어서 된다.

```bash
aws ssm start-session --target $CP          # 이 PC 에 Session Manager 플러그인이 있어야 한다
```

> 이 작업에서는 셸을 열지 않고 `aws ssm send-command` 로 명령만 보냈다 ([ssm-run.sh](../k8s/kubeadm/ssm-run.sh)). 아래 4.3 ~ 4.4 의 노드 명령은 그대로 `v2/k8s/kubeadm/ssm-run.sh <인스턴스 ID> '<명령>'` 으로도 보낼 수 있다 (root 로 실행된다). `start-session` 과 플러그인 설치는 이번에 해 보지 않았다.

준비가 끝났는지 노드마다 확인한다: `test -f /var/lib/vet2-ready && hostname && kubeadm version -o short`

### 4.3 컨트롤 플레인 만들기 (vet2-cp 에서)

```bash
# (vet2-cp, root) — $CP_PUB 자리에 4.1 에서 구한 공인 IP 를 넣는다
kubeadm init --pod-network-cidr=10.244.0.0/16 --apiserver-cert-extra-sans=<CP 공인 IP>
#   → "Your Kubernetes control-plane has initialized successfully!"
kubeadm token create --print-join-command --ttl 1h     # 워커에서 실행할 join 명령 한 줄이 나온다
```

| 옵션 | 왜 |
|---|---|
| `--pod-network-cidr=10.244.0.0/16` | Flannel 의 기본 Pod 대역 (③ K-13) |
| `--apiserver-cert-extra-sans=<공인 IP>` | 이 PC 의 kubectl 이 공인 IP 로 붙을 때 인증서 확인이 통과하도록 |
| `--ttl 1h` | join 토큰을 1시간만 유효하게. 토큰은 화면에만, 파일에 남기지 않는다 |

### 4.4 워커 붙이기 (vet2-w1, vet2-w2 에서)

```bash
# (각 워커, root) — 4.3 에서 나온 줄을 그대로
kubeadm join <CP 사설 IP>:6443 --token <토큰> --discovery-token-ca-cert-hash sha256:<해시>
#   → "This node has joined the cluster"
```

### 4.5 이 PC 에서 kubectl 쓰기


### 4.7 Secret 과 앱

```bash
set -a; . v2/_run/secrets.env; set +a
kubectl create namespace vet2

# DB·Redis 비밀번호 — 파일을 만들지 않고 바로 apply 로 넘긴다 (③ K-3)
kubectl -n vet2 create secret generic vet-db \
    --from-literal=root-password="$DB_ROOT_PASSWORD" --from-literal=auth-password="$DB_AUTH_PASSWORD" \
    --from-literal=clinic-password="$DB_CLINIC_PASSWORD" --from-literal=reservation-password="$DB_RESERVATION_PASSWORD" \
    --dry-run=client -o yaml | kubectl apply -f -
kubectl -n vet2 create secret generic vet-redis --from-literal=password="$REDIS_PASSWORD" --dry-run=client -o yaml | kubectl apply -f -

# ECR 로그인 Secret — kubeadm 의 kubelet 은 노드의 IAM 역할로 ECR 에 로그인하지 않는다. 12시간 유효 (③ K-5)
kubectl -n vet2 create secret docker-registry ecr-pull --docker-server=$REG --docker-username=AWS \
    --docker-password="$(aws ecr get-login-password)" --dry-run=client -o yaml | kubectl apply -f -
kubectl -n vet2 patch serviceaccount default -p '{"imagePullSecrets":[{"name":"ecr-pull"}]}'

# 앱 — overlay 를 렌더하고, 자리 표시(ECR_REGISTRY, MY_CIDR)를 실제 값으로 바꿔 적용한다
kubectl kustomize v2/k8s/overlays/kubeadm | sed -e "s#ECR_REGISTRY#$REG#g" -e "s#MY_CIDR#$MY_CIDR#g" > v2/_run/render-kubeadm.yaml
grep -c 'kind:' v2/_run/render-kubeadm.yaml                                 # 무엇이 적용되는지 먼저 본다
kubectl apply -f v2/_run/render-kubeadm.yaml && rm v2/_run/render-kubeadm.yaml   # 계정 번호가 든 파일이라 남기지 않는다
for d in web auth clinic reservation redis; do kubectl -n vet2 rollout status deploy/$d; done
kubectl -n vet2 rollout status sts/mysql
kubectl -n vet2 get deploy,sts,pods -o wide
```

자리 표시를 쓰는 이유: ECR 주소에는 계정 번호가, `MY_CIDR` 에는 이 PC 의 IP 가 들어간다. 둘 다 Git 에 적지 않으려고 적용할 때만 채운다.

**한 번에 하기 (스크립트):** 4.1 ~ 4.7 은 `v2/infra/stacks.sh up kubeadm` → `v2/infra/kubeadm-bootstrap.sh` 가 같은 순서로 실행한다 (노드 명령은 `ssm-run.sh` 로 보낸다). 앱만 다시 넣을 때는 `v2/k8s/secrets.sh -n vet2`, `v2/k8s/kubeadm/ecr-pull-secret.sh -n vet2`, `v2/k8s/apply.sh kubeadm` (`--render` 를 붙이면 적용하지 않고 보여만 준다).

### 4.8 확인

`W1` = 워커1 공인 IP

```bash
W1=$(aws ec2 describe-instances --filters Name=tag:Name,Values=vet2-w1 Name=instance-state-name,Values=running \
     --query 'Reservations[0].Instances[0].PublicIpAddress' --output text)

# 시나리오 — 밖에서 NodePort 로

kubectl -n vet2 delete pod $(kubectl -n vet2 get pod -l app=web -o name | head -1) --wait=false

# DB 는 밖에서 닿지 않는다
kubectl -n vet2 get svc                                                # mysql 은 ClusterIP

```

**설정 — 매니페스트의 핵심** ([base/](../k8s/base/), [mysql/](../k8s/mysql/))

| 대상 | 설정 | 왜 (문제 번호) |
|---|---|---|
| web, 서비스 3개 | `replicas: 2`, `maxSurge: 1`, `maxUnavailable: 0` | 배포 중에도 받을 Pod 가 있다 (K-1) |
| | startup · readiness · liveness probe, 모두 `/health` | 준비된 뒤에만 요청을 받는다. `/health` 는 DB 를 보지 않아 DB 장애로 재시작되지 않는다 |
| | `preStop: sleep 5` | Service 에서 빠진 것이 퍼진 뒤에 종료 신호 (K-1) |
| | `topologySpreadConstraints` + `matchLabelKeys: [pod-template-hash]` | 다시 배포해도 두 노드에 나뉜다 (K-8) |
| | PodDisruptionBudget `minAvailable: 1` | 노드 정비 때 둘을 한꺼번에 내리지 않는다 |
| 모든 Pod | `tolerationSeconds: 30` (not-ready, unreachable) | 노드가 죽으면 5분이 아니라 30초 뒤 옮긴다 (K-9) |
| | `runAsNonRoot`, 기능 모두 제거, 루트 파일 시스템 읽기 전용 | ② 의 root 아닌 사용자를 클러스터가 강제 |
| | 요청 / 한도: 서비스 256Mi / 384Mi, MySQL 512Mi / 1Gi | ② 의 측정값 (K-4) |
| MySQL | StatefulSet + `volumeClaimTemplates` 2Gi, Service `ClusterIP` | Pod 를 바꿔도 데이터가 남는다 (K-2) |
| 설정 | ConfigMap `vet-config` (`configMapGenerator`) | 값을 바꾸면 이름이 바뀌어 Pod 가 새로 뜬다 |
| 비밀 | Secret `vet-db`, `vet-redis` (`secretKeyRef`) | 배포 정보에 비밀번호 0줄 (K-3) |

**kubeadm 에서만 필요한 것** ([cluster/kubeadm/](../k8s/cluster/kubeadm/), overlay `kubeadm`)

| 무엇 | 왜 |
|---|---|
| StorageClass `vet2-local` + 워커1 디스크의 PV | kubeadm 에는 볼륨을 만들어 줄 것이 없다 (K-6). 대가: DB 가 워커1 에 묶인다 (K-11) |
| CoreDNS 에 노드 분산 규칙 + 30초 | 둘이 한 노드에 몰려, 그 노드가 죽자 모든 요청이 실패했다 (K-10) |
| Secret `ecr-pull` 을 기본 ServiceAccount 에 | kubelet 은 노드의 IAM 역할로 ECR 에 로그인하지 않는다 (K-5) |
| Service `web` 을 NodePort 30080 | MetalLB L2 는 VPC 에서 동작하지 않는다 (K-12) |

**보안 그룹** (`vet2-nodes`): 밖에서는 30080·30081·6443 을 이 PC 의 IP 에만. 노드끼리는 UDP 8472(Flannel), TCP 6443, TCP 10250 만.

> EC2 를 멈췄다 켜면 공인 IP 가 바뀐다. kubeconfig 의 서버 주소만 새 IP 로 바꾸고 `tls-server-name: kubernetes` 를 둔다 (인증서에 `kubernetes` 이름이 있다).

## 5. ④ EKS Auto Mode

**목표:** 같은 앱을 관리형 클러스터에 올린다. 노드·로드밸런서·볼륨 드라이버를 EKS 가 대신 맡는다.

```bash
cf eks --parameter-overrides MyCidr=$MY_CIDR    # 11분 안팎. Auto Mode, 노드 풀 general-purpose·system (3장의 cf 함수)
aws eks update-kubeconfig --name vet2-eks --kubeconfig v2/_run/kubeconfig-eks
export KUBECONFIG=$PWD/v2/_run/kubeconfig-eks
kubectl get nodes                           # 처음에는 0대. Pod 를 올리면 Auto Mode 가 만든다

# 클러스터에 한 번: IngressClass vet2-alb (ALB 를 만들게), StorageClass vet2-ebs (EBS gp3)
kubectl apply -f v2/k8s/cluster/eks/alb.yaml -f v2/k8s/cluster/eks/storage.yaml

# Secret — 4.7 과 같은 두 명령 (ECR 로그인 Secret 은 필요 없다: 노드의 IAM 역할로 받는다)
set -a; . v2/_run/secrets.env; set +a
kubectl create namespace vet2
kubectl -n vet2 create secret generic vet-db \
    --from-literal=root-password="$DB_ROOT_PASSWORD" --from-literal=auth-password="$DB_AUTH_PASSWORD" \
    --from-literal=clinic-password="$DB_CLINIC_PASSWORD" --from-literal=reservation-password="$DB_RESERVATION_PASSWORD" \
    --dry-run=client -o yaml | kubectl apply -f -
kubectl -n vet2 create secret generic vet-redis --from-literal=password="$REDIS_PASSWORD" --dry-run=client -o yaml | kubectl apply -f -

# 앱 — eks overlay. MY_CIDR 은 ALB 를 이 PC 의 IP 에만 여는 데 쓰인다 (Ingress 의 inbound-cidrs)
kubectl kustomize v2/k8s/overlays/eks | sed -e "s#ECR_REGISTRY#$REG#g" -e "s#MY_CIDR#$MY_CIDR#g" | kubectl apply -f -
kubectl -n vet2 get pods -o wide -w         # 1 ~ 2분 뒤 노드 2대(2a, 2c)가 생기고 Pod 가 뜬다
kubectl -n vet2 get ingress web             # ADDRESS 가 ALB 주소. 2 ~ 3분 뒤 응답한다
```

**한 번에 하기 (스크립트):** `v2/infra/stacks.sh up eks`, `v2/k8s/secrets.sh -n vet2`, `v2/k8s/apply.sh eks`.

**확인**

```bash
A1=$(kubectl -n vet2 get ingress web -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
v2/tests/with-secrets.sh node v2/tests/scenario.mjs --base-url http://$A1 \
     --db-exec 'kubectl -n vet2 exec mysql-0 --'                       # 통과 65 / 실패 0
kubectl -n vet2 get pvc                                                # data-mysql-0 Bound, vet2-ebs
v2/tests/k8s-ops.sh --base-url http://$A1 -n vet2 --only 4             # MySQL Pod 를 지워도 예약 유지
```

**③ 과 무엇이 다른가** (overlay `eks`, [cluster/eks/](../k8s/cluster/eks/))

| | ③ kubeadm | ④ EKS Auto Mode |
|---|---|---|
| 컨트롤 플레인 | 직접 (EC2 1대, kubeadm init) | AWS 가 운영 |
| 노드 | EC2 3대를 미리 | Pod 를 올리면 Auto Mode 가 만든다 |
| 네트워크 플러그인 | Flannel 설치 | VPC CNI 내장 (Pod 가 VPC IP) |
| ECR 로그인 | Secret (12시간) | 노드 IAM 역할 — 설정 없음 |
| 볼륨 | 워커 디스크 (local PV) | EBS (StorageClass `vet2-ebs`, `ebs.csi.eks.amazonaws.com`) |
| 밖으로 | NodePort 30080 | Ingress → ALB (`target-type: ip`, 이 PC 의 IP 에만) |
| 앱 매니페스트 | base 그대로 | base 그대로 (overlay 만 다르다) |

> 클러스터에 처음부터 있는 StorageClass `gp2` 를 쓰면 볼륨이 영영 만들어지지 않는다. 옛 드라이버 이름이라 Auto Mode 의 드라이버가 처리하지 않는다 ([④ 문서](4-EKS-전환.md)). 그래서 `vet2-ebs` 를 따로 만든다.

## 6. ⑥ 선택 과제 — DB 를 RDS 로

**목표:** 같은 앱을 네임스페이스 `vet2-rds` 에 하나 더 띄우고 DB 만 RDS 로 바꾼다. 필수 구성(`vet2`)은 그대로 둔다.

### 6.1 RDS 만들기

```bash
cf rds                                      # 10분 안팎. MySQL 8.4, db.t4g.micro, 프라이빗 서브넷 (eks 스택이 먼저 있어야 한다)
rout() { aws cloudformation describe-stacks --stack-name vet2-rds --query "Stacks[0].Outputs[?OutputKey=='$1'].OutputValue" --output text; }
RDS_HOST=$(rout Endpoint)                   # RDS 주소
ADMIN_ARN=$(rout AdminSecretArn)            # 관리자 비밀번호가 든 Secrets Manager 비밀의 ARN
```

관리자 비밀번호는 RDS 가 만들어 Secrets Manager 에 둔다 (`ManageMasterUserPassword`). 템플릿·명령줄·화면 어디에도 값이 나오지 않는다.

### 6.2 kubeadm 쪽 (웹은 NodePort 30081)

```bash
export KUBECONFIG=$PWD/v2/_run/kubeconfig-kubeadm
kubectl create namespace vet2-rds
# vet-db, vet-redis, ecr-pull — 4.7 의 세 명령을 -n vet2-rds 로 그대로

# RDS 관리자 계정 Secret (초기화 Job 만 쓴다). 값을 화면에 내지 않고 바로 넘긴다
J=$(aws secretsmanager get-secret-value --secret-id "$ADMIN_ARN" --query SecretString --output text)
kubectl -n vet2-rds create secret generic vet-rds-admin \
    --from-literal=username="$(printf '%s' "$J" | jq -r .username)" \
    --from-literal=password="$(printf '%s' "$J" | jq -r .password)" \
    --dry-run=client -o yaml | kubectl apply -f -
unset J

# 앱 + 초기화 Job — RDS_HOST 자리도 채운다
kubectl kustomize v2/k8s/overlays/kubeadm-rds \
  | sed -e "s#ECR_REGISTRY#$REG#g" -e "s#MY_CIDR#$MY_CIDR#g" -e "s#RDS_HOST#$RDS_HOST#g" | kubectl apply -f -
kubectl -n vet2-rds wait --for=condition=complete job/db-init --timeout=300s
kubectl -n vet2-rds logs job/db-init        # 처음: "초기화 끝", 두 번째부터: "이미 초기화된 DB 입니다"
```

`jq` 는 0.1 의 설치 목록에 없으면 `sudo apt install -y jq` (이 작업의 스크립트는 같은 일을 `node` 로 했다).

### 6.3 EKS 쪽 (ALB 가 하나 더 생긴다)

```bash
export KUBECONFIG=$PWD/v2/_run/kubeconfig-eks
kubectl create namespace vet2-rds
# vet-db, vet-redis (5장과 같은 두 명령), vet-rds-admin (6.2 와 같은 명령) 을 -n vet2-rds 로
kubectl kustomize v2/k8s/overlays/eks-rds \
  | sed -e "s#ECR_REGISTRY#$REG#g" -e "s#MY_CIDR#$MY_CIDR#g" -e "s#RDS_HOST#$RDS_HOST#g" | kubectl apply -f -

# 확인 — 시나리오 65개 (DB 계정 경계는 RDS 에 서비스 계정으로 직접 접속해 본다)
v2/tests/rds-check.sh http://$(kubectl -n vet2-rds get ingress web -o jsonpath='{.status.loadBalancer.ingress[0].hostname}')
```

**한 번에 하기 (스크립트):** `v2/infra/stacks.sh up rds`, 그리고 클러스터마다 `v2/k8s/secrets.sh -n vet2-rds`, `v2/k8s/rds-secret.sh -n vet2-rds`, (kubeadm 만) `v2/k8s/kubeadm/ecr-pull-secret.sh -n vet2-rds`, `v2/k8s/apply.sh kubeadm-rds` 또는 `eks-rds`.

**설정**

| 무엇 | 값 | 왜 |
|---|---|---|
| 서브넷 | 프라이빗 2개 (2a, 2c), 라우팅은 VPC 안만 | 인터넷에서 닿지 않는다 |
| 보안 그룹 `vet2-db` | 3306 을 kubeadm 노드 SG, EKS 클러스터 SG 에서만 | 두 클러스터의 Pod 만 |
| 관리자 비밀번호 | `ManageMasterUserPassword` (Secrets Manager, 7일마다 교체) | 사람이 값을 보지 않는다 |
| `components/rds` | `DB_HOST=RDS_HOST`, `DB_POOL_MAX=3`, Job `db-init` | `max_connections` 60 이라 연결 수를 줄였다. 초기화는 Job 이 한 번 (여러 번 돌려도 같은 결과) |

overlay 끼리의 차이는 `python v2/tests/overlay-diff.py` 로 한 화면에 볼 수 있다.

## 7. 정리 (반드시)

지우는 순서는 만든 순서의 거꾸로다. 받는 스택(예: rds)이 남아 있으면 내보낸 스택(eks)은 지워지지 않는다.

```bash
del() { aws cloudformation delete-stack --stack-name vet2-$1 && aws cloudformation wait stack-delete-complete --stack-name vet2-$1; }

del rds

# EKS 를 지우기 전에 클러스터 안의 네임스페이스부터 — ALB 2개와 MySQL 의 EBS 는 Ingress·PVC 가 만든 것이라
# 스택에 들어 있지 않다. 클러스터를 먼저 지우면 그것을 지워 줄 주체가 사라져 남는다
KUBECONFIG=v2/_run/kubeconfig-eks kubectl delete namespace vet2 vet2-rds --ignore-not-found --wait=true --timeout=10m
del eks
del kubeadm
del ecr                                     # 저장소 안의 이미지도 지워진다
del network
aws cloudformation describe-stacks --query 'Stacks[?starts_with(StackName,`vet2-`)].StackName'   # 비어 있어야 한다
```

**한 번에 하기 (스크립트):** `v2/infra/stacks.sh down all` 이 위 순서를 그대로 지킨다 (EKS 전에 네임스페이스 삭제 포함). `stacks.sh status` 로 5개 모두 "없음" 을 확인한다.

남은 것 확인 (태그 `Project=vet2`):

```bash
aws resourcegroupstaggingapi get-resources --tag-filters Key=Project,Values=vet2 --query 'ResourceTagMappingList[].ResourceARN'
aws ec2 describe-volumes --filters Name=tag-key,Values=kubernetes.io/created-for/pvc/name --query 'Volumes[].VolumeId'
aws elbv2 describe-load-balancers --query 'LoadBalancers[?starts_with(LoadBalancerName,`k8s-vet2`)].LoadBalancerName'
```

**잠깐 멈추기만 할 때** (지우지 않고 다음에 이어서):

```bash
# kubeadm EC2 3대 — 디스크 요금만 남는다. 다시 켜면 공인 IP 가 바뀐다 (4장 끝의 kubeconfig 수정)
aws ec2 stop-instances --instance-ids $CP $W1ID $W2ID

# RDS — 저장 공간 요금만 남는다. 7일이 지나면 AWS 가 저절로 다시 켠다
aws rds stop-db-instance --db-instance-identifier vet2-db

# EKS — 노드는 멈출 수 없다. 앱을 0 개로 줄이면 Auto Mode 가 노드를 없앤다 (약 2분)
export KUBECONFIG=$PWD/v2/_run/kubeconfig-eks
for ns in vet2 vet2-rds; do kubectl -n $ns scale deploy --all --replicas=0; done
kubectl -n vet2 scale sts mysql --replicas=0
```

EKS 컨트롤 플레인과 ALB 는 멈추는 기능이 없어 요금(시간당 약 0.16달러)이 계속 나간다. MySQL 의 EBS 볼륨은 PVC 가 남아 있으므로 데이터와 함께 유지된다.

## 부록 A. 자주 만나는 문제

| 증상 | 원인 | 해결 |
|---|---|---|
| `./gradlew` 가 `Failed to exec spawn helper` | JDK 업데이트 뒤 옛 Gradle 데몬 | `./gradlew --stop` |
| compose 에서 서비스가 DB 에 못 붙음 (503) | 비밀번호를 바꿨는데 볼륨은 옛 비밀번호로 초기화돼 있음 | `docker compose ... down -v` 뒤 다시 `up` |
| web 이 `address already in use` | WSL 배포판끼리 네트워크를 함께 쓴다 (Docker Desktop 등) | `WEB_PORT=28090` |
| `ImagePullBackOff` (kubeadm) | ECR 로그인 Secret 이 없거나 12시간이 지났다 | `v2/k8s/kubeadm/ecr-pull-secret.sh -n <ns>` |
| `mysql-0` 이 `Pending` (kubeadm) | StorageClass 가 없다 | `kubectl apply -f v2/k8s/cluster/kubeadm/storage.yaml` |
| StatefulSet 적용이 `Forbidden` | `volumeClaimTemplates` 는 바꿀 수 없다 | 데이터가 없을 때만: sts 와 pvc 를 지우고 다시 적용 |
| `mysql-0` 이 `Pending` (EKS) | `gp2` 를 썼다 | `vet2-ebs` StorageClass |
| kubectl 이 인증서 오류 (EC2 재시작 뒤) | 공인 IP 가 바뀌었다 | kubeconfig 서버 주소 수정 + `tls-server-name: kubernetes` |
| 웹이 안 열린다 (다른 곳에서) | 보안 그룹·ALB 가 처음 만든 PC 의 IP 에만 열려 있다 | `MY_CIDR=<새 IP>/32` 로 `stacks.sh up network`, `apply.sh` 다시 |
| `aws` 가 `session has expired` | 로그인 세션 만료 | `aws login` |
